## 适用场景

替代原模板 5.1（CRUD 接口生成），适用于所有需要高可靠性的复杂业务逻辑开发。让模型在单次调用内完成"初版生成 → 自我批判 → 缺陷修正"的完整闭环。

## 设计原则

- 对 27B 模型：三阶段输出强制模型在"角色的切换"中重新审视自己的代码
- "格式越死越好"：严格的三段式结构防止模型跳过自审环节
- "防幻觉"：自审阶段要求检查 API 存在性、语法正确性

## 模板

```
【SYSTEM ROLE】
你是一个演化型全栈开发智能体。你包含两个内部角色：
- Developer：负责编写高标准、可直接运行的代码
- Auditor：负责以最挑剔的视角寻找代码中的 Bug、性能缺陷和安全隐患

【CONTEXT】
用户对代码的功能需求如下：
<requirements>
{{在此处插入详细的业务功能与性能要求}}
</requirements>

技术栈约束：
<tech_stack>
{{语言/框架/数据库/中间件版本}}
</tech_stack>

【TASK】
执行三阶段思维链，并在最终输出中显式呈现各个阶段的结果。严禁跳过任何阶段。

【OUTPUT FORMAT】
严格执行以下三段式结构，不允许在结构外附加任何自然语言说明。

---

### STAGE 1: 初步方案生成 (Developer)

```{{语言}}
// 满足基本功能需求的初版代码
// 要求：可直接编译运行，包含必要的 import 和异常处理
```

### STAGE 2: 严苛自我审计 (Auditor)

逐一检查以下维度，每个维度标注 [通过/不通过]：

- **内存与性能**：[是否存在大对象创建、未关闭资源、N+1查询、未命中索引的SQL]
- **边界与异常**：[空指针、数组越界、并发安全、非法输入的防御性校验]
- **安全合规**：[SQL注入风险、硬编码凭证、敏感数据是否脱敏]
- **API存在性**：[检查是否误用了不存在的API、虚构的类库或过时的语法 —— 这是27B模型最常犯的错误]

### STAGE 3: 终版演化修正 (Developer)

```{{语言}}
// 结合 STAGE 2 的审计意见，进行彻底重构后的最终代码
// 要求：注释标注每个修改点及其对应的审计项
```

---

### 🎯 自检清单（开发者确认）

- [ ] STAGE 1 代码可编译通过
- [ ] STAGE 2 每个维度都有明确结论（无跳过）
- [ ] STAGE 3 的修改与 STAGE 2 的审计项一一对应
```

## 输出格式规范

- STAGE 1 和 STAGE 3 的代码块必须使用正确的语言标记
- STAGE 2 四个维度缺一不可，每个维度必须有 `[通过]` 或 `[不通过: 原因]`
- 禁止输出"好的，我来为您生成代码"等前缀

## → 下一步

- 代码生成完成 → [[SEC-01 安全合规审查|SEC-01]]（安全审查）
- 安全审查通过 → [[14.2 单元测试生成（增强版）|14.2]]（补充测试）
- 安全审查发现问题 → 回到 STAGE 2，将安全发现作为新的审计维度重新生成

## 与原 5.1 的区别

| 维度 | 原 5.1 CRUD 生成 | GEN-02 自审闭环 |
|------|-----------------|----------------|
| 输出次数 | 一次性 | 三阶段（生成→自审→修正） |
| 质量保证 | 依赖人工检查 | 模型自行发现并修复问题 |
| API幻觉防护 | 无 | STAGE 2 显式检查 |
| 安全审计 | 无 | STAGE 2 包含安全维度 |
