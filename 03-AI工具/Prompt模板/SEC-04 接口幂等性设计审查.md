## 适用场景

金融交易、支付、扣款、库存扣减、对账等场景的接口设计审查。幂等性缺失会导致重复扣款、重复入账等资损事故——这是银行内网开发的**硬性红线**。

【幂等性审查标准】
金融交易接口必须满足以下任一幂等机制：
1. 唯一业务键（如订单号、流水号）+ 数据库唯一约束
2. 幂等令牌（Idempotency-Key）+ Redis/数据库去重
3. 状态机保护（如"待支付→已支付"，不允许重复状态转换）
4. 乐观锁版本号（version 字段 + WHERE version = ?）

仅依赖"前端按钮禁用"不算幂等保证。

【TASK】
逐接口审查幂等性设计，标注缺失项并给出具体修复方案。

【OUTPUT FORMAT】

| POST /api/payment/create | POST | 否 | 无 | 🔴 高 |

### 🚨 缺失项详情
**接口**: POST /api/payment/create
**风险描述**: 网络超时后客户端重试会产生两笔支付。当前仅依赖前端按钮禁用，CDP 重放可直接绕过。
**修复方案**: 
1. 前端生成 payment_id（UUID），传入后端
2. 数据库 t_payment 表 payment_id 字段加 UNIQUE 约束
3. Service 层捕获 DuplicateKeyException，查询已有记录并返回

## 常见幂等性反模式

| 反模式 | 问题 | 正确做法 |
|--------|------|----------|
| 仅前端防重 | CDP 重放、curl 直接调用绕开 | 后端唯一键/令牌 |
| SELECT 后 INSERT | SELECT 和 INSERT 之间有竞态窗口 | INSERT ... ON DUPLICATE KEY / 唯一约束 |
| 时间戳做唯一键 | 并发请求可能产生相同时间戳 | UUID/雪花ID |
| Redis 去重不持久 | Redis 重启后去重记录丢失 | 数据库唯一约束兜底 |
