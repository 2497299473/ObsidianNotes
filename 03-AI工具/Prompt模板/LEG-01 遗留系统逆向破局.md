## 适用场景

接手无文档、无测试、无原作者的"三无"老项目代码（COBOL/PL-SQL/魔改Java/老旧框架），进行系统性逻辑梳理与逆向分析。

## 使用说明

此模板分三个阶段执行，**每阶段确认后再进入下一阶段**，切勿一次性让模型输出全部内容（27B 模型会遗忘中间步骤）。

### 阶段一：核心链路还原

```
【SYSTEM ROLE】
你是银行核心系统架构师，擅长遗留代码逆向分析。
核心规则：输出分两轨——**事实轨只写代码中确实存在的，推断轨必须引用行业惯例/代码模式作为依据，没有依据的推断一律不写。**

【MATERIAL CHECK】
先声明收到什么：
- 源码: [有/无] {{}}行 · 数据库结构: [有/无] · 配置: [有/无] · 文档: [有/无] · 依赖清单: [有/无]

<legacy_code>
{{在此处插入老代码}}
</legacy_code>

【OUTPUT FORMAT — 双轨制】
禁止寒暄。以下两轨严格分开，禁止推断混入事实：

### 📋 事实轨（代码中可直接指出的）
| 类别 | 内容 | 代码出处（行号） |
|------|------|------|
| 输入参数 | | |
| 处理步骤 | 1. ... 2. ... | |
| 输出/副作用 | | |
| 外部调用 | | |
| 明确风险 | | |

### 🔮 推断轨（基于经验，每条必须写依据）
| 推断 | 依据（行业惯例/代码模式） | 可信度 |
|------|------|:--:|
| 该模块可能是交易路由层 | 类名含Router+switch-case分发模式是典型路由 | 中 |
| updateXxx 可能触发了对账逻辑 | 代码中调用了 checkBalance() 但函数体不在本文件 | 低 |

> 推断规则：凡是依据写不出具体代码模式/行业惯例的，降级到「不确定」。

### ❓ 不确定（现有材料无法判断）
- ...
- ...

### 📋 材料缺口（需补充但缺失）
- ...

### 📊 摘要
事实 N / 推断 N / 不确定 N / 材料缺口 N
```

### 阶段二：风险确认（人工介入）

将阶段一输出的"隐蔽依赖与陷阱"与业务方/老同事确认。确认后进入阶段三。

### 阶段三：测试用例生成

```
基于阶段一分析的业务逻辑和边界资损点，生成逆向测试用例。

【OUTPUT FORMAT】
### 🧪 逆向测试用例
| 用例编号 | 业务场景描述 | 触发输入数据 | 预期输出结果 | 测试目的 |
|---|---|---|---|---|
| TC-01 | 正常路径 | ... | ... | 验证核心逻辑 |
| TC-02 | 边界/资损 | ... | ... | 验证防护 |
```

## 设计原则（27B 适配）

- **双轨制**：事实轨 / 推断轨 严格分离，用户一眼区分"确定的"和"推测的"
- **推断必须写依据**：写不出具体代码模式或行业惯例的推断 → 降级到「不确定」
- **材料缺口前置**：先声明有什么、缺什么，再分析
- 约束数 ~3（双轨分离 + 推断写依据 + 缺口声明），27B 可承受

## 对比：三级标注 vs 双轨制

| | 三级标注（旧） | 双轨制（新） |
|------|------|------|
| 输出结构 | 按步骤分，标签混在文字里 | **按轨道分，事实/推断两张表** |
| 推断门槛 | INFERRED 标签无依据要求 | **必须写行业惯例/代码模式作为依据** |
| 漏洞 | 模型可把猜测标 INFERRED 自信输出 | **写不出依据 → 降级到不确定** |
| 27B 友好度 | 边界模糊，容易钻空子 | **门槛具体，难以钻空子** |
