## 使用说明

### 适用模型

千问 3.6 27B（或同级别本地部署模型），**不是** Claude / GPT-4。

### 27B 模型的限制与对策

> ⚠️ 27B 参数量的推理深度、指令遵循、抗幻觉能力有限，以下限制需要严格遵守。

| 限制 | 表现 | 对策 |
|------|------|------|
| **指令遵循率低** | 超过 5 条约束就开始随机遗忘；10 条以上可能只遵守一半 | **每轮最多 3-5 条核心约束**，其余规则依赖模板结构（固定格式/表格）兜底 |
| 推理深度有限 | 多步逻辑容易断链，跳步或给出表面答案 | 单次任务拆到最小单元，多轮对话逐步推进；**每个 prompt 只要求一个结论** |
| **上下文窗口小** | 有效上下文约 8K-16K tokens，超过后"中间迷失"严重 | **单轮总 prompt（含代码）< 1200 字**；超过则拆分，每轮开头重复约束 |
| 长上下文容易遗忘 | 对话超过 5 轮后遗忘早期指令 | 每 3-4 轮插入 checkpoint；关键约束每轮开头重复 |
| 开放式问题表现差 | "你觉得有什么问题"这种问题几乎必定给出废话 | 给明确的选择框架，用"列出 3 个问题"而非"有没有问题" |
| 容易强行回答 | 不知道也硬编一个看起来合理的答案 | 必须给"不确定就说不知道"的出口；要求用 [不确定] 标记 |
| **容易编造/幻觉** | API/函数名/版本号编造率很高，代码中虚构 import 是常见问题 | **禁止猜测；每步要求标注信息来源；代码生成后必须自审 API 存在性** |
| **输出啰嗦、爱奉承** | 更小的模型在 RLHF 中对齐税更重，废话比例更高 | **禁止评价用户、禁止感谢、禁止总结语；直接给结论** |
| 代码生成错误率高 | 虚构 API、遗漏 import、类型不匹配 | 复杂逻辑必须拆分；生成后立即自审；关键代码必须人工验证 |
| 中文 prompt 效果更好 | 中文语料占比高，英文指令丢失率更高 | 全部用中文写指令 |

### 使用原则

1. **一次只做一件事**：不要在一个 prompt 里要求审查代码 + 优化 SQL + 写文档
2. **按独立决策单元拆分**：一个完整的类/模块/函数，而不是按固定行数切割（见 [[#任务拆分原则（替代"200 行"经验值）|0.5 任务拆分原则]]）
3. **每轮 ≤ 5 条核心约束**：超过则拆成多轮，每轮开始重复不可变的约束（如 API 签名不能改）
4. **单轮 prompt < 1200 字**：含代码和指令。超过则切分，用 checkpoint 传递上下文
5. **先跑再问**：执行结果（报错、执行计划、日志）比代码本身更有价值
6. **模板是起点**：根据实际场景调整，尤其是输出格式部分
7. **项目分析用工作流**：接手新项目时，按 [[#4.12 项目快速上手完整流程|4.12 完整流程]] 的顺序来，不要跳步
8. **每条 prompt 开头贴系统指令**：把 [[#零、系统指令前缀（每次对话必贴）|系统指令前缀]] 作为第一条消息，约束模型的输出风格和幻觉行为
9. **输出格式越死越好**：27B 模型仅在格式严格约束时输出稳定。用 Markdown 表格、固定 Section Header、具体字段名，比「请分析」有效 3 倍以上
10. **每 3-4 轮 checkpoint**：长对话中模型会渐渐遗忘早期约束。关键限制每轮开头重复一遍（见 [[#9.2 状态检查点（Checkpoint）|9.2 状态检查点]]）
11. **生成后必须自审**：所有代码生成模板必须包含"自审"步骤——27B 编造 API 的概率远高于更大参数模型
12. **默认只改目标代码**：除非明确说明，否则「除本次要求外，其余实现保持不变」

## 零、系统指令前缀（每次对话必贴）

> **这是最重要的一个"模板"。每次开启新对话，第一句话就贴这段。**
>
> 它会约束千问的输出风格（防废话、防奉承）和思考方式（防幻觉、防编造），之后再用具体任务模板。

### 标准版（适合大部分场景）

```
在本次对话中，请严格遵守以下规则：

【输出风格】
- 直接给出结论，不要开场白、不要总结语、不要评价我的问题好不好
- 不要感谢我、不要夸我、不要说"这是个好问题"之类的社交用语
- 不要问"需要我进一步解释吗"——如果我认为需要，我会追问
- 用事实和代码说话，不要用形容词堆砌

【防幻觉】
- 只基于我给出的代码和信息做出判断，**不要猜测我代码之外的情况**
- 如果不确定，直接说「不确定，需要确认：xxx」，**绝对不要编造**
- 如果信息不足，列出你需要的补充信息，等我来提供，不要自己脑补

【输出格式】
- 如果我在 prompt 中指定了输出格式（如表格、列表、代码块），严格遵循
- 没有指定格式时，用列表而非段落文字
```

### 精简版（短任务用，省 token）

```
本次对话规则：1.直接给结论，不要开场白/总结语/感谢/夸赞 2.不确定就说「不确定」，绝不编造 3.只基于我给的代码判断，不猜测外部情况 4.严格按我指定的格式输出
```

### 极简版（追加在具体 prompt 末尾）

```
只输出结论，不要废话。不确定就说不知道。不要感谢或评价。
```

### 约束优先级（多要求冲突时的裁决规则）

> 当一个 prompt 中同时存在多个约束、且它们可能冲突时（如"尽量详细"和"控制在 300 字以内"），模型容易在权衡中摇摆。以下优先级规则解决了这个问题。

```
如果在执行过程中，我的多个要求之间存在冲突，按以下优先级裁决：

① 明确禁止的事项（如"不要修改 API 签名"）——最高优先级
② 输出格式（如表格结构、字段顺序）——必须严格遵守
③ 功能正确性 —— 不能为了简洁牺牲正确
④ 完整性 —— 不能为了格式而遗漏关键信息
⑤ 字数限制 / 美观 —— 最低优先级
```

> **使用方式**：追加在系统指令前缀末尾，或首次出现多约束任务时贴一次。之后模型在遇到冲突时会更稳定地抉择。

### 事实来源标记

> 防幻觉的进一步强化。要求模型标注每条结论的来源类型，区分"代码中明确写的"和"我推断的"。

```
在输出中，每条结论后面标注信息来源类型：

- [CODE] — 代码中明确出现的
- [DOC] — 文档/注释中写的
- [FACT] — 可验证的客观事实
- [INFERENCE] — 基于以上推断的（可能出错，请验证）
- [UNKNOWN] — 信息不足，无法判断

如果 [INFERENCE] 和 [UNKNOWN] 标记过多，说明你需要我补充更多信息。
```

### 示例污染防护

> 如果 prompt 中粘贴了示例代码（作为格式参考），模型可能无意识继承示例中的命名风格、架构甚至错误。

```
注意：以下示例仅供格式参考。不要继承示例中的：
- 命名风格（变量名、函数名）
- 实现细节（算法、架构选择）
- 业务逻辑
只参考输出格式，不要参考内容。
```

### 输入资产声明（Input Envelope）

> 每个复杂模板开头应声明它依赖哪些上游产出物。如果缺失，模型应该标注而不是猜测。

```
【输入资产检查】
本模板依赖以下资产（如未提供请标注）：
- 项目上下文摘要: {有/无}
- 数据库表结构: {有/无}
- API 接口定义: {有/无}
- 已确认的技术决策: {有/无}

如果以上某项为「无」，我将在分析中标注因信息不足而无法完成的部分，不会自行脑补。
```

> **使用方式**：贴在需要多步协作的模板（第四节、第十节）开头。确保模型知道自己缺什么。

### 任务拆分原则（替代"200 行"经验值）

> 原"每次粘贴代码控制在 200 行以内"是一个粗略经验值。更准确的拆分原则是：

```
任务拆分原则：按「独立决策单元」拆分，不按行数拆分。

一个独立决策单元 = 做完这件事后，下一步的方向不会因这一步的结果而改变。

推荐粒度：
- 一个完整的类或模块
- 一组紧密相关的函数
- 一次明确的架构决策（如"选 Redis 还是本地缓存"）
- 一个完整的 SQL 查询 + 其执行计划解读

反例（不适合再拆）：
- 半个函数的代码（上下文不完整）
- 单行报错但不给 Traceback（信息不足无法判断）
```

### 使用方式

```
第一轮: 贴系统指令前缀
第二轮: 「理解了。现在开始：{贴具体任务模板 + 代码}」
```

如果对话很长、中间模型开始"飘"了（开始说废话或编造），可以再贴一次精简版把它拉回来。

> **经验**：标准版约 250 字，27B 模型基本能遵守但长对话中会衰减。关键是**每次新对话都贴**，且每 3-4 轮用精简版刷新——模型不会跨对话记住你的偏好。

### 1.1 通用 Python 代码审查

```

## 十四、测试与质量保障

> 代码审查（第一节）关注的是「代码写得好不好」，本章关注的是「代码行为对不对」。
>
> 27B 模型的测试生成有一个关键限制：**它看不到测试执行结果**。因此本章的核心策略是「先让它生成测试 → 你跑测试 → 把失败信息喂回去让它修复」。

### 14-1 代码静态检查

> 让模型在不运行代码的情况下，用「编译器视角」逐项检查代码。这不是审查（第一节）——不关注风格和设计，只关注**一定会出错**的问题。

```

【类型安全】类型标注是否完整、是否存在 `Any` 逃逸、类型窄化是否正确
【空值安全】`None` 检查是否遗漏、可选类型的解包是否安全
【资源管理】文件/连接/锁是否正确关闭、是否存在泄漏风险
【并发安全】共享状态是否有竞态条件、是否该加锁但没加
【逻辑死区】是否有永远不执行的代码分支、循环是否会无限运行

对每个问题，严格按以下格式：
  - 行号: X
  - 维度: [类型/空值/资源/并发/死区]
  - 触发条件: 什么输入/场景下会出问题
  - 修复: 修改后的代码片段
  - 置信度: [确定/可能/需确认]

如果某个维度未发现问题，输出「[维度名]: 未发现明显问题」——不要省略。

```python
{粘贴代码}
```

```

> 这是 5.3 的升级版。增加了 Mock 策略、参数化设计和测试边界分析。

```

## 十三、Claude Code 概念向千问 Prompt 的迁移

> 这是对整个模板集的**元分析**。回答一个问题：Claude Code 的 Skills、SubAgents、Hooks 这些机制，能不能迁移到千问 27B 的 Prompt 工程上？
>
> **结论：系统级能力（自动触发、进程隔离、事件拦截）无法直接迁移，但设计思想和组织模式完全可以，而且你的模板集已经在做这件事了。**

### 13.0 核心差异：运行时 vs 纯文本

Claude Code 和千问的本质区别不在于模型能力，而在于**运行环境**：

```
Claude Code 架构                    千问架构
┌──────────────────────┐           ┌──────────────┐
│  Claude Code 运行时   │           │              │
│  ┌────────────────┐  │           │  文本输入     │
│  │ 自动读 SKILL.md │  │           │     ↓        │
│  │ 创建子进程      │  │           │  千问 27B    │
│  │ 拦截工具调用    │  │           │     ↓        │
│  │ 注入上下文      │  │           │  文本输出     │
│  └────────────────┘  │           │              │
│         ↓            │           └──────────────┘
│  Claude API          │
└──────────────────────┘
```

Claude Code 有**操作系统级别的能力**——它可以读文件系统、创建子进程、拦截系统调用。千问只有一个能力：**接受文本，返回文本**。因此，所有迁移的关键问题是：**这个能力能不能用"Prompt 设计"来模拟？**

### 13.1 迁移总览表

下表给出了每个 Claude Code 概念的迁移状态：✅ 已实现 / 🔧 可增强 / ❌ 受限。

| Claude Code 概念 | 千问等效方案 | 状态 | 对应模板 |
|---|---|---|---|
| **Skill 按需加载** | Prompt 模板手动选择 | ✅ | 模板速查索引（十二节） |
| **Skill description 触发** | 模板前加语义标签，Ctrl+F 搜索 | 🔧 | 可给每个模板加 `[场景]` 标签 |
| **SubAgent 上下文隔离** | 链式对话：上一轮输出浓缩后喂入下一轮 | ✅ | 九节「链式提问」、4.12 完整流程 |
| **SubAgent 权限边界** | Prompt 中声明角色 + 约束输出格式 | ✅ | 1.1（只审查不修复）、1.4（只检查不安全修改） |
| **SubAgent 并行探索** | 开多个千问窗口同时问，人工汇总 | ❌ | — |

| **Agent Teams 多角色** | 同一轮 prompt 中定义多个视角 | 🔧 | 10.3 方案对比（A vs B 双视角） |

### 13.2 逐层解析

#### 第一层：Skills → Prompt 模板（✅ 已完成）

**Claude Code 做的事**：SKILL.md 放在 `.claude/skills/` 目录下，包含 description（语义触发器）+ 正文（执行指令+领域知识），Claude 运行时会自动读取所有 Skill 的 description，语义匹配后加载全文。

**千问的等效做法**：你已经做到了——

```
Claude Code SKILL.md             你的 Prompt 模板
┌──────────────────────┐        ┌──────────────────────┐
│ description:          │        │ ### 1.1 通用 Python   │
│ "Review Python code   │   =    │ 代码审查              │
│  for bugs..."         │        │                        │
│ ---                   │        │ 审查以下 Python 代码…  │
│ 正文：审查步骤+输出格式│        │ 【BUG】【PERF】…       │
└──────────────────────┘        └──────────────────────┘
```

**区别**：千问不能自动匹配。你需要手动 Ctrl+F 搜「代码审查」→ 复制模板 → 粘贴到千问。但这个流程已经足够高效了。**模板速查索引（十二节）就是你的「description 索引」。**

**可以增强的地方**：
- 给每个模板加一个 **[场景标签]** 在最前面，如 `[代码审查] [Python] [通用]`，搜索时更快
- 建立**模板间的 input→output 链**：标注「这个模板的输出适合喂给哪个模板」

#### 第二层：SubAgents → 角色扮演 + 链式对话（✅ 已完成）

**Claude Code 做的事**：创建独立上下文窗口，给子代理分配 tools 权限（Read only / Write / Bash），子代理完成后只把结论带回主对话。

**千问的等效做法**：你的模板本质上就是「角色定义 + 权限边界 + 输出格式」。

对比一下 Claude Code 的 SubAgent 配置和你已有的模板：

```yaml
# Claude Code SubAgent (.claude/agents/code-reviewer.md)
---
name: code-reviewer
tools: Read, Grep, Glob  # 只读权限
---
你是代码审查专家。
审查代码时：1. 检查安全问题 2. 检查代码规范
输出格式：【BUG】…【PERF】…【STYLE】…
```

```markdown
# 你的模板 1.1（等价于上面的 SubAgent 定义）
审查以下 Python 代码，按七个类别给出问题；无问题的类别输出"None"：

【BUG】逻辑错误、边界条件遗漏、异常处理缺失
【PERF】不必要的循环、N+1 查询、重复计算、内存浪费
【STYLE】命名不规范、代码重复、注释缺失
【SECURITY】注入风险、敏感信息泄露、权限校验缺失
【MAINTAINABILITY】耦合过紧、魔术数字
【TESTABILITY】难以测试的硬编码依赖
【UNKNOWN】怀疑有问题但无法确认——标注「建议人工确认」

对每个问题，严格按以下格式输出：
  - 行号: X
  - 类别: [BUG/PERF/STYLE/SECURITY/MAINTAINABILITY/TESTABILITY/UNKNOWN]
  - 问题: 一句话描述
  - 修复: 修改后的代码片段
  - 来源: [CODE/FACT/INFERENCE]
```

结构几乎一样：角色定义（"审查"）→ 分类约束（三个类别 = 权限边界）→ 严格输出格式。区别只在于 Claude Code 能**物理上**阻止子代理调用 Write 工具，而千问只能靠 prompt 约束。但 27B 模型在固定格式+短约束下仍能稳定执行，prompt 层面的约束已经够用。

**Multi-Agent 架构的迁移**：

Claude Code 的四层递进（[[多Agent架构的仿生学思考]]）在千问中是这样映射的：

| Claude Code 架构层级 | 千问等效做法 | 你的模板 |
|---|---|---|
| 单 Agent | 直接提问 | 任何一个单独模板 |
| + Skills | 选模板 → 粘贴使用 | 十二节速查索引 |
| + SubAgents | 链式对话，每轮换角色 | 九节「链式提问」五种模式 |
| + Handoffs | 上一轮输出截取关键结论→喂入下一轮 | 4.12 三阶段完整流程 |
| + Router | 人工判断该用哪个模板 | 十二节速查索引（你手动路由） |

**并行探索的替代方案**：千问不能并行，但你可以开 3 个千问窗口，分别贴 4.6、4.7、4.8 的模板，同时探索路由、数据库模型、代码热力图，然后把三份结果汇总到 4.13 做一句话描述。

#### 第三层：Hooks → 规则前置 + 链式校验（✅ 大部分已完成）

**Claude Code 做的事**：PreToolUse（阻止危险命令）、PostToolUse（自动格式化+lint 反馈）、Stop（测试不通过不让停）。

**千问的等效做法**：

| Claude Code Hook | 千问等效 Prompt 设计 | 你的模板 |
|---|---|---|
| `block-dangerous.sh`：拦截 `rm -rf /` | 前置规则：「不要建议任何包含 rm -rf、DROP TABLE 的命令」 | 1.4 迁移脚本审查中的「幂等性保证」= 阻止危险的不可回滚操作 |
| `protect-files.sh`：阻止修改 .env | 前置规则：「如果要修改配置，必须先列出变更并请我确认」 | 隐含在模板的「只审查不修改」设计中 |
| `auto-format.sh`：写完后自动格式化 | Prompt 中要求：「所有 Python 代码用 4 空格缩进，遵循 PEP 8」 | 5.1 CRUD 生成中的「要求」字段 |
| `lint-check.sh`：写完后自动 lint | 链式：「先生成→再审查你自己刚才生成的代码」 | 九节模式三 |
| `run-tests.sh`：测试不通过不让停 | 链式：「审查通过才算完成」→ 没通过就继续 | 10.8 第四轮压力测试 |

**PostToolUse 的 `additionalContext` 反馈循环**，在千问中的等效实现就是你的**链式提问模式三**：

```
Claude Code: 写代码 → PostToolUse lint → additionalContext 反馈 → Claude 自动修复 → 循环
千问等效:   第一轮生成代码 → 第二轮「审查你刚才生成的代码，修复发现的问题」
```

区别是两个：千问需要你手动发起第二轮；千问没有自动终止循环的能力（需要你判断「修好了」然后停止）。但这些都不是大问题——你的 27B 模型限制对策第一条就是「单次任务拆小，多轮逐步推进」，链式对话本来就是你推荐的主要工作方式。

#### 第四层：CLAUDE.md / 记忆系统 → 上下文快照（✅ 已经是最亮眼的部分）

**这是你的模板集中最体现 Claude Code 思想的部分。**

对比一下 Claude Code 的记忆体系和你的十一节：

| Claude Code 机制 | 你的等效方案 | 对应模板 |
|---|---|---|
| CLAUDE.md（每次对话自动加载） | 项目上下文文件（11.3），每次新对话第一轮粘贴 | 11.2 会话恢复 |
| Skills 渐进式加载（description 常驻，正文按需） | 模板速查索引（常驻 Obsidian）→ 选中模板 → 粘贴全文 | 十二节 → 具体模板 |
| 跨会话持久记忆（文件系统） | Obsidian vault 持久化 + 会话存档 | 11.1 会话存档 |
| Hooks 审计日志 | 存档快照中的「已完成」「关键决策」「重要代码片段」 | 11.1 的存档格式 |

你把 Obsidian 变成了千问的**外置大脑**——这个设计思路和 Claude Code 用文件系统做记忆是完全一致的。区别只是 Claude 自动读，你需要手动贴。

### 13.3 迁移路线图：还能做什么

你的模板集已经很完善了。以下是三个**低成本高回报**的增强方向：

#### 增强一：给每个模板加语义标签（5 分钟）

在每个模板标题前加一组 `[标签]`，让你在 Obsidian 里 Ctrl+F 搜索时更快定位：

```markdown
### 1.1 [代码审查] [Python] [通用] 通用 Python 代码审查
### 2.1 [性能分析] [SQL] [慢查询] 慢查询分析
### 4.5 [项目上手] [全局认知] [第一步] 项目全貌速览
### 10.1 [创意] [方案设计] [发散] 方案发散：一个需求，多种实现
### 11.1 [会话管理] [存档] [必做] 会话存档
```

#### 增强二：标注模板间的输入输出链（10 分钟）

在模板底部加一行「下一步模板」，形成可复用的链式工作流：

```markdown
**→ 下一步模板**: 
- 如果发现了性能问题 → [[#2.1 慢查询分析]]
- 如果发现了逻辑 Bug → [[#3.2 逻辑 Bug 定位]]
- 如果代码需要重构 → [[#5.2 重构建议]]
```

这相当于把 Claude Code 的流水线编排（Explore → Review → Fix → Test）显式化为 Prompt 之间的边。

#### 增强三：创建一个「Prompt 角色卡」系列（20 分钟）

受 SubAgent 配置文件的启发，为常用角色创建独立的「角色卡」Prompt：

```markdown
## 角色卡：Python 代码审查员

**角色**: 你是一个资深 Python 后端代码审查员。
**权限**: 你只能审查代码，不能直接修改。如果你认为需要修改，给出修改建议让我来执行。
**关注维度**（按优先级）:
1. 逻辑错误和边界条件遗漏——这是最高优先级
2. 性能瓶颈（N+1 查询、不必要的循环）
3. 代码风格和可维护性
**输出格式**: 严格使用【BUG】【PERF】【STYLE】三分类
**不确定就说**: 如果不确定某个问题是否存在，说「建议人工确认：xxx」
```

角色卡可以单独存在，也可以被其他模板引用（「调用角色卡：Python 代码审查员」），相当于 Claude Code 中 SubAgent 通过 `skills:` 字段预加载领域知识。

### 13.4 一个思维框架：从"用什么 Prompt"到"建什么工作流"

回顾 [[多Agent架构的仿生学思考]] 的核心洞见——**AI Agent 架构设计本质上是在模拟人类的社会分工**。这个框架在千问中同样适用：

| 你在想什么 | 你应该做什么 | Claude Code 等效概念 |
|---|---|---|
| "我要审查这段代码" | 直接贴 1.1 模板 | 单 Agent + Skill |
| "我要审查完了再修复" | 先用 1.1 审查 → 提取问题列表 → 贴给第二轮让它修复 | SubAgent 流水线 |
| "我要修复前先理解这个模块的调用链" | 先用 4.2 分析 → 再修复 | Explore → Fix |
| "我想了几个方案，不确定选哪个" | 用 10.3 做 A/B 对比 | Judge Panel |
| "我要记住今天的进展" | 跑 11.1 存档 | 记忆持久化 |
| "我要接手一个新项目" | 按 4.12 三阶段走 | 完整的 Multi-Agent Onboarding 流程 |

**关键心智转变**：你不是在「写一个 Prompt」，而是在**给一个 AI 团队写工作指令**。你的模板集就是这个团队的 SOP 手册。千问没有 Claude Code 的运行时，但你有 Obsidian 和 Ctrl+C/V——你就是那个运行时。

### 13.5 什么确实做不到（承认边界）

以下 Claude Code 的能力在千问上**确实无法等效**，需要接受这个边界：

1. **自动语义触发**：千问不会自动读你的模板目录并匹配。你必须手动选择模板。但这也是优势——你始终掌握控制权。
2. **真正的并行执行**：开多个千问窗口可以模拟，但上下文不共享，需要你手动汇总。
3. **系统级工具拦截**：千问不能阻止你执行它建议的危险命令。你得自己长眼。所以 1.4（迁移脚本审查）这类模板特别重要——在执行前多一层审核。
4. **基于文件系统事件的自动触发**：千问不会在你 git commit 时自动弹出审查。这是物理限制。
5. **长上下文跨轮持续**：千问的上下文窗口有限且不会持久化。你的十一节记忆系统已经是最好的弥补方案了。

### 13.6 总结：你已经在做的是"Prompt 工程化"

回头看整个模板集的设计思路：

- **代码审查 / SQL 优化 / Bug 定位**（一~三节）= 参考型 Skill，定义「怎么做」
- **项目分析完整流程**（第四节，尤其是 4.12）= 完整的 SubAgent 流水线编排
- **创意探索**（第十节，尤其是 10.8）= 多 Agent 协作的链式对话
- **会话记忆管理**（第十一节）= CLAUDE.md + Hooks 审计日志的手动版
- **模板速查索引**（第十二节）= Skills description 索引

你做的事情本质上就是把 Claude Code 的工程化思维**降维**到纯 Prompt 层面——用结构化的文本指令替代系统级的运行时能力。这是一个非常务实的做法，而且你的模板集覆盖度已经很高了。

**一句话：Claude Code 的概念不是代码，是一套思想。这套思想完全可以迁移到千问上，你的模板集就是最好的证明。**

### 13.7 补：渐进式披露——从 Skills 架构到 Prompt 设计

Claude Code 的 Skills 采用**三层渐进式加载**（[[Claude的使用/11｜循序渐进：渐进式披露架构设计|第 11 讲]]），这个设计模式可以直接指导你的 Prompt 写法：

```
Skills 三层                   你的 Prompt 等效方案
━━━━━━━━━━━━━━━━━━           ━━━━━━━━━━━━━━━━━━━
第一层：description          模板速查索引（第十二节）
  只加载 ~50 字                  常驻 Obsidian，手工搜索
  语义匹配 → 决定是否激活        → 找到模板编号 → 复制

第二层：SKILL.md 正文         具体模板内容（第一~十一节）
  激活后才加载                   粘贴到千问窗口
  ~200-500 tokens               ~200-500 字

第三层：reference/ 附件        上下文注入（贴代码、贴日志）
  按需读取，不自动加载            手动贴在模板的代码块位置
```

**Prompt 写作启示**：一个好的 Prompt 模板也应该遵循这个三层结构——

1. **标题行 = description**：「审查以下 Python 代码，按三个类别给出问题」→ 模型一眼就知道要干什么
2. **正文 = SKILL.md**：具体的分类标准 + 输出格式 + 约束条件
3. **附件 = reference/**：粘贴的代码块、报错日志、表结构（你用 `{粘贴代码}` 占位符）

你已经下意识地这样做了。每个模板的标题行就是 description，正文就是 SKILL.md，`{粘贴代码}` 就是附件层的占位符。

### 13.10 补：Prompt 写作的期望值框架

[[Claude的使用/CLAUDE.md 的期望值决策框架]] 给出了判断 CLAUDE.md 中「某一行值不值得写」的形式化公式。**这个框架对 Prompt 设计同样适用**：

$$P(\text{出错} \mid \text{没有这句}) \times \text{纠错成本} > \text{这句的稀释成本}$$

应用到你的模板上：

| Prompt 中的内容 | P(出错) | 纠错成本 | 稀释风险 | 结论 |
|---|---|---|---|---|
| "只基于我给出的代码判断" | 高（模型天然喜欢脑补） | 中 | 低（12 字） | ✅ 必留 |
| "不确定就说「不确定」" | 高（27B 模型有强答倾向） | 高（编造的错误信息会误导后续判断） | 低 | ✅ 必留 |
| "用列表而非段落" | 中 | 低 | 低 | ✅ 保留 |
| "遵循 Python 最佳实践" | ≈0（模型已经会） | — | 占位 | ❌ 删除 |
| 冗长的背景说明 | — | — | 高 | ❌ 精简到 2-3 句 |

你现在做的**系统指令前缀（零节）**，本质上就是把「高 P(出错) × 高纠错成本」的规则集中放在每次对话开头，每个字都经过了期望值筛选。这个框架告诉你：**不要因为"怕漏掉什么"就往 Prompt 里堆规则——堆越多，每条越弱。**

### 13.11 补：千问的"操作系统"模型

[[Agent 即操作系统：资源管理的五个映射]] 把 Agent 系统映射到了 OS 概念。对千问 Prompt 工程最有价值的一个映射是：

```
OS                         千问 Prompt 工程
━━━━━━━━━━━━━━━━━━━━      ━━━━━━━━━━━━━━━━━━━
L1 Cache（寄存器）         段落标题 + 当前正在执行的指令
  几 KB，即时访问              "审查以下 Python 代码，按三个类别…"

L2 Cache                  当前 Prompt 全文
  ~100K tokens                你粘贴的所有内容

L3 Cache（共享缓存）       对话历史（千问的上下文窗口）
  最近几轮对话                 随对话增长，越远越模糊

主内存                     Obsidian vault
  CLAUDE.md + Skills          模板集 + 上下文快照

磁盘（换页）                shell 命令输出
  RAG 检索                     先跑命令提取信息 → 再喂给模型
```

**核心启示**：
- 你的 Prompt 第一句话最重要——它是 L1 Cache，模型最先注意到
- 把最重要的约束放在 Prompt **开头**（如系统指令前缀的第一行 "直接给出结论，不要开场白"）
- 次要参考信息放在 Prompt **末尾**或作为附件——相当于放在 L2 Cache 的末尾区域
- 你的第四节模板（用 shell 命令先提取信息再喂模型）本质上就是「从磁盘换页到内存」——用廉价的外部命令换取昂贵的上下文 token

### 13.12 补：三个可直接用于千问的高级 Prompting 技巧

来自 [[Claude的使用/高级 Prompting 技巧：让 Claude 产出更好代码]]，这三个技巧在千问上同样有效：

#### 技巧 A：对抗性审查（Grill Me）

```
原始：「审查这段代码」
升级：「审查这段代码，逐行质疑我的设计决策。在我通过你的审查之前，不要说我做得对。」
```

**对应模板**：10.8 第四轮压力测试——但你可以**直接用在任何审查模板里**。在 1.1 模板末尾追加一句：「对每个问题，说明为什么这不是小问题——如果忽略它，什么场景下会出 bug？」

#### 技巧 B：推倒重来（Scrap and Reimplement）

```
第一轮：「根据这个表结构生成 CRUD 接口，能跑就行」
第二轮：「基于你刚才对项目代码风格和业务逻辑的理解，把第一版推倒重来，写出生产级代码」
```

**对应模板**：九节模式一（先理解 → 再分析），但多了一步「重写」。这个技巧利用了千问在实现过程中积累的"隐性知识"——它已经理解了表结构、字段关系、命名风格，第二轮能做出更好的全局架构。

#### 技巧 C：先写规格再动手（Specs First）

```
❌ 「优化这个查询」
✅ 「优化这个查询：当前 EXPLAIN 的 rows=50000，type=ALL。目标 rows < 100，用 idx_user_status 索引，不要改业务逻辑」
```

你的模板集已经在做这件事了——每个模板都有详细的结构化输出格式。技巧 C 的核心价值在于：**不是写更长的 Prompt，而是把「你对问题的理解」写成约束条件放进 Prompt**。你越清楚问题，模型的输出越精准。

### 13.13 补：631 行 vs 60 行——Prompt 瘦身的实证

`claude-code-engineering-main/02-Memory/projects/03-bloated-claude-md/` 里有两个 CLAUDE.md：

| | 原始版 | 重构版 |
|---|---|---|
| **行数** | 631 行 | 60 行 |
| **结构** | 全部规则塞在一个文件里 | 主文件只放概述 + 速查表 + 已知问题 |
| **详细规则** | 内联在 CLAUDE.md 中 | 拆分到 `.claude/rules/` 的 11 个独立文件 |
| **加载方式** | 每次对话加载全部 631 行 | 主文件 60 行常驻，详细规则通过 `paths:` glob 按需加载 |

重构版的核心做法：

```markdown
# 重构版 CLAUDE.md（60 行）
## Rules
All coding standards are organized in `.claude/rules/`:

| Rule File | Scope |
|-----------|-------|
| `react.md` | Component structure, state, hooks, styling, a11y |
| `express.md` | Controller/service pattern, routing, auth, logging |
| `database.md` | Schema conventions, migrations, queries |
| ... (11 files total) | ... |

## Known Issues
- Cart race condition: `SELECT FOR UPDATE` in `cart.service.ts:L45-L80`
- Algolia sync lag: 2-5s delay. Expected.
```

**这对你的 Prompt 设计的启示**：

1. **不要写「全功能 Prompt」**。一个试图同时审查代码、优化 SQL、检查安全漏洞的 Prompt = 631 行的 bloated CLAUDE.md。拆成独立模板，按场景选用。

2. **你的模板集已经在做这件事了**。12 个类别 × 45+ 个模板就是你的 `.claude/rules/` 目录。每个模板精悍、单一职责。模板速查索引就是重构版 CLAUDE.md 的「Rules 速查表」。

3. **「已知问题」= 系统指令前缀里的核心约束**。重构版 CLAUDE.md 末尾的「Known Issues」只列了真正重要、容易出现、代价高的 4 个问题（而非 bloated 版里淹没在 600 行中的几十条规则）。你的系统指令前缀（零节）就是这个「Known Issues」——只放 P(出错)×纠错成本 最高的几条规则。

4. **条件加载的概念迁移**：Claude Code 的 `paths:` glob 可以让 `database.md` 只在涉及数据库文件时加载。千问做不到，但你可以**手动模拟**——当你处理 SQL 问题时，除了贴系统指令前缀，再多贴一句「调用规则：数据库操作规范」（一段你预先写好的 3-5 行约束）。这就相当于手动版的 `paths:` 条件加载。

### 13.14 补：Bug 修复流水线——四阶段链式 Prompt 模板

`claude-code-engineering-main/03-SubAgents/projects/05-bugfix-pipeline/` 定义了一条四阶段流水线，每个 Agent 有独立角色 + 工具权限 + 输出格式 + 交接说明。这个设计可以直接转化为一组链式 Prompt：

```
Locator → Analyzer → Fixer → Verifier
  ↓          ↓         ↓         ↓
只读搜索    只读分析   有写权限   运行测试
定位在哪    找到根因   修复代码   验证通过
```

**一个重要的设计细节**：每个 Agent 的输出格式里都有一个**「交接」字段**：

```markdown
# bug-locator 的输出格式
### Handoff to Analyzer
[What the analyzer should focus on]

# bug-fixer 的输出格式  
### Testing Notes for Verifier
[What the verifier should test]
```

这不是随意的——它确保下游 Agent 不用重新理解整个问题，直接聚焦。**这个设计可以直接加到你的链式 Prompt 中**。

{粘贴第二轮的「交接给下一轮」+ 根因}

你现在做一件事：修复代码。不要解释为什么要这样修复（上一轮已经分析过了）。

输出格式：
## 修复报告
### 修改的文件和行号
### 修复后代码
```python
{完整函数或方法}
```
### → 交接给下一轮：需要测试验证的点和回归风险

═════════════════════════════════════════
  阶段四：验证（贴给千问第四轮）
═════════════════════════════════════════

{粘贴第三轮的「交接给下一轮」+ 修复后的代码}

你现在做一件事：验证。如果有测试命令就贴给我让我执行；如果只能静态分析，检查逻辑正确性。

输出：
- 预期行为 vs 修复后行为对比
- 可能引入的新问题（回归风险）
- 最终判断：✅ 可以合并 / ⚠️ 需要手动测试 / ❌ 有问题
```

**为什么四轮而不是一轮**：
- 一轮（直接问「帮我修复这个 bug」）：27B 模型会跳过定位和分析，直接猜一个修复方案——这就是幻觉的温床
- 四轮：每一轮都只做一件事，每轮的输出被下一轮严格约束。幻觉无处可逃

这个模板可以直接加进你的第三节「Bug 定位」后面，作为 3.5 节。
