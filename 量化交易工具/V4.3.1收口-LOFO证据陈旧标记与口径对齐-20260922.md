## 背景：这条风险的形状

Summer 提的问题是「实验口径与线上不一致风险」。落到本批可核实的具体形态：

线上日报的「模型可信度」逐基金读 `data/model_registry/lofo_evidence.json` 的 `stability`。这份证据产出于 **2026-08-30**，当时：

1. 冻结样本机制（V4.3 P0-1）还不存在（09-20 才落地）⇒ 它消费的是**活缓存**，没有"哪份样本 + 哪套 K 线指纹"的可追溯绑定；
2. 之后发生了两件使历史可比性失效的事：**09-10 重冻结**样本、**09-18 C2 特征非时点不变**（est_chg 漂移 81.7% / 个股 K 线 sha 186/240 变）。

结论：线上仍在**静默引用一份口径已过期的证据**给可信度打分。数字看起来正常，但它回答的已经不是当前数据世界的问题——这就是实验与线上口径不一致的真实落点。

## ① 产出端：证据必须自带三件套（`backtest_lofo.py`）

`lofo_evidence.json` 现在写：

- `status`：`FRESH`（本次重跑产出）
- `valid_for`：`code_commit` / `samples_file` / `samples_sha256_lf` / `kfp_comparability`

四个语义 = 「本证据只对**这套代码 + 这份冻结样本 + 这套 K 线指纹**有效」。重冻结后未重跑即视为 STALE。

- **复用不新写**（八荣八耻第 4 条）：`code_commit` 直接用 `freeze_verify_tool.git_commit()`（D3 三件套的单一真源），不在 LOFO 侧另起一套 commit 探测。
- 顺带修一个显示缺陷：`str(None)[:12] or "unknown"` 会印字面量 `"None"` 而不是诚实的 `unknown` ⇒ 抽 `_code_commit_short()` 先判空再截。
- 报告首行区同步打印 `valid_for` 摘要，人类可读留档与机器可读 JSON 同源。

## ② 存量件：就地标 STALE，但绝不伪造可追溯性

`data/model_registry/lofo_evidence.json`（08-30 那份）就地加：

- `status: "STALE"` + `stale_marked_at` + `stale_reason`（写明 09-10 重冻结 + 09-18 特征非时点不变两条因）
- `valid_for` 四键**全部诚实置 null**，附 `note` 说明原因：生成于冻结机制之前、当时消费活缓存 ⇒ 无三件套可回填；`code_commit` 亦诚实 null —— 实测 `git rev-list -1 --before 2026-08-30T11:27:47+08:00 HEAD` 返回空（本仓库最早提交 **09-08**，历史根本不追溯 08-30）。
- `funds` 数值**一字未动**（`bak-20260922` 对比核实：funds 段逐字节相同），只是打上「仅作历史参照」的标签。

取舍：宁缺毋造。可追溯性缺失要写成缺失，不能为了字段整齐回填一个看起来合理的 commit。

## ③ 消费端：陈旧标记上链，但不动任何数值判定

- `core/forecast_engine.py`：`_load_fund_evidence()` 改返回 `(funds, status)`；文件缺失 / JSON 损坏 / 无 `status` 字段 ⇒ `"unknown"`（**不猜 FRESH**，诚实未判定）。`get_fund_evidence()` 增 `status` / `stale` 两个**纯增量键**。
- `core/report_generator.py`：可信度尾随 `⚠证据陈旧`。
- `backtest_t5_scorecard.py`：⑨ 行按 status 显示 `⚠️ STALE（09-26 须重跑） | lofo json (status=STALE)`。

**硬边界**：`confidence` 的四因子权重、映射函数、门禁判据**一字未改**。陈旧标记只做展示层。这条不是口头承诺——新增回归闸门测例 `test_staleness_does_not_move_confidence` 显式钉住「STALE / FRESH / unknown 三种状态下 confidence 必须逐位相等」。

理由：翻证据重跑是网络操作（挂 09-26 窗口 + 人工授权），线上不能因为一个展示标记就静默改变决策数值；要让陈旧**被人看见**，而不是替人做决定。

## ④ Path-WF 口径措辞对齐事实（`backtest_walk_forward.py`）

发现注释与实际调用不符：

- 注释/报告写：「每折 fold-train 重估**基金级** μ/σ」
- 实际代码：`pf.fit_path_params(f["train"], 5)` —— **不传 `fund_code`**

按 `path_forecast` v1.3 的签名语义，不传 `fund_code` 走的是**池口径**：μ = 去重全样本均值，σ = 逐基金 `(fund,date)` 去重后各取最近 20 交易日等权拼接。真正的「单基金口径」（μ/σ 都只用该基金）只在线上 `shadow_policy.py` / `forecast_path(fund_code=)` 使用。

⇒ 措辞改为「**池级 μ/σ（σ 窗口逐基金最近 20 交易日）**」。这正好是「实验 vs 线上口径不一致」的第二个实例：实验用池口径，线上用单基金口径，而文档把两者写成同一个词。

**只修文字，不改计算**：WF 全部数字与 T+5 verdict 未动。若改计算就是重跑实验 + 重出结论，那是另一批的事。

## ⑤ 离线冒烟抓到一个既存隐患（`_read_wf_evidence`）

为验证 ⑨ 行展示做了次零网络端到端冒烟（`backtest_t5_scorecard.py --force`），第一次跑就 exit=1：

```
ValueError: could not convert string to float: '84.2%'
```

根因：评分卡读 WF 留档 md 时**只按行前缀匹配**。而 `backtest_walk_forward_20260901.md` 现在含四张表，`| T+5 |` 和 `| 4 |` 两个前缀**跨表重复出现**：

| 表 | 前缀冲突行 | 列数 |
|---|---|---|
| 主判据（IC/CI） | `\| T+5 \| +0.080 \| [+0.020, +0.140] \| -0.035 \|` | 4 |
| 各周期 pooled IC | 同上形态 | 4 |
| CQR 覆盖率 | `\| T+5 \| 84.2% \| 53.1% \| …` | 7 |
| 逐折 WF | `\| 4 \| … \| -0.035 \| -0.012 \| -0.023 \|` | 6 |
| Path-WF 折表 | `\| 4 \| … \| +0.00104 \| 0.03212 \| …` | 11 |

⇒ 覆盖率行的 `84.2%` 被当 IC 直接崩；更坏的是 11 列 Path-WF 行的 **μ/σ 会被静默当成 wf_ic/frozen_ic**（不崩，出错误数字）。

修法：**按列数认表**（主判据 4 列 / 逐折 6 列），与 09-01 已有的 `_read_calib_evidence` 同风格守卫（那次修的是 calib 侧同类问题，WF 侧漏了）。

教训与 09-01 那条同源：**留档 md 一旦加新表，所有按文本前缀解析它的消费点都要重审**（改输入协议/文档结构必须审计所有消费调用点）。

## 顺带清掉的两处技术债

1. **行尾污染**：上批工具编辑把 3 个 LF 文件写成 CRLF ⇒ `git diff --stat` 显示 448/683 行整文件重写，真实改动只有 30/2 行。已按 HEAD 的 EOL 归一化，diff 收窄到 +209/−13。**本仓库 core.* 是 CRLF、部分脚本是 LF，混用是既存状态**，未擅自统一，只做「与 HEAD 对齐」。
2. **`.gitignore` 补 `*.bak-[0-9]*`**：就地改写前的单文件回滚副本属冗余（前一版本已在 git 历史），与既有 `output/backup_klines_*/` 同族约定。
