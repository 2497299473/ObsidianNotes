## 一、V4.1 四项（🔴 三项 + 隐私口子）

### ① Dataset Snapshot 与 Model Registry 解环（P0）

- **问题实证**：`data_fingerprint.py` 全量 `rglob("data/")` 收录 `data/model_registry/registry.json`，而
  `model_registry.capture_provenance()` 又把清单 sha256 写回 registry 每个 entry ⇒
  **manifest ─hash→ registry ─内嵌→ manifest 的 hash** 自指环。且已实际不一致
  （清单记 `2390f0f1…`、registry 实际 `54619525…`）——任何一次重生成都会让「清单描述 registry」立即过时。
- **修法**：清单 scope 收窄为 `dataset_inputs`（排除 `model_registry/` 与 `models/`），依赖变为单向
  **Dataset Snapshot → Model Provenance → 模型权重 / git commit**；`_assert_acyclic()` 写盘前硬报错
  （排除集被改回时**宁可崩**，不产出自指清单）；`snapshot_id` 改**内容寻址**（同数据必同 ID，不随 mtime/生成时刻漂移）；
  键名统一正斜杠（旧版 Windows 反斜杠使同一数据在 Windows/WSL 清单键不可比）。
- **新增审计 P0-5**：每次复核**已落盘**清单（生成时校验管不住历史文件与手工回填）。
- 旧版全量清单自动归档 → shadow 记录内嵌的 `afd156ab12a3bff1` 仍可解析，**回溯链未断**。
- 保留 `data/promotion_prereg.json` 在清单内（Summer 拍板）：它是授权凭据，且不构成环。

### ② 生产资格只看 active model（P0）

- **问题**：`derive_states` 与 P1-3 旧实现把「registry 里全部 promotion=blocked 的模型」当否决条件 ⇒
  **历史失败记录会永久阻止未来模型晋升**（forecast_v4 即便 approved，只要 v2 还在 registry 就永远 BLOCKED）。
- **修法**：纯函数 `resolve_model_promotion(active_model, models, model_ready)`，`derive_states` 与 P1-3 共用；
  active 由 `config.forecast.active_model` 显式声明（当前 `forecast_v3.pkl`，与 `MODEL_VERSION=3` 一致，
  **不靠字符串推断**、审计侧保持 stdlib-only 不 import `forecast_engine`）；fail-closed（未声明/未登记/promotion 非 approved ⇒ BLOCKED）。
  旧 `inputs.blocked_models`（全量）语义原样保留，新增 `active_model` / `active_promotion` / `promotion_basis` / `historical_blocked_models` 表达拆分。
- 连带修 **P1-2**（评审 ⑥）：旧 `if not rf: continue` 使「根本没写 `report_file`」与「绑定正确」同样 PASS；
  现 active 缺 `report_file`/`report_sha256` ⇒ FAIL，历史模型缺绑定 ⇒ WARN。

### ③ `cache:fallback` 进入 Runtime Degraded 状态机（P0）

- **漏网路径**：EastMoney 失败 → Sina 失败 → 退旧缓存 → `load_fund()` **正常返回不抛异常**
  ⇒ run.py 只 `try/except` 抓不到 ⇒ 不记 degraded ⇒ exit=0 ⇒ publish_gate 看不见污染。
  而该事实旧版只被 `report_generator` 一处消费（**读者看得见、状态机看不见**）。
- **修法**：`data_loader` 新增 `is_nav_fallback()` + `NAV_FALLBACK_PREFIX` 作**单一事实源**；
  run.py 新增 `nav_fallback_funds()` → `fund_data_fallback:<codes>` 进 `degraded` ⇒ **exit=2** →
  写 `run_manifest.data.fallback` → `GATE_FUND_KEYED` 注册 `("data","fallback")` ⇒ 门禁**逐基金归因**拦截发布；
  报告层改用同一谓词，撤掉本地 `startswith`，杜绝两处判定漂移。

### ④ 运行清单掩码（隐私口子，V4.1 收尾时自查发现）

- **问题**：`run.py` 注释写着「清单不得写代码：run_manifest 会被跟踪，写进去等于泄露持仓」，
  但同一文件的 `data.failed` / `data.fallback` 一直是**真实 6 位代码**。现有 5 份清单没泄露，
  只是因为**从没真降级过**——契约与产物自相矛盾。
- **修法**：落盘前 `mask_manifest_funds()` 把全部逐基金字段（`GATE_FUND_KEYED` 五处 + `data.status_unknown`）
  与 `degraded_reasons` 的代码段换成**位置别名** `F1…Fn`，基准 = `config.fund_pool` **升序位**
  （故同一只基金在所有字段、所有清单里都是同一个 F 号），文件内留 `fund_refs.pool_sha256_8` 供反查；
  门禁侧 `resolve_fund_refs()` 按同一张表反查 ⇒ **逐基金归因能力不变**；反查不出来的（基准表缺失/指纹不符/F 号越界）
  **不推断**，走「不在论域」的 fail-closed 分支。掩码后仍残留 6 位码 ⇒ **拒绝落盘**（转 DEGRADED，exit=2）。
- 审计侧 `P1-9` 的 `checks[]` detail 同步掩码（该段会整段写进 `audit_current.json`）。
- ⚠️ **两处刻意保留的偏离**：① 清单用「池升序位」而非 `audit_current.json` 的「列表内位置」别名——
  后者在多字段场景下同一 F 号会指向不同基金，门禁无法反查；② 旧清单（09-18 及更早）**不回改**（在档证据）。

## 二、V4.2 四项（🟠）

| 项 | 旧行为（问题） | 现行为 |
|---|---|---|
| **P1-7 审当前运行** | 只要 `output/run_manifest/` 存在**任意** JSON 就 PASS，且取 `files[-1]` ⇒「今天没跑、昨天留了一份 SUCCESS」照样过关 | 四问核验最新清单：命名/内容自洽、必备字段齐备、`status` ∈ 三态词表、**新鲜度**（`last_expected_run_date()`：交易日过 11:30 算今天，否则回溯上一交易日）、逐基金字段不得残留 6 位码 |
| **audit_current 时效** | README 说「所有人只看 `audit_current.json`」，但该文件只在人手动跑审计时才更新，实况曾停在上一交易日 | payload 增 `evidence_as_of` / `evidence_expected_as_of` / `evidence_stale` / `evidence_latest_run`；`run.py` **post 收尾**调 `refresh_current()` 自动刷新 current + 追加 history |
| **`_lsjz` 动作门** | 取数失败时 `load_fund()` 照常返回、状态落「未知」，这层信息**不进任何状态机** ⇒ 动作层一打开就可能输出**执行不了**的加/减仓 | `data_loader.is_fund_status_known()` 单一事实源 + `decision_engine._check_gates` 硬门禁（状态未知 ⇒ invalid ⇒ 动作恒 HOLD）；未知清单记进 `data.status_unknown`（掩码；**不进发布门禁**——它只锁动作层） |
| **Signal Journal 幂等** | 无条件追加 ⇒ 修 bug 后重跑会与旧行并存，读者无从判断哪行是当日定论 | 同一交易日只留一行，重跑**就地更新**当日行（last-run-wins，与门禁同口径）；只做**单行替换 + 原子写**，其余行逐字节不动 |

### 关键决策与理由

1. **新鲜度判定用「最近应产出交易日」而非「今天」**：直接比今天会在周一早上/假期误报；
   交易日 + 11:30 时点回溯的写法让「周一 09:00 停在周五」判干净、「周一 15:00 停在周五」判过期。
2. **指针刷新放在清单落盘之后**：指针要描述的是「含本次运行在内」的证据状态，放前面会滞后一轮
   （post 轮的发布门禁证据就白写了）。
3. **刷新失败不降级本次运行**：指针是**派生视图**，其时效由 `evidence_stale` 自证，结果只进本地日志
   （`output/logs/`，gitignored）——派生视图不进证据链。
4. **状态未知不进发布门禁**：它只影响「动作能不能执行」，不影响报告其余栏可信度；
   进 degraded 会让整批不推，属过度拦截。故它只锁动作层 + 记清单（掩码）。
5. **掩码基准 = 池升序位**（见 ① ④ 的偏离说明），指纹随清单落盘以便事后复核。
