### Q3. 对 PyQt 底层的了解程度如何？

**应对策略**：承认以应用为主，但底层有一定了解——信号槽的 MOC 机制、事件循环、线程亲和性。

### Q4. 在 PyQt 中，你是如何理解"信号与槽（Signal & Slot）"机制的？

**核心回答**：

信号与槽是 Qt 的核心通信机制，本质是**观察者模式的类型安全实现**：

```
信号（Signal）：事件源发出的通知，声明"我发生了什么"
槽（Slot）：响应函数，声明"当某事发生，我做什么"
连接（Connect）：把信号和槽绑定在一起
```

**关键特性**：
- **松耦合**：发送者不知道谁在监听，接收者不知道谁在发——两端代码完全独立
- **多对多**：一个信号可以连多个槽，多个信号可以连同一个槽
- **类型安全**：信号参数类型与槽参数类型在编译/运行时检查匹配
- **跨线程安全**：自动选择 QueuedConnection，保证槽在接收者线程执行

### Q5. 当点击控件触发事件时，发出的这种通知一般叫什么？

**回答**：**信号（Signal）**。

Qt 中几乎所有用户交互都会发出信号：`QPushButton.clicked`、`QLineEdit.textChanged`、`QComboBox.currentIndexChanged` 等。

### Q6. 绑定的执行函数接收到信号后会执行，这种机制一般叫什么？

**回答**：**槽（Slot）** 或 **槽函数**。

在 PyQt5 中，槽就是一个普通的 Python 函数/方法，用 `@pyqtSlot()` 装饰器标记（可选但推荐，提升类型安全）。

### Q7. 槽函数与普通的回调函数（Callback）有什么区别？

这是经典对比问题：

| 维度 | 回调函数 | 信号槽 |
|------|---------|--------|
| **耦合度** | 紧耦合——调用方必须持有被调用方的引用 | 松耦合——双方只通过 `connect()` 建立关系 |
| **类型安全** | 无编译时检查，运行时炸 | 信号参数类型与槽参数类型匹配检查 |
| **多对多** | 一对一（或手动管理列表） | 原生支持多对多 |
| **跨线程** | 需要手动加锁 / 队列 | 自动 QueuedConnection，安全传递 |
| **生命周期** | 回调对象被销毁 → 悬空指针崩溃 | Qt 自动管理——发送者或接收者销毁时自动断开 |
| **连接方式** | 硬编码 | 可在运行时动态 connect/disconnect |

> 面试话术：信号槽 = 回调的「高端升级版」——解决了回调在复杂 GUI 应用中的耦合和线程安全问题。

---

### Q8. 控件在触发信号回调时，为什么用槽函数而不用普通的 Callback？槽函数有哪些写法？

**为什么不用普通 Callback**：
1. **线程安全**——GUI 控件的事件必须回到主线程处理，回调做不到自动调度
2. **生命周期管理**——控件销毁时，回调可能变成悬空指针；信号槽自动断开
3. **一对多通知**——一个按钮点击要同时更新多个控件，回调需要手动维护监听列表

**槽函数的写法**：

```python
# 写法一：普通方法（最常用）
class MainWindow(QMainWindow):
    def on_button_clicked(self):
        print("clicked")

btn.clicked.connect(self.on_button_clicked)

# 写法二：lambda（简单逻辑）
btn.clicked.connect(lambda: self.status_label.setText("已点击"))

# 写法三：@pyqtSlot 装饰器（推荐，类型安全）
@pyqtSlot(bool)
def on_checkbox_toggled(self, checked: bool):
    print(f"Checkbox: {checked}")

# 写法四：信号连信号（高级）
line_edit.textChanged.connect(label.setText)

# 写法五：partial 绑定参数
from functools import partial
btn.clicked.connect(partial(self.on_action, arg1=42))
```

### Q9. 实际编写上位机软件时，有没有详细了解过 PyQt 的信号与槽底层机制？

### Q10. PyQt 里面有线程管理器（QThread），它跟普通的 Thread 有什么区别？

| 维度 | `threading.Thread` | `QThread` |
|------|-------------------|-----------|
| **本质** | Python 标准库，封装 OS 线程 | Qt C++ 类，也是 OS 线程 |
| **事件循环** | 无（裸线程，没有消息循环） | 有——`run()` 默认启动 `exec()` 事件循环 |
| **信号槽** | 不支持（需要手动 queue.Queue） | 原生支持——emit → 自动入队 → 接收线程执行 |
| **生命周期管理** | `start()` / `join()`，简单粗暴 | `start()` / `quit()` / `wait()` / `finished` 信号，状态机更完善 |
| **线程安全 GUI** | 不能操作 GUI（任何线程操作 GUI 崩溃） | 信号槽自动调度回主线程，安全更新 UI |
| **适用场景** | 通用后台任务 | GUI 应用的标准选择 |

> 面试话术：QThread 是为 GUI 定制的线程方案——自带事件循环 + 信号槽自动跨线程调度，解决了 threading.Thread 做 GUI 开发时最常见的两个问题：UI 更新安全和线程间通信。

## 三、并发编程

### Q23. Python 里面的并发编程（多进程 Multiprocessing、多线程 Threading）你是怎么理解的？

**核心区分**：

```
多线程（Threading）：
  一个进程内多个线程，共享内存空间
  受 GIL 限制，同一时刻只有一个线程执行 Python 字节码
  适合 IO 密集型（网络请求、文件读写、等待）

多进程（Multiprocessing）：
  多个独立进程，各自有独立内存空间和 GIL
  真正并行执行，不受 GIL 限制
  适合 CPU 密集型（数值计算、模型训练）
  代价：进程创建开销大、进程间通信需要序列化（pickle）
```

> 面试话术：Python 的 GIL 是理解多线程 vs 多进程的关键——GIL 让多线程无法真正并行计算，但对于 IO 密集型任务（等待网络/磁盘），线程在等待时释放 GIL，多线程依然有效。需要真正并行计算时，用 multiprocessing。

---

### Q24. 在设计软件时，什么时候开线程，什么时候开进程？

| 场景 | 选择 | 理由 |
|------|------|------|
| **网络请求/文件读写** | 线程 | IO 等待时释放 GIL，线程轻量、数据共享方便 |
| **UI 响应（PyQt）** | 线程（QThread） | 不能阻塞主线程，信号槽天然支持跨线程通信 |
| **数据库操作** | 线程 | 连接池管理、异步写入 |
| **CPU 密集型计算** | 进程 | 绕过 GIL，多核并行 |
| **ML 模型推理（CPU）** | 进程 | 模型推理纯 CPU 计算 |
| **ML 模型推理（GPU）** | 线程即可 | 计算在 GPU 不在 CPU，Python 只是调度 |
| **需要隔离风险的任务** | 进程 | 子进程崩溃不影响主进程 |

---

### Q25. 什么叫 CPU 密集型任务？什么叫 IO 密集型任务？

**CPU 密集型**：瓶颈在 CPU 计算速度——图像处理、矩阵运算、加密解密、科学计算。需要更多 CPU 核心。

**IO 密集型**：瓶颈在等待外部设备——网络请求、数据库查询、文件读写、用户输入。CPU 大部分时间闲置等待。

| | CPU 密集型 | IO 密集型 |
|------|-----------|----------|
| **特征** | CPU 使用率接近 100% | CPU 使用率低，大量时间 wait |
| **Python 方案** | `multiprocessing` | `threading` / `asyncio` |
| **示例** | 仿真计算、模型推理、视频编码 | Web 爬虫、Web 服务器、文件同步 |

### Q26. 了解守护线程和非守护线程吗？为什么要设计守护线程？

**区别**：

| | 守护线程（Daemon） | 非守护线程（Non-daemon） |
|------|------|------|
| **主线程退出时** | **被强制终止**（不等待） | 主线程等待其完成 |
| **用途** | 后台服务（日志、心跳、GC） | 需要确保完成的任务 |
| **创建** | `t.daemon = True` 或 `t.setDaemon(True)` | 默认 |

```python
import threading
import time

def background_task():
    while True:
        print("守护线程工作中...")
        time.sleep(1)

# 守护线程：主线程退出时自动结束
t = threading.Thread(target=background_task, daemon=True)
t.start()
time.sleep(3)
print("主线程退出，守护线程自动终止")
```

**为什么设计守护线程？**
1. **避免程序无法退出**——如果有个死循环的后台线程不是 daemon，主程序永远退不出
2. **生命周期管理**——后台服务性质的线程（日志刷新、定时上报）不需要阻止程序退出
3. **类比**：用户线程 = 餐厅厨师（必须等到菜做完），守护线程 = 背景音乐（餐厅关门就自动停）

## 五、业务架构与系统设计

### Q34. 你觉得这个视觉检测软件的复杂度，跟你之前开发的软件比，哪个更复杂？

### Q36. （场景题）如果同时有 100 个用户各发送一个推理请求（单次耗时 200ms），单服务如何处理才能保证数据不丢失、请求不丢失？

**核心思路**：请求队列 + 并发处理 + 背压控制。

```
100 个用户
    │
    ▼
┌─────────────────────────────────┐
│  请求入口（Nginx / Gunicorn）      │  ← 高并发接入
│  • 接收 100 个请求               │
│  • 转发到内部队列                 │
└────────────┬────────────────────┘
             │
             ▼
┌─────────────────────────────────┐
│  消息队列（Redis List / RabbitMQ） │  ← 缓冲层，削峰填谷
│  • 持久化到磁盘（不会丢）          │
│  • 消费者按能力消费                │
└────────────┬────────────────────┘
             │
             ▼
┌─────────────────────────────────┐
│  Worker Pool（多进程/多GPU）      │  ← 真正的推理执行
│  • 4 个 GPU → 4 个 Worker 进程   │
│  • 每个 GPU 批量推理（batching）   │
│  • 200ms × 100 / 4 = 5 秒完成    │
└────────────┬────────────────────┘
             │
             ▼
┌─────────────────────────────────┐
│  结果回调（WebSocket / 轮询）      │  ← 异步通知用户
│  • 推理完成 → 通知用户取结果       │
└─────────────────────────────────┘
```

**关键设计点**：

| 机制 | 作用 |
|------|------|
| **消息队列** | 削峰——100 个请求不会瞬间全打到推理服务，排队等消费 |
| **队列持久化** | 不丢数据——即使推理服务挂掉，重启后从队列继续消费 |
| **Worker Pool** | 并行处理——多个 Worker 分摊负载 |
| **超时 + 重试** | 单个请求超时 5s 未完成则标记失败，放回队列重试 |
| **背压** | 队列太长时（>1000），返回 HTTP 503 + Retry-After，防止系统被压垮 |

> 面试话术：核心是"先落地，再消费"——请求进来先写队列（已持久化），然后 Worker 慢慢处理。请求进入队列的那一瞬间，数据就不会丢了。

### Q37. 刚才提到的 Nginx 工具中，有哪些能实现"只用一个端口对外暴露多个内部应用"的路由转发功能？

**回答**：`proxy_pass`（反向代理）+ `location` 匹配。

```nginx
server {
    listen 80;  # 只对外暴露 80 端口

    # /api/ 路由到后端服务
    location /api/ {
        proxy_pass http://127.0.0.1:8000;
    }

    # /admin/ 路由到管理后台
    location /admin/ {
        proxy_pass http://127.0.0.1:3000;
    }

    # /ws/ 路由到 WebSocket 服务
    location /ws/ {
        proxy_pass http://127.0.0.1:9000;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }

    # 其他走静态文件
    location / {
        root /var/www/html;
    }
}
```

**关键 Nginx 指令**：
- `proxy_pass`：反向代理，转发到内部服务
- `location`：按 URL 路径匹配分发
- `upstream`：定义后端服务器组，支持负载均衡（轮询/加权/IP Hash）
- `stream`：四层代理（TCP/UDP），如 `stream { server { listen 3306; proxy_pass db:3306; } }`

### Q38. 对防火墙的概念了解吗？

**回答**：

防火墙是网络安全的第一道防线，分为：
- **网络层防火墙**——基于 IP/端口过滤（如 Linux `iptables`）
- **应用层防火墙**——基于应用协议内容过滤（如 WAF，Web Application Firewall）

**常见操作**：
```bash
# Ubuntu ufw
sudo ufw enable                    # 开启防火墙
sudo ufw allow 22/tcp              # 允许 SSH
sudo ufw allow from 192.168.1.0/24 # 允许内网段
sudo ufw deny 3306                 # 禁止外部访问数据库

# 云服务器安全组
# 白名单模式：默认拒绝所有入口，仅开放必要端口（80/443/22）
```

> 面试话术：对于工业视觉软件来说，防火墙主要用于保护推理服务和数据库——只允许上位机 IP 访问，拒绝其他一切连接。

## 六、AI 辅助编程（Cursor）

### Q39. 在 10 万行代码中，如果有个 Bug 可能跟某个变量相关，你怎么用 Cursor 快速定位到这个变量？

**回答**：

1. **全局符号搜索**（`Ctrl+T` / `Cmd+T`）→ 输入变量名 → 列出所有定义和引用位置
2. **项目级搜索**（`Ctrl+Shift+F`）→ 输入变量名 → 按文件分组列出所有出现位置
3. **代码跳转**（右键 → Go to References）→ 从定义跳到所有引用
4. **AI Chat** → 选中可疑代码段 → 描述 bug 现象 → 让 Cursor 分析变量生命周期和数据流
5. **@Codebase 搜索** → `@Codebase 这个变量在哪里被修改过？` → AI 跨文件追踪赋值位置
6. **Git 历史** → `git log -p -S "variable_name"` → 找到变量首次引入和修改记录

> 关键思路：先用搜索定位变量所有出现位置 → 用 AI 分析数据流 → 用 Git 追溯变更历史 → 用 debugger 运行时验证。
