## 核心启发

> 凡是重复性的工作，都可以用 Skills 替代。

这不是一个技术判断，是一个**识别方法**。你不需要分析"这个场景适合参考型还是任务型"——你只需要问：**这件事我做过第二次吗？**

- 做过第二次 → 有模式可提取 → 值得封装
- 只做过一次 → 先做，等第二次出现再说

## 从想法到落地的三步

### 第一步：识别候选

不需要系统分析，三个信号任意一个触发就够：

| 信号 | 例子 |
|------|------|
| 你做过第二次 | "又在手动写 CRUD 了" |
| 你说过同一句话两次 | "帮我看看这个死锁日志" |
| 你复制过同一段提示词两次 | 每次 code review 都贴同一段 checklist |

### 第二步：用 skill-creator 快速生成骨架

Claude Code 内置的 `skill-creator` 会引导你完成：

```
/skill-creator
```

它会问你：
1. 这个 Skill 叫什么？
2. 它做什么？（自动生成 description 草稿）
3. 放在哪个层级？（project / personal / enterprise）
4. 需要哪些工具权限？

生成的是一个**可工作的最小骨架**——SKILL.md 有了、目录建好了、description 是草稿状态。你不用从空白文件开始。

### 第三步：用着改着

最重要的原则：**先让 Skill 能用，再让它好用。**

```
v0: skill-creator 生成的骨架 → 能用就行
v1: 用了 3 次后，把 description 里 AI 选错的点改掉
v2: 用了 10 次后，把重复出现的知识挪进 reference/
v3: 发现两个 Skill 的 description 冲突 → 加路由逻辑
```

不要试图一开始就写出完美的 SKILL.md。第 9 讲的所有规范（description 公式、reference/ 结构）都是**v3 阶段的事**，不是 v0。

### 附：description 该写中文还是英文

**结论：中英混杂最好，纯英文也可以，纯中文也行。写法比语言重要。**

底层原因：LLM 做语义匹配，不是关键词匹配。"帮我看看代码"和 "Review code for quality" 在 embedding 空间里是近的，不需要同一种语言。

| 写法 | 中文输入触发 | 适用场景 |
|------|------------|---------|
| 中英混杂 | ✅ 最稳 | **推荐**——技术术语保留英文，场景描述用中文，覆盖用户多种表达 |
| 全英文 | ✅ 能触发 | 分享给跨语言团队、公共仓库 |
| 全中文 | ✅ 能触发 | 领域术语本身就是中文的 |

**中英混杂示例**（推荐）：

```yaml
description: 审查后端代码的质量和安全性。检查 bug、性能问题、规范遵守情况。当用户要求 code review、审查代码、检查 PR、看看代码有没有问题时使用。
```

覆盖了同一语义的三种表达（review / 审查 / 检查），匹配面比单一语言更宽。

**真正影响触发率的不是语言，是覆盖面**：

```yaml
# ❌ 只覆盖一种表达
description: 进行代码审查。

# ✅ 覆盖用户可能说的所有变体
description: 审查代码质量和安全性。检查 bug、性能、规范遵守。当用户要求 code review、审查代码、检查 PR、看看代码有没有问题时使用。
```

多写几种"用户可能怎么说这件事"的措辞，比纠结中英文有效得多。

## 和现有构想库的对应

你现在 [[技能构想/参考型 Skill 候选清单|有 6 个候选]]：

| 候选 Skill | 重复信号 | 用 skill-creator 可以 |
|-----------|---------|---------------------|
| 死锁日志解读 | 每次死锁排查都要重新解释日志格式 | 3 分钟生成骨架 |
| 后端代码评审 | 每次 review 说同样的 checklist | 直接生成 + 补 reference/ |
| 任务拆分指导 | 每个 feature 都要解释项目模块结构 | 生成后重点补 reference/ |
| CRUD 代码生成 | 每次新资源都写一样模式的代码 | 生成 + 补代码模板 |
| 特定开发场景 | 消息队列消费者写了 N 次 | 生成 + 补标准模板 |

## 备注

- `skill-creator` 本身也是一个 Skill——这恰好印证了"Skills = 可操作知识"：连"如何创建 Skill"这件事也被封装成了 Skill
- 判断一个 Skill 是否该存在的终极标准不是设计，是**频率**：一个月触发不到 3 次的 Skill，要么 description 写坏了，要么它不该是 Skill，该放 CLAUDE.md 或者直接删掉

### CLAUDE.md vs Skill：到底放哪，要不要加引用

课程里说"犹豫就放 Skill，并在 CLAUDE.md 加一行引用"。但 Skill 目录会被自动扫描，为什么还要引用？

**自动扫描解决"发现"，引用解决"重视"。**

- 自动扫描：Claude 读了所有 description，语义匹配到了就加载 → **被动**
- CLAUDE.md 引用：告诉 Claude"这件事很重要，不确定的时候优先考虑" → **主动**

**不是每个 Skill 都要加引用。**

| 加引用 | 不加引用 |
|--------|---------|
| 几乎每次对话都可能用到的核心规范 | 只在特定场景触发，平时用不到 |
| 用户不会主动说触发词，但 Claude 应该知道 | 触发场景明确，用户自然会说出匹配词 |
| 定义了"在这个项目里怎么做事"的基础约定 | 某个具体任务的执行流程 |

示例：

```markdown
# CLAUDE.md

## 核心规范
- API 设计遵循 api-conventions Skill
- 数据库操作遵循 sql-index-tuning Skill

## 可用能力
其他 Skill（死锁分析、任务拆分、CRUD 生成等）按需自动加载。
```

前两行是每次都可能用到的基础规范——加了。后面的"可用能力"一句话带过——不加。

**实际上，多数情况下不加也没事。** 如果你的 description 写得够好，自动扫描基本够用。课程那句话的重点在前半句——**别放 CLAUDE.md，放 Skill**。"加一行引用"是可选的。
