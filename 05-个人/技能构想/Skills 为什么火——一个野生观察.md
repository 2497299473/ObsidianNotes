## 官方叙事 vs 实际传播

Skills 的官方叙事：语义触发、渐进式加载、企业本体论、认知层调度。

Skills 实际传播的原因：**可分享、好理解、好生成、低门槛。**

两者不矛盾，但重心完全不同。官方强调的是"为什么设计成这样"，用户在意的是"我能用它干什么、多快能干成"。

## 最大特色 = 最大弊端

语义触发是 Skills 最具野心的设计——让模型自己决定什么时候用什么技能。

但现状是：
- CC 全家桶环境：基本可用（仍不稳定）
- 非 CC 环境：约等于一个 `/command`

对于无法使用 CC 全家桶的用户，Skill 的技术先进性感知为零——它就是另一个 YAML 配置块。

## 那为什么还是火了

不是因为语义触发。是因为 **Skill 成了一个标准化的"能力分享格式"**。

```
以前的路径：
  看到工具 → 学文档 → 写代码 → 调试 → 集成 → 维护

现在的路径：
  看到工具 → 让 CC 生成 Skill → 只说诉求就能用
```

关键变化不是 AI 更强了，是**学习成本从人转移到了 AI**。人不学工具，人描述需求。Skill 是这个转移的载体。

### 三个传播驱动力

| 驱动力 | 以前 | 现在（Skills 时代） |
|--------|------|-------------------|
| 分享 | 分享一个 prompt 文本块 | 分享一个有目录结构、能直接被 CC 理解的能力包 |
| 学习 | 人看文档学工具 | 人让 AI 把工具封装成 Skill，人只说诉求 |
| 生成 | 手动写 prompt，反复调试 | `/skill-creator` 引导生成，有标准骨架 |

这三个加起来，门槛低到了"有想法就行"。

## 无心插柳：许愿生成 → 标准化裂变

"小工具许愿生成"（对着 AI 说"帮我写一个 xxx 的脚本"）早就有了，而且很稳定。但它一直停留在个人级的一次性交互——你许愿、AI 生成、你用，结束了。

Skills 做了一件事：**给"许愿生成"一个标准化的容器。**

有了标准容器之后：
- 你可以把生成的 Skill **存下来**——不是一次性脚本，是可复用的能力单元
- 你可以**分享**给别人——别人拿到后不需要理解你的 prompt，直接用
- 别人可以**在上面改**——因为有标准结构（SKILL.md + reference/ + templates/），知道往哪改
- 生态开始**裂变**——一个人封装，一百个人用，每个人再定制

标准化本身比技术先进性更有传播力——这是 HTTP、Markdown、JSON 反复验证过的规律。

## 一句话总结

> Skills 火的不是它的技术机制，是它让"能力封装"从个人手艺变成了可分享、可继承、可定制的标准格式。
