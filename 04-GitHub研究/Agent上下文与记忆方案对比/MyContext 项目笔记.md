## 一句话定位

**一个本地优先运行的个人工作上下文层，把散落在 IM（钉钉/飞书）、文档、会议记录里的多源工作数据，持续加工成一份私有的"工作档案"，供大模型、本地 Agent 与授权 AI 应用检索使用——重点解决高熵业务数据的治理（时序变化、矛盾信息），而不是简单堆料。**

---

## 🎯 解决的核心痛点

> 行业叙事：限制 Agent 落地的瓶颈正从"模型推理能力"转向"**企业上下文供给**"。（MIT NANDA 报告：约 95% 企业级生成式 AI 试点**没有可衡量的收益**）

| 痛点 | 说明 |
|------|------|
| **上下文缺失** | Agent 个人效率已很好，但真实工作场景里缺"岗位职责、协作关系、历史结论"这种关键上下文 |
| **多源数据异构** | 同一个事实散落在 IM、文档、会议里，格式不一、互相打架 |
| **时序变化** | 信息随时间是会变的，"下周一上线"后面可能改成"月底" |
| **矛盾信息** | 简单"取最新 / 取最高置信度"都会**丢信息**，传统方案处理不了真实业务语料 |
| **可信与可回溯** | Agent 给答案得"挂得住证据"，不能编 |

## 🏗️ 核心机制

### 整体定位：上下文链路的最上游

```
  MyContext（采 / 提炼 / 裁决）           后续可叠加
  ┌─────────────────────────────┐
  │ 数据源（IM/文档/会议）          │     OpenViking / TencentDB（存）
  │   → 标准化处理 + 增量同步       │   → Headroom（省 / 压缩）
  │   → 提炼工作档案               │   → LLM
  │     · 职责范围 · 协作关系      │
  │     · 行为习惯 · 工作结论      │
  └─────────────────────────────┘
    数据与索引存在用户本机（SQLite），默认不上云
```

### 工作流程

| 步骤 | 说明 |
|------|------|
| **下载部署** | 本地优先方式运行桌面应用 |
| **授权数据源** | 连接并授权钉钉、飞书等 IM 及文档、会议数据 |
| **导入数据** | 自动标准化处理 + **增量同步** |
| **生成档案** | 自动沉淀职责范围、协作关系、行为习惯、讨论结论，并持续更新 |
| **构建 Agent** | 基于档案生成专属 Agent：总结知识 / 查询工作信息 / 以本人语气辅助回复 |
| **人工确认关键环节** | 矛盾信息、发送消息等有后果操作 → 用户确认后执行 |

### 核心差异化算法：矛盾/时序数据治理

> [!important] 独门机制（其他三家都没有）
> - **不简单采用"最新信息"或"最高置信度"**作为最终结果
> - 用**语义分析**判断冲突内容该**合并**还是**覆盖**
> - 系统**无法自行判断**时 → **交由用户确认**
> - **用户确认后的结论，模型永不自动覆盖**（人工锚定，给档案上了"人工锁"）

### 搜索机制（可追溯、不编造）

- 自然语言询问自己的工作历史
- 结合**本地全文检索 + 语义召回 + 图谱查询**
- Agent 基于**可追溯来源**组织答案
- Agent 运行环境**不可用时明确降级为本地相关结果**，而不是悄悄生成没有依据的答案

### 三条核心设计原则

| 原则 | 含义 |
|------|------|
| **本地默认** | 个人工作数据与索引存在用户本机（SQLite），默认不上云 |
| **证据先于答案** | 每条结论保留来源引用可回溯；搜索答案必须挂得住原始证据 |
| **AI 是消费方不是所有者** | 模型/Agent 通过受控接口使用上下文，数据与权限归用户所有；发送、删除等不可逆或外部可见操作需用户**显式确认** |

## ✅ 优点 / ⚠️ 局限

### 优点
- **卡在上下文链最上游**：别人都是"没数据先存"，它是"先有真实工作数据"（钉钉 2000 万企业 / 近 8 亿用户做入口）
- **矛盾/时序数据治理是独门武器**：语义裁决 + 人工锚定，避免传统方案丢信息
- **全程可回溯抗幻觉**：每条信息带来源+时间+内容，降级不编造
- **本地优先保隐私**：数据本机 SQLite，AI 只是使用方；契合企业数据安全要求
- **人机安全闸**：发送等有后果操作必须用户授权，对齐"人机协同"而非纯工具
- **全栈闭环**：阿里是"应用驱动 + 全栈闭环"路线（区别于海外"数据云/软件工程化框架"）

### 局限
- **仍处早期**：上线仅一周、开发者预览、官方警告破坏性改动，未经历社区大规模回测，可信度远不如被广泛验证的 Headroom(64.6k★)/OpenViking(27.9k★)
- **协议不是传统开源**：Elastic License 2.0 禁止作为托管/管理服务提供给第三方，商用前需读清条款
- **绑定钉钉/飞书生态**：个人版目前只接 IM/文档/会议，日历/任务/邮件还在规划
- **强依赖阿里云/千问 embedding 与模型链路**：跨生态通配性未知
- **SQLite 迁移部分不可逆**：官方不建议把不可再生成的数据只存于此
- **不能替代其他方案**：它只出"档案素材"，喂模型前该压缩还得压缩（Headroom），多人沉淀还是要治理层（TencentDB）

## 🔀 碰撞分析：MyContext × 已跟踪的记忆类项目（2026-08-23）

> [!important] 结论先放前面
> Obsidian 及记忆里已跟踪项目与 MyContext **均不构成直接竞争**；最容易"撞脸"的 **Mnemosyne** 恰是最互补的一个——**MyContext 是先判断对错再入库（有主裁决），Mnemosyne 是只管存只管查（无主记忆）**。两者是上下游分工，而非同类竞品。

### MyContext × Mnemosyne（最容易被误认成竞品）

Summer 已跟踪列表里，和 MyContext 长在同一棵"表面同款"树上的是 **Mnemosyne**，而非 Headroom/OpenViking/TencentDB：

| 维度 | MyContext | Mnemosyne |
|------|-----------|-----------|
| 存储 | 本地 **SQLite** | 本地 **SQLite**（单文件） |
| 本地优先 | ✅ | ✅ 零云 |
| 分层 | 档案层级提炼 | BEAM 三层（工作/情景/时序知识图谱） |
| 混合检索 | 全文检索+语义召回+图谱查询 | sqlite-vec+FTS5 混合评分 |
| 抗幻觉 | 挂来源引用，降级不编造 | LongMemEval 98.9%（2026-04） |
| 诞生 | 阿里·千问办公 | 海外社区，Hermes-first |

**表面像同类，实际完全不是一路：**
- **Mnemosyne = 记忆引擎**：解决"已有内容怎么存/召回/评分"，入口是消息/代码/任意文本，产出是记忆检索结果，纯开发者框架（Hermes 协议 + MCP）。
- **MyContext = 上下文供给 + 裁决**：解决"原始工作语料怎么变成可信档案"，入口是钉钉/飞书 IM、文档、会议（**人的工作数据，没法当普通文本直接灌**），产出是"工作档案"，并自带 **Mnemosyne 完全没有的矛盾语义裁决**。

**真正的碰撞点只有一处，且是分工不是竞争：**
MyContext 负责"采 + 裁"（把群聊/文档/会议翻译成可信档案），Mnemosyne 负责"存 + 取"（把档案当长期记忆检索）。理论上可串成：**MyContext 出档案 → 喂给 Mnemosyne 当长期记忆 → Mnemosyne 检索给 Agent**——和 MyContext × OpenViking 的"采→存"关系同构，只是 Mnemosyne 更轻（单文件零云）。

**决定性差异（判断会不会打架的关键）：**
- Mnemosyne 是**无主记忆**——不管数据对不对、冲突怎么解，只管"存得好不好、查得准不准"。
- MyContext 是**有主裁决**——核心价值恰在"这条可信吗？和旧档案冲突吗？要不要用户拍板？"（用户确认后模型不可再覆盖）。这一层 Mnemosyne/OpenViking/TencentDB 全都不做。

### 其他已跟踪项目的碰撞快速结论

- **CodeGraph**：虽同为"本地 SQLite 预索引 + 图谱"，但完全是**代码域**（AST/符号/调用边/34 语言），MyContext 是**办公语料域**（IM/文档/会议）。仅"图谱查询"这一技术手段有交集，领域与用途无碰撞。
- **Headroom / OpenViking / TencentDB**：已定性——上下游非竞品，MyContext 卡最上游"供料"。
- **herdr / EigenFlux / book-to-skill / Astryx**：Agent 多路复用、广播网络、书籍转 Skill、设计系统——与上下文供给无直接碰撞。
