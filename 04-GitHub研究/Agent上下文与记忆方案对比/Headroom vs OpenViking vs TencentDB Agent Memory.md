## 一句话定位

| 项目 | 定位 |
|------|------|
| **Headroom** | 本地运行的上下文**压缩层**，拦截 Agent 发给 LLM 的所有内容，砍掉 60–95% 冗余 token，压缩**可逆** |
| **OpenViking** | 自进化的上下文**数据库**，把记忆 / 知识 / 技能统一成 `viking://` 虚拟文件系统，Agent 像用文件一样浏览上下文 |
| **TencentDB Agent Memory** | 团队级**记忆中枢**，把对话 / 文档 / 代码变成 4 类可治理、可共享、可装配的记忆资产 |
| **MyContext** | 本地优先的**个人工档助理**，把 IM / 文档 / 会议多源数据加工成持续更新、可回溯的"工作档案"，靠**矛盾裁决**保准 |

> [!important] 核心结论
> 这四者看似同赛道，其实卡在上下文链路的**不同环节**：MyContext 管"**来源**"（多源数据采集与提炼，最上游），Headroom 管"**省**"（压缩传输中的 token），OpenViking 管"**存与取**"（上下文数据库），TencentDB 管"**团队沉淀与治理**"（记忆资产化）。它们**不完全互斥**，理论上可以叠加使用——MyContext 产出的档案素材，仍可交给 OpenViking/TencentDB 存储，再经 Headroom 压缩后喂给 LLM。

## 🧩 四者的分工与关系

```
Agent 工作时的上下文链路：

  数据源头（采）          长期沉淀层（存）          传输压缩层（省）
  ┌────────────────┐     ┌────────────────┐     ┌──────────────┐
  │ MyContext       │     │ OpenViking      │     │ Headroom      │
  │ （钉钉/飞书/     │ ──▶ │ TencentDB       │ ──▶ │ （压缩后发    │ ──▶ LLM
  │  文档/会议 →     │     │ Memory          │     │   给 LLM）    │
  │  工作档案）      │     └────────────────┘     └──────────────┘
  └────────────────┘       负责"记住、组织、取回"     负责"少发、省钱、可逆"
    负责"采集、提炼、裁决矛盾"
```

- **MyContext**：本地优先的个人工档层，**卡在链路最上游**，从多源工作数据提炼"职责/协作/结论"档案，自带矛盾语义裁决。
- **Headroom**：无状态中转层，Agent 发什么就压什么，**不存长期记忆**，解决"当下这次请求太贵太慢"。
- **OpenViking**：有状态数据库，统一存储 + 分层按需加载 + 会话自动沉淀成长期记忆。
- **TencentDB Agent Memory**：有状态 + 多 Agent 团队治理，强调资产化、权限、跨框架复用。

## 🏗️ 技术机制对照

| 维度 | MyContext | Headroom | OpenViking | TencentDB Agent Memory |
|------|-----------|----------|-----------|------------------------|
| **核心资产** | 多源数据 → 持续更新的**"工作档案"**（职责范围/协作关系/行为习惯/工作结论） | CCR 可逆压缩 + 3 个专用压缩器 | `viking://` 虚拟文件系统 + L0/L1/L2 分层 | L0–L3 分层（对话→原子→场景→人格）+ 4 类记忆资产 |
| **数据来源** | 原生对接**多源异构**：钉钉/飞书 IM、文档、会议记录 | Agent 发给 LLM 的内容 | 对话/知识/技能（自组织） | 代码库/文档/历史会话 |
| **独门算法** | **矛盾数据语义裁决**：判合并/覆盖，判不了交用户裁定，**用户确认后模型永不可再覆盖** | 按内容类型路由压缩器（JSON→SmartCrusher、代码→CodeCompressor、文本→Kompress-v2-base） | 写入时预生成三层：L0 摘要(~100 token) / L1 概览(~2k) / L2 原文，目录递归检索 | 异步管线逐层蒸馏，检索时按需回退 L1/L0 |
| **检索方式** | 档案按层级提炼后按需供给 | CCR 检索回原文（可逆） | 向量先定位最高分目录，再逐层下钻，**轨迹可观测** | BM25 + 向量 + RRF，带条数/字符/超时预算 |
| **可源溯/抗幻觉** | ✅ 每条信息带**来源+时间+内容**（可回溯） | ✅ CCR 可逆回到原文 | ⚠️ 部分（轨迹可观测但非逐条溯源） | ✅ asset 级 |
| **长期记忆** | ✅（档案自治沉淀） | ❌ 无（只做压缩） | ✅ 会话 commit 后异步抽取偏好与经验 | ✅ 核心卖点，资产化管理 |
| **本地优先** | ✅ 用户本机运行 | ✅ 数据不出本机 | ✅ | ❌ 三服务部署 |
| **代码理解** | ❌ 面向办公语料，非代码 | CodeCompressor（AST 压缩） | 作为 resource 存储 | CodeGraph（符号/调用/影响路径） |
| **交付形态** | 本地桌面应用 + GitHub `openTrinity`，本地 SQLite 存储，Elastic 2.0 | 库 / TS SDK / HTTP 代理 / MCP | pip 包 + CLI(`ov`) + 多 Agent 集成 | memory-core + memory-hub + proxy 三服务 |
| **人机协同/分身** | ✅ 以用户语气拟人回复，**发送等动作需人授权** | ❌ | ❌ | ❌ |
| **权限/团队** | 本次个人版无，企业版规划中 | ❌ 无 | 按 user 隔离 | ✅ private/team/restricted(ACL)/agent 四级可见性 |

> [!note] MyContext 的技术支柱（据公开资料 + ChooseAI 对 README 的拆解）
> 多源数据 → 分层信息提炼（与 OpenViking/TencentDB 的"分层按需加载"思想同构）→ 高熵冲突用**语义分析与人工锚定**处理（判合并/覆盖，判不了交用户，用户确认后模型永不再覆盖）。搜索结合**本地全文检索 + 语义召回 + 图谱查询**，答案须挂得住来源引用；Agent 环境不可用时**明确降级为本地结果而非编造**。存储为本地 SQLite（版本化迁移，部分不可逆）。已实现 IM/文档/会议采集，日历/任务/邮件在规划中。

## 📊 性能基准（各自口径，不可直接横比）

| 项目 | 衡量维度 | 数据 |
|------|---------|------|
| **Headroom** | token 压缩率 | JSON 场景 60–95%；基准 10,144→1,260 token（~88%） |
| **OpenViking** | 长期记忆召回质量 | LoCoMo 准确率 24–57% → 80–83%，输入 token 降 34–91%，延迟降 58–66% |
| **TencentDB Agent Memory** | 人格/记忆一致性 + 编码能力 | PersonaMem 48% → 76%（+59%）；SWE-bench 通过率 +9.9%；输入 token −33% |

> [!warning] 基准维度完全不同
> Headroom 测的是**压缩率**，OpenViking 测的是**记忆召回准确率**，TencentDB 测的是**人格一致性**——三个数字不在同一维度上，不能直接横向比较。

## ✅ 各自优点

**Headroom**
- 直击 token 成本，proxy 模式零代码改动，Apache 2.0 商用无忧
- CCR 可逆机制保证答案质量，不是有损摘要
- 本地优先，数据不出本机

**OpenViking**
- 数据库范式最完整：统一存储、可浏览（ls/tree/find）、检索轨迹可调试
- 分层按需加载从根上省 token，且会话自动沉淀长期记忆
- 字节大厂背书，迭代活跃（2026-01 创建）；核心技术来自 **VikingMem 论文（VLDB 2026 录用）**，源于字节内部 VikingDB 向量检索积累

**TencentDB Agent Memory**
- 唯一覆盖**多 Agent 团队治理**：资产版本、归属、ACL 权限、人工审核、loadout 装备绑定
- 冷启动友好：导入代码库/文档/历史会话即自动生成资产（Chat Memory / Skill / LLM-Wiki / CodeGraph 四类）
- **明确拒绝**暴力堆历史和不可逆有损摘要（立场鲜明，几乎直指 Headroom 这类方案的软肋）
- TypeScript 栈对 Node 生态友好，"一人公司组建会成长的 Agent 团队"叙事清晰

**MyContext**
- 卡在**最上游**：从钉钉/飞书/文档/会议的真实工作语料采集提炼，别人都是"没数据先存"，它是"先有真实数据"
- **矛盾数据治理是独门武器**：多源冲突时语义裁决（合并/覆盖），判不了交用户裁定，**且用户确认后模型永不可覆盖**——把"取最新/取最高置信"都可能会丢信息的问题单独拎出来解决
- 本地优先 + **全程可回溯**（来源/时间/内容），抗幻觉能力强
- 自带**人机安全闸**：拟人自动回复等有后果的动作必须用户授权，对齐"人机协同"而非纯工具
- 背靠钉钉 2000 万企业/近 8 亿用户的数据入口 + 千问办公作为落地消费方，是**有真实闭环**而非通用框架

## ⚠️ 各自局限

| 项目 | 主要局限 |
|------|---------|
| **Headroom** | 不做长期记忆；极端情况下 LLM 可能未检索原文而漏细节；需本机跑 proxy/MCP |
| **OpenViking** | AGPL-3.0 对闭源集成有传染性；多了一层服务端基础设施；Python 生态为主 |
| **TencentDB Agent Memory** | LICENSE 非标准需核实；三服务部署偏重；团队治理功能对个人单 Agent 场景略显冗余 |
| **MyContext** | **仍处早期**：上线约 1 周仅 1k+★，算法细节偏概念，未经社区大规模回测，可信度远不如已被验证的三家；现阶段只接 IM/文档，个人版绑定钉钉/飞书生态；强依赖阿里云/千问 embedding 与模型链路，跨生态通配性未知；**不能替代其他三家**（只出档案素材，喂模型前该压还得压） |

## 🎯 怎么选

- **只想立刻省 token、不改代码** → **Headroom**：proxy 模式最省事，Apache 2.0 商用无忧。
- **要给 Agent 建可浏览、可调试、会自我沉淀的上下文库** → **OpenViking**：数据库范式最完整，但注意 AGPL 传染性。
- **做多 Agent 协作 / 团队知识资产化 / 需要权限治理** → **TencentDB Agent Memory**：唯一覆盖这块，Node 生态友好。
- **想要"会自己采集、提炼并裁决矛盾的私人工档助理"** → **MyContext**：本地优先、可回溯、有真实办公数据入口，但目前仍处早期、绑定钉钉/飞书生态。

> [!tip] 组合玩法
> Headroom（传输压缩）与存储记忆类（OpenViking/TencentDB）不冲突，可叠加：用 OpenViking/TencentDB 管长期记忆，用 Headroom 压进入上下文的内容。MyContext 在最上游负责"供料"——它产出的工作档案素材，可存进 OpenViking/TencentDB，再经 Headroom 压缩喂给 LLM，形成 "采 → 存 → 省" 完整链路。
>
> 💡 MyContext 与三家本质是**上下游**关系，不构成直接竞争，反而是打通链路缺的那块源头拼图。

## 💡 个人思考

这四个项目放在一起看，正好勾勒出 Agent 上下文工程的**完整栈**：最上游是"采"（MyContext 采集提炼多源数据），底层是"记住"（存储与检索），上层是"省着用"（压缩与按需加载）。Headroom 赌的是"token 大多浪费在重读上"，所以做可逆压缩；OpenViking 赌的是"上下文应该像文件系统一样被确定性地浏览"，所以做虚拟文件系统 + 分层；TencentDB 赌的是"经验应该资产化、团队化、可复利"，所以做治理中枢；而 **MyContext 赌的是"Agent 最缺的是真实、可信、有据可查的工作上下文"，所以从数据源头做起**。

有意思的是四者都用了**分层按需加载**这同一思想（Headroom 的 CCR、OpenViking 的 L0/L1/L2、TencentDB 的 L0–L3、MyContext 的档案层级提炼），只是落点不同——一个落在"压缩后可取回"，一个落在"写入时预分层"，一个落在"对话逐层蒸馏成人格"，一个落在"多源高熵语料的提炼与裁决"。这说明"别把全部内容一次性灌给 LLM"已经是行业共识。

**MyContext 真正值得单独深挖的不是"分层/本地/可回溯"这些共性**（它们三家里也有），而是它的独门差异：
- **矛盾数据的语义裁决 + 人工锚定**——当群聊说"下周一上线"、文档写"月底"，传统方案"取最新/取最高置信"都会丢信息。MyContext 用语义分析判合并/覆盖，判不了交用户裁定，且**用户确认后的结论模型永不可覆盖**，等于给档案上了人工锁。这是 OpenViking/TencentDB 都没有的机制。
- **对齐"人机协同 + 数字分身"的产品闭环**，而非纯基础设施——默认落在一个"以用户语气自动回复工作消息"的应用上，还带人机安全闸。

从工程选型看，**个人开发者 / 重度 coding agent 用户**从 Headroom 入手收益最直接；**团队 / 企业**如果要沉淀跨 Agent 的组织经验，则 OpenViking 或 TencentDB 更合适，二者的分水岭在于是否需要"人管资产"的治理面板和权限体系；**要在真实办公场景里让 Agent"懂你"** 则关注 MyContext（但要等它成熟）。

> [!quote] 一句话总结
> Headroom 是"省钱的可逆压缩阀"，OpenViking 是"可浏览的上下文数据库"，TencentDB Agent Memory 是"会复利的团队记忆中枢"，**MyContext 是"会自己采集、提炼并裁决矛盾的私人工档助理"**——它们解决的是 Agent 上下文问题的四个不同环节，而非四个竞品；MyContext 卡在最上游"供料"，可与另外三家叠加成 "采 → 存 → 省" 链路。
