## P0（照抄必翻车 / 概念教错）

### P0-① `07 场景 1` api 连的是不存在的 `db` Service → 应用起来也连不上库

- **位置**：`07-业务场景实战合集.md` L122-125（api 的 `DATABASE_URL`）；对照 L137-151（db 的 Service 只有 `db-headless`）
- **原文摘录**：
  > L125：`value: "postgres://user:pass@db:5432/app"`
  > L140：`metadata: { name: db-headless }` … `clusterIP: None`
- **问题说明**：该块只创建了 `web`、`api`、`db-headless` 三个 Service，**没有名为 `db` 的 Service**。`db` 这个短名在 CoreDNS 里查不到（StatefulSet 的 Pod DNS 是 `db-0.db-headless`，Service 是 `db-headless`）。结果：Pod 全部 Running（不报错），但 api 连库 `getaddrinfo ENOTFOUND db`，属于最危险的**静默语义错误**。同页 L548 的练习命令 `kubectl exec … "nc -z db 5432"` 也踩同一个坑。
- **修复建议**：把 headless Service 直接命名为 `db`（`metadata.name: db` + `clusterIP: None`，StatefulSet 的 `serviceName: db` 同步改），这样 `db` 既可解析又保持 headless 语义；或保留 `db-headless` 并新增一个普通 ClusterIP Service `db`。
- **验证方式与结果**：静态名称比对脚本输出 `L77 services=['api','db-headless','web'] / env host refs=[('db','5432')] / !! hosts with no Service: ['db']`（未实跑）。

### P0-② `附录-Compose 到 K8S` 的 initContainer 永远等不到 `db` → api 卡在 `Init:0/1`

- **位置**：`附录-Compose 到 K8S 逐行对照.md` L176-182（initContainers）；对照 L229-239（db 的 Service 名为 `db-headless`）
- **原文摘录**：
  > L179：`command: ["sh", "-c", "until nc -z db 5432; do sleep 1; done"]`
  > L233：`name: db-headless`
- **问题说明**：与 P0-① 同根，但症状更糟——`until` 循环不设上限，`db` 永不解析，api 的两个 initContainer 之一会**永久 Loop**，api Pod 永远停在 `Init:0/1`，后面所有验证（探针、Ingress、自愈）都无从谈起。而附录 L405-408 的挑战练习要求"通过 Ingress 访问 web → web 调 api → api 调 db"，第一步就断。
- **修复建议**：同名修复（把 headless Service 命名为 `db`）；另外给 `until` 加超时（`until nc -z db 5432 || [ $SECONDS -gt 60 ]; do sleep 1; done`），避免无限等待掩盖真因。
- **验证方式与结果**：同上脚本，该块输出 `services=['api'] / refs=[('cache','6379'),('db','5432')]`，`db` 在**全篇**任何代码块中都没有同名 Service（`cache` 有，见 L318）。

### P0-③ `v4` 在 ConfigMap 值里写 `$(POSTGRES_PASSWORD)`，K8s 不会展开它

- **位置**：`毕业项目-Web应用K8S化/v4-ConfigMap与Secret版.md` L59（ConfigMap 的 `DATABASE_URL`）、L91-96（api 的 env 引法）
- **原文摘录**：
  > L59：`DATABASE_URL: "postgres://user:$(POSTGRES_PASSWORD)@db-0.db-svc:5432/app"   # $(POSTGRES_PASSWORD) 由 K8S 变量替换注入`
  > L94-96：`- name: DATABASE_URL / valueFrom: / configMapKeyRef: …`
- **问题说明**：K8s 的 `$(VAR_NAME)` 展开**只作用于 `env[].value` 这个字面量字段**（`EnvVar.value` 的 API 文档原文："Variable references $(VAR_NAME) are expanded using the previously defined environment variables in the container…"；`valueFrom` 与 `value` 是互斥字段，文档不承诺对 `valueFrom` 取值做展开）。而这里的 `$(POSTGRES_PASSWORD)` 是**写在 ConfigMap 的 data 里**的——ConfigMap 值不做任何变量展开（社区结论一致："variables/secrets expansion is not supported in ConfigMaps"）。所以容器里拿到的 `DATABASE_URL` 极可能是字面量 `postgres://user:$(POSTGRES_PASSWORD)@db-0.db-svc:5432/app`，密码段变成字符串 `$(POSTGRES_PASSWORD)`，psql 认证失败。注释"由 K8S 变量替换注入"是**教错了机制**。
- **修复建议**：把完整连接串放进 Secret（`DATABASE_URL: "postgres://user:super-secret-password-v4@db-0.db-svc:5432/app"` 用 `stringData`），api 只 `secretKeyRef`；或保留拆分但改成 `env[].value` 字面量组合（`value: "postgres://user:$(POSTGRES_PASSWORD)@db-0.db-svc:5432/app"` 且 `POSTGRES_PASSWORD` 的 env 项必须排在它前面）——后者才是 `$()` 真正生效的写法，可作为"两种写法对比"的教学点。
- **验证方式与结果**：官方 API 语义（`value` 与 `valueFrom` 互斥，展开语义只写在 `value` 上）+ StackOverflow 高票结论（ConfigMap 内不支持变量展开）；**未实跑**（本机无集群）。建议实测一句：`kubectl exec deploy/api -- printenv DATABASE_URL`，若输出含 `$(POSTGRES_PASSWORD)` 即证实。

## P1（重要缺陷：误导、缺关键验收、跨篇矛盾）

### P1-① `07 场景 5` 的备份 CronJob 一定失败（缺 `PGPASSWORD`，且 `mydb` 库不存在）

- **位置**：`07` L413-428
- **原文摘录**：
  > L427：`command: ["pg_dump", "-h", "postgres-0.postgres-headless", "-U", "postgres", "mydb"]`
  > L399-401：该 StatefulSet 只设了 `POSTGRES_PASSWORD`（`secretKeyRef`），**没有** `POSTGRES_DB`
- **问题说明**：两处硬伤：(1) `pg_dump` 非交互环境必须有 `PGPASSWORD`（或 `.pgpass`），否则 `fe_sendauth: no password supplied`；(2) 未设 `POSTGRES_DB` 时官方镜像默认库名是 `postgres`，`mydb` 不存在 → `database "mydb" does not exist`。这个 CronJob 的产物是每天一次的 `Failed` Job，而正文没给任何验证方式。
- **修复建议**：加 `- { name: PGPASSWORD, valueFrom: { secretKeyRef: { name: db-secret, key: POSTGRES_PASSWORD } } }`，并把库名改成 `postgres`（或在该 StatefulSet 补 `POSTGRES_DB: app` 后保持 `app`）；验证加一句 `kubectl get jobs -l …` → `COMPLETIONS 1/1`。
- **验证方式与结果**：静态字段核对（`grep PGPASSWORD` 全篇 0 次；`POSTGRES_DB` 在该 StatefulSet 块内 0 次）；未实跑。

### P1-② `05b` 进阶练习的 `-f values-dev.yaml` 路径与实际写入位置不一致（直接报 no such file）

- **位置**：`05b-Helm 与 Chart 模板.md` L431-437（写入）、L455-456（引用）
- **原文摘录**：
  > L431：`cat > my-first-chart/values-dev.yaml << 'EOF'`
  > L455：`helm install myapp ./my-first-chart -f values-dev.yaml -n dev --create-namespace`
- **问题说明**：文件被写进 `my-first-chart/` 目录，命令却在当前目录找 `values-dev.yaml`。`helm` 会直接 `open values-dev.yaml: no such file or directory`。同一段还有第二个坑：`-n dev --create-namespace` 建了 namespace，但 L459 `kubectl get pods -n dev` 之前没有任何等待/验证，学员容易把"Pod 还没起来"误判成失败。
- **修复建议**：命令改为 `-f my-first-chart/values-dev.yaml`（或 `cd my-first-chart` 后再 `-f values-dev.yaml`）；v6 L243 的 `-f values-prod.yaml` 同源问题一并统一。
- **验证方式与结果**：路径静态比对（写入路径 2 段，引用路径 1 段）；未实跑 helm。

### P1-③ `05b` 挑战练习的模板会渲染失败：`.Values.db.host` 在 `db` 键不存在时是 nil pointer

- **位置**：`05b` L472-484（ConfigMap 模板）、L497（只追加了 `redis:` 到 values）
- **原文摘录**：
  > L482-483：`host: {{ .Values.db.host | default "localhost" }}` / `port: {{ .Values.db.port | default 5432 }}`
- **问题说明**：`helm create` 生成的 values.yaml 里没有 `db` 键，练习也只 `printf 'redis:\n  enabled: true\n' >>`。Go template 对 nil 取子键会直接报 `nil pointer evaluating interface {}.host`——`default` 救不了它（`default` 只在取到的值本身为空时生效，而这里连取值这一步就 panic）。所以这份"挑战练习"的模板一 `helm install` 就报错。
- **修复建议**：在 values.yaml 显式给骨架（`db: {host: localhost, port: 5432}`），或模板改成 `{{ dig "host" "localhost" (.Values.db | default dict) }}`；并在文字里点明这个坑（"`default` 挡不住 nil pointer，需要先给默认 map"），这本身是个很好的教学点。
- **验证方式与结果**：Go template 求值语义推理（未实跑 helm）；同类报错在 Helm 社区为高频已知错误。

### P1-④ `v6` 用 `myapp.*` 引用了 v5 里叫 `webapp.*` 的 helper，且 ServiceMonitor 选不到任何 Service

- **位置**：`v6-监控告警版.md` L148、L150、L155；对照 `v5` L113-123（只定义了 `webapp.labels` 与 `webapp.fullname`，**没有** `selectorLabels`）
- **原文摘录**：
  > v6 L148：`name: {{ include "myapp.fullname" . }}`
  > v5 L114：`{{- define "webapp.labels" -}}`
- **问题说明**：两层错：(1) chart 名是 `webapp`，helper 前缀却是 `myapp` → `helm upgrade` 直接 `no template "myapp.fullname" associated with template "gotpl"`，整个 v6 装不上；(2) 即使改名，`spec.selector.matchLabels` 用的是 `app.kubernetes.io/*` 标签，而 v5 的 `web-service.yaml`/`api-service.yaml` 模板**没有给 Service 打任何 labels**（v5 L151-159 只写了 `type/selector/ports`）——ServiceMonitor 是按 **Service 的 labels** 选的，选不到就没有 target，Prometheus 一条指标都采不到（而且这是静默失败：`kubectl get servicemonitor` 一切正常）。
- **修复建议**：v6 统一改用 `webapp.*`；v5 给每个 Service 的 `metadata.labels` 加 `{{- include "webapp.labels" . | nindent 4 }}`，并在 `_helpers.tpl` 补 `webapp.selectorLabels`；同时在 v6 加验证语句"`kubectl get endpoints -n prod` / Prometheus UI → Status → Targets 里能看到 `myapp-api`"。
- **验证方式与结果**：名称与字段静态比对（v5 全文无 `selectorLabels` 定义、Service 模板无 labels）；未实跑 helm。

### P1-⑤ HPA 练习的压测负载大概率压不到阈值，学员会误以为 HPA 坏了

- **位置**：`05` L306-308 与 L417-420；`99-第二周复习检查点` L99-104
- **原文摘录**：
  > L419-420：`kubectl run load --rm -it --image=busybox:1.36 -- /bin/sh -c "while true; do wget -q -O- http://hpatest; done"`
- **问题说明**：HPA 的 `averageUtilization` 是"**实际 CPU / requests**"。Deployment 的 requests 是 `cpu=100m`，要触发 50% 需要单 Pod 稳定消耗 50m。单个 busybox `wget` 循环是"起进程→建连→取首页→退出"，吞吐通常只有几十到一两百 rps，nginx 在 alpine 上服务静态首页的 CPU 往往只有 10–20m。结果是 `TARGETS` 长期显示 `0%/50%`，`kubectl get hpa -w` 永远不动 —— 练习的"观察扩容"做不到，而这恰好是最容易让初学者怀疑"K8s 装坏了"的环节。
- **修复建议**：三选一（按可靠度）：(a) 把 requests 降到 `cpu=10m`（同样负载即可越过 50%）；(b) 起 3–5 个 loadgen（`--replicas` 不支持，改用 `kubectl create deployment load --image=busybox -- sh -c "…"` 后 scale）；(c) 用 `hey`/`ab`/`wrk` 容器打并发。并在步骤里给出验收阈值："`TARGETS` 出现 `>50%` 且 `REPLICAS` 从 1 变到 2"。
- **验证方式与结果**：HPA 计算式与负载模型推理（**未实跑**，本机无集群）。属"高置信、需实测确认"的条目。

### P1-⑥ `07 场景 2` 把"滚动更新"当成"灰度发布"讲（概念教错）

- **位置**：`07` L213-218
- **原文摘录**：
  > L216：`# Docker Swarm + Traefik 加权路由（手动配置，较粗糙）`
  > L217：`docker service update --image myapp:v2 --update-parallelism 1 web`
- **问题说明**：`docker service update --image` 是**滚动更新**（逐个替换 task），不是按比例分流的灰度；标题写"Traefik 加权路由"，命令里却完全没有 Traefik。这会让"灰度 vs 滚动更新"这个高频面试考点在一开始就被混淆——而 08 Q18（零停机部署）恰好要求区分这两者。
- **修复建议**：改成真正的 Swarm 灰度手法（两个 service + Traefik `traefik.http.services.*.loadbalancer.weight` 或 `--replicas` 比例 + 单一 frontend），或干脆改写为"Docker 侧只能靠副本比例做粗粒度灰度，无权重路由原语"。
- **验证方式与结果**：`docker service update` 语义（官方 CLI 参考：`--update-parallelism` 控制滚动更新的并发 task 数）；未实跑。
