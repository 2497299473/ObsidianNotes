### P1（重要缺陷：误导、缺关键验收、跨篇矛盾）

#### P1-① 毕业项目 v1→v6 主线在 v5 断裂，v6 依赖不存在的前置

- **位置**：`v5-Helm包管理版.md` L32-54（Chart 结构）、L125-207（实际给出的模板）、L22-30（改造对照表）；`v6-监控告警版.md` L140-164
- **原文摘录**：
  > v5 L40-52：`templates/` 下列出 `_helpers.tpl / configmap.yaml / secret.yaml / web-deployment.yaml / web-service.yaml / api-deployment.yaml / api-service.yaml / db-statefulset.yaml / db-service.yaml / cache-deployment.yaml / cache-service.yaml / ingress.yaml`（**11 个**）
  > v5 L216-217：`helm create webapp-chart` → `# 然后用上面的 Chart.yaml、values.yaml 和 templates/ 替换默认内容`
- **问题说明**：文档实际只给出 **2 个**模板（`web-deployment.yaml`、`db-statefulset.yaml`，后者还内联了 db 的 Service）。`api-deployment.yaml`、`api-service.yaml`、`cache-*`、`configmap.yaml`、`secret.yaml`、`ingress.yaml` 全部只有文件名没有内容。后果链：
  1. `helm install` 后只有 nginx + postgres 起来，**api 与 cache 根本不存在**，v4 里配好的 `DATABASE_URL`/`REDIS_URL` 无处可用；
  2. v5 L232-233 的升级验证 `--set api.replicas=3` 打在一个不存在的模板上，`kubectl get pods -l app=myapp-api` 必然空；
  3. v6 L163-164 明确要求"v5 Chart 中 `templates/api-service.yaml` 定义端口名 `http`"——这份文件在 v5 从未出现，v6 的 ServiceMonitor 落到无对象可采。
- **修复建议**：在 v5 补齐 `api-deployment.yaml`、`api-service.yaml`（端口 `name: http`）、`cache-*`、`configmap.yaml`、`secret.yaml`、`ingress.yaml` 六个模板；或在 v5 开头明确写"本版只演示 web+db 两个模板的模板化手法，其余五个模板与 v4 相同，请自行照抄 v4 YAML 加 `{{ }}`"，并把 v6 的前置条件改为"确认 api-service 端口已命名"。
- **验证方式与结果**：静态比对——`grep` v5 全文，`templates/` 仅出现 3 处带内容的代码块（`_helpers.tpl`、`web-deployment.yaml`、`db-statefulset.yaml`），`api-deployment`/`api-service` 字样仅出现在目录树与 v6 引用中（未实跑 helm，因本机无 helm）。

#### P1-② v1 的自检标准与 v1 的 YAML 自相矛盾

- **位置**：`v1-Deployment基础版.md` L100-110（api env）、L62-63（"ports 暂不处理 / volumes 暂不处理"）、L206（🟢 自检）
- **原文摘录**：
  > L105-106：`- { name: DATABASE_URL, value: "postgres://user:pass@db:5432/app" }` / `- { name: REDIS_URL, value: "redis://cache:6379" }`
  > L206：`🟢 基础 | 4 个 Deployment 全部 Running，kubectl scale 扩缩容正常`
- **问题说明**：v1 明确"网络层留给 v2"，因此 v1 **没有任何 Service**，`db`/`cache` 这两个主机名在集群内不可解析。若 Flask 应用启动即连库（绝大多数示例如此），api 会 `CrashLoopBackOff`，v1 的 🟢 验收条件"4 个 Deployment 全部 Running"不可达。这不是"没写清楚"，而是**验收标准与示例代码互斥**，学员第一步就会怀疑自己环境坏了。
- **修复建议**：三选一——(a) 在 v1 声明里注明"api 预期 CrashLoop（DNS 未就绪），v2 加 Service 后恢复"，并把 🟢 改成"4 个 Deployment 均被创建、web/db/cache 三个 Running"；(b) 给 v1 加一个最小 ClusterIP Service 给 db（破坏"只改一个维度"，不推荐）；(c) 把 api 的镜像换成一个不依赖 DB 的占位镜像。
- **验证方式与结果**：静态推理 + 名称比对（脚本 `ref_check.py`：v1 代码块内 Service 数量 = 0，env 中出现 `db`、`cache` 两个主机名）——未实跑。
