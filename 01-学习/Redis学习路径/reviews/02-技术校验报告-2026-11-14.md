### P0（照抄必翻车 / 概念教错）

#### T-1　阶段一 02 整表按 Redis 6.2 讲编码：Hash 默认值、List 编码、配置名三处错

- **位置**：`阶段一-数据结构与命令/02-五大基础数据结构.md:19, 32, 33, 34, 35, 135-140, 242`
- **原文摘录**：
  > `:137`　| Hash | ziplist | hashtable | `hash-max-ziplist-entries`（默认128） |
  > `:138`　| List | ziplist | quicklist | `list-max-ziplist-size` |
- **问题说明**（逐条对照官方文档）：
  1. **Hash 小编码**：7.0 起为 `listpack`（ziplist 仅 ≤6.2）。文档：`OBJECT ENCODING` → "Hashes … `ziplist`, Redis <= 6.2 … `listpack`, Redis >= 7.0"。
  2. **Hash 默认条目数**：`hash-max-listpack-entries` 默认 **512**，不是 128（128 是 **ZSet** 的默认值）。文档 Memory optimization 页 "Redis >= 7.0: hash-max-listpack-entries 512 / zset-max-listpack-entries 128"。
  3. **List 小编码**：**不存在** "ziplist 小数据编码"。7.0+ 小 list 的 `OBJECT ENCODING` 直接是 **`listpack`**；元素多了才变 `quicklist`（quicklist 的节点自 7.0 起也是 listpack）。ziplist 仅 ≤6.2。阈值参数是 `list-max-listpack-size`，**默认 -2（8KB/节点，负数表示字节数而非条目数）**。表里"小数据 ziplist → 大数据 quicklist、`list-max-ziplist-size`"三格全错。
  4. **Set**：7.2 新增 `listpack` 编码（`set-max-listpack-entries 128` / `value 64`），表中只写 intset/hashtable，漏掉 7.2 新特性（而 `00 索引:20` 已写明"Set 自 7.2 起还有 listpack 编码"）。
  5. **ZSet**：小编码同为 `listpack`（≥7.0），非 ziplist；默认 128 正确。
  6. `:242` 🔴 自检"能解释 ziplist 和 skiplist 的时间复杂度差异"——在 7.2 上应先解释 listpack，否则学习者 `OBJECT ENCODING` 看到的字和书上对不上。
- **修复建议**：把 `:135-140` 整表替换为 7.2 口径：

  | 类型 | 小编码（7.2） | 大编码 | 阈值（默认） |
  |------|--------------|--------|-------------|
  | Hash | listpack（≥7.0） | hashtable | `hash-max-listpack-entries` 512 / `-value` 64 |
  | List | listpack（≥7.0 的小 list） | quicklist（节点为 listpack） | `list-max-listpack-size -2`（8KB/节点，非条目数） |
  | Set | intset（全整数）/ listpack（≥7.2 非整数） | hashtable | `set-max-intset-entries` 512；`set-max-listpack-entries` 128 |
  | ZSet | listpack（≥7.0） | skiplist+hashtable | `zset-max-listpack-entries` 128 / `-value` 64 |

  并在 `:19` 学习目标、`:32/:35` 对比表、`:242` 自检同步改词；补一句"旧 `*-max-ziplist-*` 名在 7.x 仍作为别名可用，但新配置应写 `*-max-listpack-*`"。另：`00 索引:20` 的"List 自 3.2 起始终为 quicklist"也不够准（7.0+ 小 list 直接以 listpack 编码），该句应一并改为"3.2 起引入 quicklist；7.0 起小 list 直接用 listpack、quicklist 节点亦为 listpack"。
- **验证方式与结果**：
  - https://redis.io/docs/latest/commands/object-encoding/ （List/Hash/Set/ZSet 编码与版本分界，已抓取原文）
  - https://redis.io/docs/latest/operate/oss_and_stack/management/optimization/memory-optimization （`hash-max-listpack-entries 512`、`zset-max-listpack-entries 128`、`set-max-listpack-entries 128`）
  - 7.2 分支 `redis.conf` 原文实测：`hash-max-listpack-entries 512`、`list-max-listpack-size -2`、`set-max-listpack-entries 128`、`zset-max-listpack-entries 128`（`cdn.jsdelivr.net/gh/redis/redis@7.2/redis.conf` 抓取后 grep）。**已实测。**

#### T-2　MOVED 示例的槽号与目标节点双错（`mykey` 实为 14687 → 7002）

- **位置**：`阶段二-持久化与高可用/03-Cluster分片集群.md:84, 91-92`
- **原文摘录**：
  > `:84`　redis-cli -p 7000 CLUSTER KEYSLOT mykey
  > `:92`　# (error) MOVED 5798 127.0.0.1:7001
- **问题说明**：`CLUSTER KEYSLOT mykey` 的真实返回值是 **14687**。按本页 `:31-37` 的分配（0-5460 / 5461-10922 / 10923-16383），14687 落在 **7002**，不是 7001。学习者按 `:84` 自测会立刻拿到与 `:92` 矛盾的数字；更糟的是同一页同时教"槽→节点"映射，示例却给出错误的映射，属于概念级错误。范例可改用官方 cluster-spec 的 `GET x → -MOVED 3999 127.0.0.1:6381` 形式，或直接写真实值。
- **修复建议**：改为
  ```
  redis-cli -p 7000 SET mykey hello
  # (error) MOVED 14687 127.0.0.1:7002
  ```
  并在下一行加"槽号可用 `CLUSTER KEYSLOT mykey` 复核（→ 14687）"，把示例变成自洽的自测闭环。
- **验证方式与结果**：用 Redis 官方 CRC16(XMODEM) 算法本地计算：`crc16("mykey") % 16384 = 14687`（同实现校验 `foo → 12182` 与官方文档示例一致）。**已实测（纯计算，未连服务器）。**

#### T-3　`sentinel.conf` 只启 1 个哨兵却配 quorum 2 → 永远不会 ODOWN，而 run.sh 声称"5 秒后自动切换"

- **位置**：`code/05-replication/sentinel.conf:5`、`code/05-replication/run.sh:14, 19`
- **原文摘录**：
  > `sentinel.conf:5`　sentinel monitor mymaster 127.0.0.1 6379 2
  > `run.sh:14`　redis-sentinel sentinel.conf --daemonize yes　　`run.sh:19`　哨兵将在 5 秒后自动切换
- **问题说明**：quorum 是"**判定客观下线所需同意票数**"，票源是哨兵自己 + 其他哨兵。只启 1 个哨兵时最多 1 票 < 2，**永远进不了 ODOWN，也就永远不会 failover**。脚本却明确承诺 5 秒切换，学习者按脚本走会发现"主库已死、哨兵毫无反应"，从而怀疑自己对哨兵的理解。这与 `阶段二/02:196`"至少 3 个哨兵（奇数）"直接冲突——正文说要 3 个，代码只给 1 个。
- **修复建议**：二选一——
  ① 最低成本：把该 conf 的 quorum 改 **1**，并在文件头注明"单哨兵仅用于观察 SDOWN/日志，**不具备故障转移能力**（failover 需多数哨兵授权）"；
  ② 推荐：补 `sentinel-26380.conf`/`sentinel-26381.conf`（同 monitor 行、不同 port），run.sh 起 3 个，quorum 保持 2，此时"5 秒 SDOWN → 数秒内 ODOWN → switch-master"才成立。
- **验证方式与结果**：https://redis.io/docs/latest/operate/oss_and_stack/management/sentinel/ 原文："The **quorum** is the number of Sentinels that need to agree about the fact the master is not reachable… the quorum is only used to detect the failure. In order to actually perform a failover… vote of the **majority** of the Sentinel processes."；同页 "You need at least three Sentinel instances for a robust deployment."。**已实测（文档核对 + 逻辑推理；未实跑）。**

#### T-5　哨兵篇把 quorum 说成"多数投票"，与总索引的"两个独立概念"口径冲突

- **位置**：`阶段二/02-主从复制与哨兵.md:110, 130`；`v4-主从高可用版.md:32`
- **原文摘录**：
  > `:110`　sentinel monitor mymaster 127.0.0.1 6379 2   # 2 = 多数投票
  > `:130`　3. 询问其他哨兵 → 多数同意 → 标记客观下线（ODOWN）
- **问题说明**：ODOWN 的门槛是 **quorum**，Leader 授权才是 **majority**。3 哨兵 + quorum 2 时两者数值恰好都是 2，看不出差别；换成 5 哨兵 + quorum 2 就会暴露（2 票即可 ODOWN，但仍需 3 票授权）。`00 索引:20` 已明确写"quorum 与 majority 是两个独立概念"，正文却用同一个词"多数"覆盖两步。v4 只给 quorum 数字、不做任何解释。
- **修复建议**：`:110` 注释改"2 = **quorum**（判定 ODOWN 所需同意票数，≠ 选举授权票数）"；`:130-131` 拆成"达到 quorum → ODOWN"与"多数哨兵投票 → 选出 Leader"两步并各注英文名；v4 在配置块下补 2 行同义说明。
- **验证方式与结果**：官方 Sentinel 页同 T-3 引文（quorum 只用于判失败，failover 需 majority 授权）。**已实测（文档）。**

#### T-6　缓存击穿的互斥锁示例不带 owner token 就 `DEL`，与本文自己的陷阱表冲突

- **位置**：`阶段三/03-缓存三大问题与分布式锁.md:60-66`；`code/08-cache-penetration/demo.py:32-38`

#### T-7　分布式锁缺"续期/看门狗"实现，Redlock 缺时间预算与 fencing token

- **位置**：`阶段三/03:117-125, 204`
- **原文摘录**：
  > `:119`　Redlock 在多个独立 Redis 节点上申请锁，过半成功才认为加锁成功。
  > `:125`　业界常用单节点 `SET NX EX` + 看门狗续期（如 Redisson）
- **问题说明**：三处缺口：① "看门狗"只出现名字，没有实现思路（后台线程按 `TTL/3` 续期、续期也要校验 token）；② Redlock 缺"**必须在锁有效期内、扣除时钟漂移后**完成多数派加锁，总耗时超预算即视为失败"这一关键约束，只写"过半成功"会让人以为可以慢慢重试；③ 缺 fencing token（单调递增版本号）这一"锁过期后旧持有者仍可能写库"的兜底手段——而这正是 Redlock 争议的核心。`:204` 🔴 自检要求"能用 Lua 实现完整的分布式锁（加锁/解锁/续期）"，正文没有续期任何内容（见体验报告 E-2）。
- **修复建议**：补"锁续期"伪代码（`if GET==token then PEXPIRE`）+ "锁过期后业务仍在跑"的时序图 + fencing token 一段；Redlock 段补"有效性 = TTL − 加锁耗时 − 时钟漂移"。
- **验证方式与结果**：与正文 `:181` 陷阱"锁过期但业务未完成 → 用看门狗续期"对照，确认只在陷阱表出现、正文无展开。**已实测（文本对照）；Redlock 具体阈值属推理，未引官方规范。**

#### T-8　Cluster 实验的 6 个节点共用同一工作目录，`dump.rdb`/`appendonlydir` 互相覆盖

- **位置**：`code/06-cluster/redis-7000.conf:1-6`、`code/06-cluster/run.sh:8-10`
- **原文摘录**：
  > `redis-7000.conf`（全文 6 行，无 `dir`、无 `dbfilename`）
  > `run.sh:8`　sed "s/7000/$port/g" "$CONF_DIR/redis-7000.conf" > "$CONF_DIR/redis-$port.conf"
- **问题说明**：`sed` 只替换了端口，6 个实例的 `dir` 都是当前目录，`dbfilename` 都是默认 `dump.rdb`，7.x 下 `appendonlydir` 也是同一个目录（该 conf 第 5 行 `appendonly yes`）。同一目录多实例写同名 RDB/AOF 属经典踩坑：后写的覆盖先写的，重启用错数据；AOF 多文件结构下更可能因 manifest 冲突导致启动失败。这与正文 `阶段二/03` 的教学目标（"能搭建 3 主 3 从"）直接冲突——搭起来能跑，重启就出事。
- **修复建议**：模板加 `dir ./data/$PORT`（或 `dbfilename dump-$PORT.rdb` + `appenddirname aof-$PORT`），run.sh 里 `mkdir -p`；`sed` 同步替换 `$PORT` 占位符。
- **验证方式与结果**：配置文件原文审查（无 `dir/dbfilename/appenddirname`）+ `run.sh` 的 sed 逻辑推演。**未实跑**（本机无 redis-server），结论依据 Redis 默认文件名规则。

#### T-9　`Makefile` 的 v1 目标用 `kill %1` 收尾，跨 recipe 行必然失败

- **位置**：`毕业项目-分布式缓存网关/Makefile:21-26`
- **原文摘录**：
  > `:21-26`　python app.py & / sleep 2 / curl … / kill %1
- **问题说明**：make 默认**每行 recipe 起一个独立 shell**（未设 `.ONESHELL`），`python app.py &` 起在上一行的 shell 里，该 shell 退出即失去作业控制，最后一行 `kill %1` 报 `no such job` 并让 target 非 0 退出——"✅ v1 验收通过"永远打不出来，且 `app.py` 进程泄漏。既然全文件其余 target 都是单行/顺序命令，这里是最容易踩的一处。
- **修复建议**：改成单行串联或加 `.ONESHELL:`：`@python app.py & PID=$$!; sleep 2; curl …; kill $$PID`（用 `$$PID` 传真实 PID）；或改用 `flask --app app run &` + `trap`。
- **验证方式与结果**：make 语义推理（本机无 `make`，`Get-Command make` → NOT FOUND），**未实跑**；结论基于"每个 recipe 行独立 shell"这一 GNU make 行为。

#### T-10　v7 调优表用旧配置名 `hash-max-ziplist-entries`，且与阶段一 02 的默认值互相打架

- **位置**：`v7-监控与压测调优版.md:72`；对照 `阶段一/02:137`
- **原文摘录**：
  > `v7:72`　| hash-max-ziplist-entries | 512 | 1024 | 减少内存 |
