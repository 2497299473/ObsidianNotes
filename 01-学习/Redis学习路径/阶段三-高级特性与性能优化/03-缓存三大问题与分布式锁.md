## 📖 核心内容

### 缓存三大问题对比

| 问题 | 现象 | 根因 |
|------|------|------|
| **穿透** | 查不存在的数据，绕过缓存打 DB | 恶意攻击或查询不存在的 key |
| **击穿** | 热点 Key 过期瞬间，大量请求打 DB | 热点 key 过期 |
| **雪崩** | 大量 Key 同时过期，DB 压力骤增 | 过期时间集中 |

### 缓存穿透

**解决方案**：布隆过滤器、缓存空值

```python
# 缓存空值
value = r.get(key)
if value is None:
    value = db.query(key)
    if value is None:
        r.setex(key, 60, "EMPTY")  # 短过期空值
    else:
        r.setex(key, 300, value)
elif value == "EMPTY":
    return None  # 防穿透
```

### 缓存击穿

**解决方案**：互斥锁、逻辑过期

```python
# 互斥锁重建缓存（必须带 owner token，否则锁过期后会误删他人的锁——见下方分布式锁）
import uuid, time
lock_key = f"lock:{key}"
token = str(uuid.uuid4())
lock = r.set(lock_key, token, nx=True, ex=10)
if lock:
    try:
        value = db.query(key)
        r.setex(key, 300, value)
        return value        # ★ 抢锁成功者也要 return：否则包成函数后返回 None（自检加计数器时立刻踩到）
    finally:
        # 比对 token 再删（Lua 原子），避免删掉别人已抢到的锁
        r.eval("if redis.call('GET',KEYS[1])==ARGV[1] then return redis.call('DEL',KEYS[1]) else return 0 end", 1, lock_key, token)
else:
    # 未抢到锁：有限次退避重试，仍拿不到就降级直查 DB（不会无限递归）
    for attempt in range(3):
        time.sleep(0.05 * (2 ** attempt))   # 50ms → 100ms → 200ms
        value = r.get(key)
        if value is not None:
            return value
    return db.query(key)                    # 兜底：少量请求会打到 DB，但不会无限加深递归
```

### 缓存雪崩

**解决方案**：过期时间加随机值、多级缓存、熔断降级

```python
import random
expire = 300 + random.randint(0, 60)  # 过期时间打散
r.setex(key, expire, value)
```

### 分布式锁

**核心要求**：互斥性、避免死锁、可重入、容错性

```python
import uuid

# 最简分布式锁（SET NX EX 一条命令保证原子性）
def acquire_lock(key, expire=30):
    token = str(uuid.uuid4())
    ok = r.set(f"lock:{key}", token, nx=True, ex=expire)
    return token if ok else None

# 安全释放（Lua 保证比对+删除原子性）
unlock_script = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('DEL', KEYS[1])
else
    return 0
end
"""
def release_lock(key, token):
    r.eval(unlock_script, 1, f"lock:{key}", token)

# 使用
token = acquire_lock("order:1001")
if token:
    try:
        # 业务逻辑
        pass
    finally:
        release_lock("order:1001", token)
```

### 锁续期（看门狗）与 fencing token

锁有 TTL，但业务可能跑超时——锁过期后旧持有者仍可能写库。两个兑底手段：

```python
# 看门狗：后台线程按 TTL/3 续期，续期也要校验 token（只续自己的锁）
renew_script = """
if redis.call('GET', KEYS[1]) == ARGV[1] then
    return redis.call('PEXPIRE', KEYS[1], ARGV[2])
else
    return 0
end
"""
# 每隔 expire/3 秒调一次 r.eval(renew_script, 1, lock_key, token, expire_ms)
# 业务结束即停续期；Redisson 的看门狗默认 30s TTL、每 10s 续期
```

- **fencing token**：每次加锁返回一个单调递增版本号，写库时带上该版本，存储层拒绝旧版本的写入——即使锁过期、旧持有者“复活”也写不进去。这是 Redlock 争议的核心兑底。

### Redlock 算法

Redlock 在多个独立 Redis 节点上申请锁，过半成功才认为加锁成功。**关键约束**：必须在锁有效期内、扣除时钟漂移后完成多数派加锁——有效性 = TTL − 加锁耗时 − 时钟漂移，总耗时超预算即视为失败（不能慢慢重试）。

**争议**：
- 实现复杂
- 需要多个独立 Master
- 时钟漂移可能导致问题
- 业界常用单节点 `SET NX EX` + 看门狗续期（如 Redisson）

## 💻 代码示例

完整的缓存+锁方案：

```python
import redis
import time
import random
import uuid

r = redis.Redis(decode_responses=True)

def get_with_cache(key, db_query, ttl=300, attempts=3):
    """带互斥锁的缓存读取（attempts 为抢锁重试上限，防递归加深）"""
    value = r.get(key)
    if value == "EMPTY":
        return None                # 命中空值缓存：直接返回，不查 DB（防穿透）
    if value is not None:
        return value               # 注意别写 if value: —— DB 返回的 0/'' 会被当空值再查一遍

    lock_key = f"lock:{key}"
    token = str(uuid.uuid4())
    lock = r.set(lock_key, token, nx=True, ex=10)

    if lock:
        try:
            value = db_query(key)
            if value is not None:   # 同理：0/'' 是合法缓存值，不能用 truthiness 判空
                expire = ttl + random.randint(0, 60)  # 防雪崩
                r.setex(key, expire, value)
            else:
                r.setex(key, 60, "EMPTY")  # 防穿透
            return value
        finally:
            # Lua 原子释放锁
            r.eval("""
                if redis.call('GET', KEYS[1]) == ARGV[1] then
                    return redis.call('DEL', KEYS[1])
                else
                    return 0
                end
            """, 1, lock_key, token)
    else:
        if attempts <= 0:
            return db_query(key)          # 退避用尽：直查 DB，不再抢锁
        time.sleep(0.1)
        return get_with_cache(key, db_query, ttl, attempts - 1)
```

## ⚠️ 常见陷阱

| 陷阱 | 后果 | 解决方案 |
|------|------|---------|
| SETNX + EXPIRE 分两步 | 可能死锁 | 用一条 `SET NX EX` |
| 锁过期但业务未完成 | 并发问题 | 设置合理过期时间，用看门狗续期 |
| 删除锁不判断 owner | 误删他人锁 | 用唯一 token + Lua 验证 |
| 缓存空值不设置过期 | 内存浪费 | 短过期时间 |
| 雪崩不加随机过期 | 集中过期打 DB | 过期时间加随机值 |

## 🎯 本文学完自检

| 层次 | 检查项 |
|------|--------|
| 🟢 基础 | 给 `db.query` 加计数器：连续两次读同一个不存在的 key，计数器只 `+1`（空值缓存生效），`TTL` 约 60s；再读一个存在的 key，第二次 `GET` 不再触发 DB（计数器不增） |
| 🟡 进阶 | 20 个并发（`seq 20 \| xargs -P20`）同时读同一个已过期的热 key，DB 计数器只为 `+1`（互斥锁生效）；再拿一个错误 token 调释放 Lua，返回 `0` 且 `GET lock:key` 仍有值（不会误删） |
| 🔴 挑战 | 写一段“错误版”复现误删：锁 `ex=1`、业务 `sleep 2`，B 抢到锁后 A 的 `finally` 把 B 的锁删掉（B 的 `GET lock:key` 变空）；换成本篇 token+Lua 版重跑同样时序，证明不再发生，并把“A 过期 → B 持锁 → A 释放 → 并发重建”写成 3 行时序说明 |
