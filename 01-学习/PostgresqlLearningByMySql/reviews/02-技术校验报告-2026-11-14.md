## P0 问题（照抄必翻车 / 概念教错）

### T-P0-01 v0 与 v5：按 `NOW()` 造 100 万行日志，但分区只建到 2026-08

- **文件/位置**：`v0-数据库初始化.md` L354-361；`v5-存储过程与触发器迁移.md` L200-209
- **原文**：
  > `INSERT INTO server_logs (log_time, …) SELECT NOW() - (n / 100000.0) * INTERVAL '30 days', … FROM generate_series(1, 1000000) AS n;`
  > 分区：`FOR VALUES FROM ('2026-07-01') TO ('2026-08-01')` / `('2026-08-01') TO ('2026-09-01')`
- **问题**：插入值域是"当前时刻往前 30 天"，而分区只有 2026-07、2026-08 两个。任何在 2026-09 之后执行的环境（含今天 2026-11-14）都会命中 `ERROR: no partition of relation "server_logs" found for row`。v0 是全部 v1-v7 的基座，这条一挂，后续全断。v5 同样一段 `NOW() - n minutes` 也是必挂。
- **修复建议**：分区改为动态生成（`now()` 所在月 ±1），或把插入值改成落在 2026-07/08 的固定基准：`TIMESTAMPTZ '2026-07-01' + (n || ' seconds')::interval`。最小改动：在 v0/v5 的分区列表后面补一句「若当前日期不在 2026-07/08，请把分区边界与插入基准一起平移」并给出 `DO $$ … EXECUTE format('CREATE TABLE … FOR VALUES FROM (%L) TO (%L)', …)` 的模板。
- **验证方式**：官方文档 PG 16 §5.11.2.2「Inserting data into a partitioned table… if no partition matches, an error is raised」+ 日期算术推理（`NOW()` 在 2026-11 → 值域 2026-10-15~11-14，落在两个分区外）。**未实跑**（本机无 psql）。

### T-P0-02 v3：`(RANDOM()*4)::INT + 1` 会取到 5，5 万行必然违反外键

- **文件/位置**：`v3-查询与索引优化.md` L54-59
- **原文**：
  > `SELECT (RANDOM() * 4)::INT + 1,  -- 1~4；(RANDOM()*4+1)::INT 会四舍五入出 5，违反外键`
- **问题**：注释诊断对了、修复却错了。PostgreSQL 的 `double precision → integer` 转换是**四舍五入**（`1.5::int=2`、`3.7::int=4`），`random()*4 ∈ [0,4)`，其中 `[3.5,4)` 占 12.5% 会转成 4，`+1` 得 5。users 只有 id 1-4，5 万行插入几乎 100% 撞 `orders_user_id_fkey`。
- **修复建议**：`1 + floor(random() * 4)::int`（或 `(random()*3)::int + 1` 也有 1/3 概率得 1~4 但分布不均，推荐 floor 版）。
- **验证方式**：PG 官方文档 §9.8/§10.4 浮点转整数为 round-to-nearest（另：`SELECT 2.5::int` 得 2，银行家舍入）+ 概率计算 12.5%×50000。**未实跑**。

### T-P0-03 v7：`citus_add_node('worker_1', 5433)` 端口写的是宿主机映射端口

- **文件/位置**：`v7-Citus分布式扩展.md` L92-93（配合 L44-82 的 compose）
- **原文**：
  > `SELECT citus_add_node('worker_1', 5433);` / `SELECT citus_add_node('worker_2', 5434);`
  > compose：`worker_1: ports: ["5433:5432"]`
- **问题**：coordinator 容器内用服务名 `worker_1` 直连，走的是容器网络，worker 监听的是 **5432**；5433 只是宿主机侧映射，容器内没人监听。结果：节点注册成功但 `isactive=false`，`citus_get_active_worker_nodes()` 返回 0 行，后续 `create_distributed_table` 全部失败。
- **修复建议**：`citus_add_node('worker_1', 5432)`、`citus_add_node('worker_2', 5432)`；若坚持用映射端口，节点名要写 `host.docker.internal` 而不是服务名，且两条路只能选一条。同时在验收里加 `SELECT nodename, nodeport, isactive FROM pg_dist_node;` 要求 isactive=t。
- **验证方式**：Citus 官方 UDF 文档 `citus_add_node(node_name, node_port)` — "node_port: the port on which PostgreSQL is listening on the worker node"（https://docs.citusdata.com/en/stable/develop/api_udf.html）+ docker 网络端口语义推理。**未起容器**。

### T-P0-04 v7：三处从 `pg_dist_placement` 取 nodename/nodeport，列不存在

- **文件/位置**：`v7` L303-307（任务 4.1）、L317-319（任务 4.2）、L356-361（任务 5.1）
- **原文**：
  > `SELECT s.shardid, p.placementid, p.nodename, p.nodeport, … FROM pg_dist_shard s JOIN pg_dist_placement p ON p.shardid = s.shardid`
  > `SELECT nodename, nodeport, COUNT(*) FROM pg_dist_placement GROUP BY nodename, nodeport;`
- **问题**：`pg_dist_placement` 的真实列是 `placementid | shardid | shardstate | shardlength | groupid`——**没有 nodename/nodeport**（Citus 7.0 起 `pg_dist_shard_placement` 已废弃，节点信息搬到 `pg_dist_node`）。三处都会报 `column p.nodename does not exist`，任务 4 与任务 5 的健康检查直接跑不动。这正是"v7 几乎每个任务跑不通"的历史残留。
- **修复建议**：统一 JOIN `pg_dist_node n ON n.groupid = p.groupid AND n.noderole='primary'` 再取 `n.nodename, n.nodeport`；或直接查 `citus_shards` 视图（它已含 nodename/nodeport/shard_size，10 篇的写法就是对的）。
- **验证方式**：Citus 官方元数据文档给出 `SELECT * from pg_dist_placement;` 的输出与列定义（https://docs.citusdata.com/en/v11.0/develop/api_metadata.html）：`placementid | shardid | shardstate | shardlength | groupid`。已核实。

### T-P0-05 v7：为了满足分布键，把 `order_items` 去重成"一单一明细"

- **文件/位置**：`v7` L139-144
- **原文**：
  > `DELETE FROM order_items a USING order_items b WHERE a.order_id = b.order_id AND a.id > b.id;`
  > `ALTER TABLE order_items ADD PRIMARY KEY (user_id, order_id);`
- **问题**：订单明细表天然是"一单多行"；`PRIMARY KEY (user_id, order_id)` 强制一单只剩一行，于是前面必须删掉 20 万行里的绝大部分。这不是迁移，是把业务模型改坏（后续 `quantity/unit_price` 只能记一个商品）。Citus 的硬约束只是"主键/唯一约束必须包含分布列"，用 `(user_id, id)` 即可满足，完全不必牺牲语义。
- **修复建议**：`ALTER TABLE order_items ADD PRIMARY KEY (user_id, id);`（id 已是 identity 唯一），外键改 `FOREIGN KEY (user_id, order_id) REFERENCES orders(user_id, id)`；删除 L139-142 的去重语句。若担心 `(user_id, order_id)` 组合唯一性，另建普通索引即可。
- **验证方式**：Citus 文档"distribution column must be included in primary key/unique constraints"（api_metadata / create_distributed_table 说明）+ 关系建模推理。已核实约束口径，建模结论为推理。

### T-P0-06 02：`ROW(...)` 直接插入复合类型列，缺显式 cast

- **文件/位置**：`02-数据类型与DDL对比.md` L512-513
- **原文**：
  > `INSERT INTO companies (name, address) VALUES ('Acme', ROW('123 Main St', 'Springfield', '62701'));`
- **问题**：`ROW(...)` 产生的是**匿名 record**，赋给 `address_type` 列会报 `column "address" is of type address_type but expression is of type record`（HINT: 需要 rewrite 或 cast）。必须 `ROW(...)::address_type`。
- **修复建议**：`VALUES ('Acme', ROW('123 Main St','Springfield','62701')::address_type);`，并在正文点明"复合类型列必须显式 cast，或写成 `('123 Main St','Springfield','62701')` 的字面量形式"。
- **验证方式**：PG 官方文档 §4.2.13「By default, the value created by a ROW expression is of an anonymous record type. If necessary, it can be cast to a named composite type」（https://www.postgresql.org/docs/current/sql-expressions.html）+ 同款报错复现记录（DoltHub 博客给出 `ERROR: ASSIGNMENT_CAST: target is of type t1 but expression is of type record`）。已核实。

### T-P0-07 08 / 99-二 / v4：`consume_tasks` 的 OUT 参数名与列名撞车，运行即报 ambiguous

- **文件/位置**：`08` L432-447；`99-第二周复习检查点.md` L181-191；`v4` L169-186
- **原文**（三处同构）：
  > `RETURNS TABLE (id INTEGER, task_type TEXT, payload JSONB) AS $$ … UPDATE task_queue … WHERE id IN (SELECT id FROM task_queue WHERE status='pending' … FOR UPDATE SKIP LOCKED)`
- **问题**：`RETURNS TABLE` 的列是 OUT 参数（PL/pgSQL 变量）。函数体里 `SELECT id FROM task_queue` 的 `id` 同时匹配"OUT 变量 id"与"列 task_queue.id"，而 `plpgsql.variable_conflict` 出厂值是 `error`，于是运行期直接 `ERROR: column reference "id" is ambiguous`。三个文件都在教同一个跑不通的队列函数。
- **修复建议**：给表起别名并限定列（`SELECT q.id FROM task_queue q …`），或把 OUT 参数改名（`out_id`/`task_id`），或在函数首行加 `#variable_conflict use_column`。推荐第一种（最直观）。
- **验证方式**：PG 官方文档 §43.11.1「plpgsql.variable_conflict … where error is the factory default」（https://www.postgresql.org/docs/16/plpgsql-implementation.html，已抓取原文）。**未实跑**。

### T-P0-08 03：用 `SELECT (xmax=0)` 判断"这次是插入还是更新"——永远返回 true

- **文件/位置**：`03-SQL查询语法差异与进阶.md` L901（练习 5 自测方法）
- **原文**：
  > `SELECT (xmax=0) FROM product_stock` 首次 true 重复 false
- **问题**：`xmax` 技巧只在 `INSERT … ON CONFLICT … RETURNING` 的返回行上成立（更新走的行其 xmax 是当前事务）。对表做普通 `SELECT`，返回的是**当前可见版本**，其 `xmax` 恒为 0（未删除），所以永远 true。照这个自测做，学生会得出"第二次也是插入"的错误结论——典型"能跑但结果错"。
- **修复建议**：改为 `INSERT … ON CONFLICT … DO UPDATE … RETURNING (xmax = 0) AS is_insert;` 并在同一语句里读结果；或改用 `RETURNING id, (SELECT count(*) FROM product_stock) …` 之类可判定的写法。自测项改成"连续执行两次同一 INSERT…RETURNING，第一次 is_insert=t、第二次 f"。
- **验证方式**：PG 系统列语义（`xmax` = 删除/锁定该行版本的事务 ID；可见版本未删除则为 0）+ 03 自身 L579 的正确用法对比。推理，未实跑。

### T-P0-09 04：`Index Only Scan … Heap Fetches = 0` 的验收在未 VACUUM 时必然失败

- **文件/位置**：`04-索引与查询优化.md` L730-734（练习 5）
- **原文**：
  > **预期输出**：普通索引显示 `Index Scan`（需回表，Heap Fetches > 0）；覆盖索引显示 `Index Only Scan`（无回表，Heap Fetches = 0）
- **问题**：两处错。① `Index Scan` 根本不输出 `Heap Fetches` 字段（该字段只属于 Index Only Scan），无法"对比 >0"。② Index Only Scan 依赖 visibility map；练习 5 刚 `INSERT 100000` 行且没 VACUUM，页未置 all-visible，`Heap Fetches` 会接近 10 万而不是 0。学生按验收做，100% 判失败。
- **修复建议**：验收前加 `VACUUM (ANALYZE) events_covering;`，并把判据改为"覆盖索引计划为 Index Only Scan 且 Heap Fetches 显著小于返回行数（VACUUM 后应为 0）"；删掉"普通索引 Heap Fetches > 0"这句。
- **验证方式**：PG 官方文档 §11.9「Index-Only Scans… requires that the visibility map bit be set… VACUUM sets it」+ EXPLAIN 输出字段定义。已核实。

### T-P0-11 v0：在 `learn_pg` 里 `CREATE EXTENSION pg_cron` 会报错

- **文件/位置**：`v0` L56（要求装进 learn_pg）、L68（`CREATE EXTENSION IF NOT EXISTS pg_cron;`）
- **原文**：
  > 「先 `CREATE DATABASE learn_pg`，再 `\c learn_pg`…然后回到本节执行 CREATE EXTENSION」
  > `CREATE EXTENSION IF NOT EXISTS pg_cron;             -- 定时任务`
- **问题**：pg_cron 每集群只能装在一个库，默认 `cron.database_name = postgres`；在 learn_pg 里创建会报 `ERROR: can only create extension in database postgres / DETAIL: Jobs must be scheduled from the database configured in cron.database_name`。v0 的"先建库再装扩展"指引恰好把它引到坑里。
- **修复建议**：pg_cron 单独成段："在 `postgres` 库执行 `CREATE EXTENSION pg_cron;`，其他库用 `cron.schedule_in_database(..., 'learn_pg')` 投递"；或直接 `ALTER SYSTEM SET cron.database_name='learn_pg'` 后重启。其余扩展（pg_trgm/pgcrypto/citext/btree_gist）留在 learn_pg 没问题。
- **验证方式**：pg_cron 官方 issue #427 与多份部署记录的原文报错（`can only create extension in database …`，HINT: Add cron.database_name = '…'）。已核实。

### T-P0-12 v6：`DROP SCHEMA repack CASCADE` 会连 pg_repack 扩展对象一起删掉

- **文件/位置**：`v6-pg_repack在线表重组.md` L287-288、L300-302
- **原文**：
  > `-- 清理残留（安全操作，不影响原表数据；删除 repack schema 会级联清掉影子表和触发器）`
  > `-- DROP SCHEMA IF EXISTS repack CASCADE;`
- **问题**：pg_repack 的扩展对象（`repack.version()`、`repack.repack_trigger()` 等）就装在 `repack` schema 里；`DROP SCHEMA repack CASCADE` 把这些函数一起删掉，扩展处于"已安装但对象缺失"的坏状态，下次 `pg_repack` 直接失败。这不是"安全操作"。
- **修复建议**：只删残留影子表/触发器：`DROP TABLE IF EXISTS repack.table_<oid> CASCADE;` + `DROP TRIGGER IF EXISTS z_repack_trigger ON <原表>;`；若要彻底重来，`DROP EXTENSION pg_repack; CREATE EXTENSION pg_repack;`。
- **验证方式**：v6 L274 与 10 L96 都写明"pg_repack 在独立的 repack schema 中工作"，扩展对象即在该 schema；推理 + 扩展 schema 归属事实。**未实跑**。

### T-P0-13 RLS 教学闭环失效：owner 绕过 + v0 主动给应用角色 BYPASSRLS

- **文件/位置**：`08` L357-365；`09` Q16 L262-267、Q22 L391-403；`v0` L434-442
- **原文**：
  > 08：「`ALTER TABLE orders ENABLE ROW LEVEL SECURITY;` … `SELECT * FROM orders;  -- 只返回 user_id = 42 的订单」`
  > v0：「`ALTER ROLE app_user BYPASSRLS;`（授予后 app_user 将不再受上面 orders_isolation 策略的限制）」
- **问题**：① 表**owner**（以及 superuser / BYPASSRLS 角色）默认绕过 RLS，除非 `ALTER TABLE … FORCE ROW LEVEL SECURITY`。v0 的表都是 postgres 建的，学生用 postgres 执行"验证"会看到全部 100000 行，与注释"只返回 42"矛盾。② v0 又把 `app_user`（正是演示用的应用角色）设成 BYPASSRLS，等于把要演示的隔离关掉。③ `current_setting('app.current_user_id')` 在未设置时直接报错，不是返回空集。
- **修复建议**：加 `ALTER TABLE orders FORCE ROW LEVEL SECURITY;`；用非 owner 角色（`SET ROLE app_user`，且不加 BYPASSRLS）演示；策略条件改 `current_setting('app.current_user_id', true)::bigint` 并配 `NULLIF`；把 v0 的 `ALTER ROLE app_user BYPASSRLS` 改成注释掉的"DBA 排障时才用，勿给应用角色"。
- **验证方式**：PG 官方文档 CREATE POLICY / RLS 章节「Table owners normally bypass row security… FORCE ROW LEVEL SECURITY」+ `current_setting(text, missing_ok)` 语义。已核实。

### T-P0-14 08：没有任何唯一约束却用 `ON CONFLICT DO NOTHING` 声称"幂等入队"

- **文件/位置**：`08` L462-465（场景 7）
- **原文**：
  > `-- UPSERT 幂等入队` / `INSERT INTO task_queue (task_type, payload) VALUES ('email_send', '{"to": "alice@test.com"}') ON CONFLICT DO NOTHING;`
- **问题**：`task_queue` 只有 `id SERIAL PRIMARY KEY`，`payload` 无唯一索引。`ON CONFLICT DO NOTHING`（无冲突目标）在任何冲突时都不插入，但这里**永远不会有冲突**——每执行一次就多一行，所谓"幂等"完全不成立。v0 L280 反而把这件事写对了（"其余表没有业务唯一约束，ON CONFLICT DO NOTHING 并不会去重"），两篇互相打脸。
- **修复建议**：给幂等键建唯一索引（如 `CREATE UNIQUE INDEX ON task_queue ((payload->>'to'), task_type) WHERE status='pending';`）后 `ON CONFLICT ((payload->>'to'), task_type) DO NOTHING`；或老实改成"每次插入新任务，去重由应用层负责"。
- **验证方式**：PG 文档 INSERT … ON CONFLICT 语义（无冲突目标时只在**存在**冲突时跳过）+ 08 表定义无唯一约束。已核实。

### T-P0-15 02：教了 MySQL 不存在的 `DEFAULT UUID()` 语法

- **文件/位置**：`02` L643-644
- **原文**：
  > `-- MySQL: DEFAULT UUID()`
  > `-- PostgreSQL 13+: DEFAULT gen_random_uuid()`
- **问题**：MySQL 8.0.13+ 才支持表达式默认值，且**必须加括号**：`DEFAULT (UUID())`。裸写 `DEFAULT UUID()` 是语法错误。这条会直接污染迁移脚本。
- **修复建议**：改为 `-- MySQL 8.0.13+: uuid CHAR(36) DEFAULT (UUID())`；并补一句 8.0.13 以下只能用触发器。
- **验证方式**：MySQL 8.0 官方手册 §13.6 Data Type Default Values「enclose expression default values within parentheses … `b BINARY(16) DEFAULT (UUID_TO_BIN(UUID()))`」（https://dev.mysql.com/doc/refman/8.0/en/data-type-defaults.html）。已核实。
