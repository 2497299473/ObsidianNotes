## 毕业项目 v3：查询与索引优化

**改造维度**：查询改写 + 索引策略
**MySQL 锚点**：BTREE → B-tree/GIN/BRIN + EXPLAIN ANALYZE
**验收标准**：EXPLAIN 达到预期扫描路径 + 查询性能提升

### 目标

在 v2 的表结构上，设计合理的索引策略，用 EXPLAIN ANALYZE 验证查询计划，并改写 MySQL 风格查询为 PG 风格。

### 任务清单

- [ ] 创建复合索引、部分索引、覆盖索引
- [ ] 用 EXPLAIN ANALYZE 分析查询计划
- [ ] 用窗口函数做排名和累计分析
- [ ] 用递归 CTE 查询分类层级
- [ ] 用 DISTINCT ON 取每组第一名
- [ ] 用游标分页优化深分页

### 完整代码

```sql
\c graduation_db

-- ============================================
-- Step 1：插入更多测试数据
-- ============================================
INSERT INTO products (name, specs, price, stock, status, tags)
SELECT 'Product_' || n,
    jsonb_build_object('brand', CASE WHEN n%2=0 THEN 'Apple' ELSE 'Samsung' END),
    (RANDOM() * 5000 + 100)::NUMERIC(10,2),
    (RANDOM() * 100)::INT,
    CASE WHEN n%3=0 THEN 'draft' ELSE 'published' END,
    ARRAY['phone']
FROM generate_series(1, 10000) AS n;

INSERT INTO orders (user_id, status, total_amount, created_at)
SELECT (RANDOM() * 4)::INT + 1,  -- 1~4；(RANDOM()*4+1)::INT 会四舍五入出 5，违反外键
    CASE WHEN n%2=0 THEN 'paid' ELSE 'pending' END,
    (RANDOM() * 1000)::NUMERIC(10,2),
    NOW() - (n || ' hours')::INTERVAL
FROM generate_series(1, 50000) AS n;

-- ============================================
-- Step 2：索引设计
-- ============================================
-- 复合索引：用户订单按时间倒序
CREATE INDEX idx_orders_user_created ON orders (user_id, created_at DESC);

-- 部分索引：只索引待处理订单（省空间）
CREATE INDEX idx_orders_pending ON orders (created_at) WHERE status = 'pending';

-- 覆盖索引：包含 amount 避免回表
CREATE INDEX idx_orders_user_covering ON orders (user_id) INCLUDE (total_amount, status);

-- ============================================
-- Step 3：EXPLAIN ANALYZE 对比
-- ============================================
-- 无索引时的全表扫描
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders WHERE status = 'pending' AND created_at >= NOW() - INTERVAL '7 days';
-- 观察是否有 Index Scan 或 Bitmap Heap Scan

-- 对比索引大小
SELECT pg_size_pretty(pg_relation_size('idx_orders_pending')) AS partial_size,
       pg_size_pretty(pg_relation_size('idx_orders_user_created')) AS composite_size;

-- ============================================
-- Step 4：窗口函数分析
-- ============================================
-- 每个用户订单金额排名
SELECT user_id, total_amount,
    RANK() OVER (PARTITION BY user_id ORDER BY total_amount DESC) AS rank_val,
    SUM(total_amount) OVER (PARTITION BY user_id) AS user_total
FROM orders
WHERE status = 'paid'
ORDER BY user_id, rank_val
LIMIT 20;

-- 累计销售额
SELECT DATE_TRUNC('day', created_at) AS day,
    COUNT(*) AS order_count,
    SUM(total_amount) AS daily_total,
    SUM(SUM(total_amount)) OVER (ORDER BY DATE_TRUNC('day', created_at)) AS cum_total
FROM orders
WHERE created_at >= NOW() - INTERVAL '7 days'
GROUP BY DATE_TRUNC('day', created_at)
ORDER BY day;

-- ============================================
-- Step 5：递归 CTE（分类层级）
-- ============================================
CREATE TABLE categories (
    id SERIAL PRIMARY KEY,
    name VARCHAR(50),
    parent_id INT REFERENCES categories(id)
);

INSERT INTO categories (name, parent_id) VALUES
('电子产品', NULL),
('手机', 1), ('电脑', 1),
('iPhone', 2), ('Android', 2), ('笔记本', 3), ('台式机', 3);

WITH RECURSIVE category_tree AS (
    SELECT id, name, parent_id, 0 AS depth, name::text AS path
    FROM categories WHERE parent_id IS NULL
    UNION ALL
    SELECT c.id, c.name, c.parent_id, ct.depth + 1,
           ct.path || ' > ' || c.name
    FROM categories c JOIN category_tree ct ON c.parent_id = ct.id
)
SELECT depth, path FROM category_tree ORDER BY path;

-- ============================================
-- Step 6：DISTINCT ON（每组取第一行）
-- ============================================
-- 每个用户金额最高的订单
SELECT DISTINCT ON (user_id) user_id, total_amount, status, created_at
FROM orders
ORDER BY user_id, total_amount DESC;

-- ============================================
-- Step 7：游标分页（深分页优化）
-- ============================================
-- 第一页
SELECT id, total_amount, created_at
FROM orders
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 第二页（用上一页最后一条的值）
SELECT id, total_amount, created_at
FROM orders
WHERE (created_at, id) < ('2026-07-24 00:00:00+08', 50000)
ORDER BY created_at DESC, id DESC
LIMIT 20;

-- 对比 OFFSET 深分页性能
EXPLAIN (ANALYZE)
SELECT * FROM orders ORDER BY created_at DESC LIMIT 20 OFFSET 49980;
-- vs
EXPLAIN (ANALYZE)
SELECT * FROM orders
WHERE (created_at, id) < ('2026-07-24 00:00:00+08', 50000)
ORDER BY created_at DESC, id DESC LIMIT 20;

-- ============================================
-- Step 8：FILTER 条件聚合
-- ============================================
SELECT user_id,
    COUNT(*) AS total,
    COUNT(*) FILTER (WHERE status = 'paid') AS paid_count,
    COUNT(*) FILTER (WHERE status = 'pending') AS pending_count,
    SUM(total_amount) FILTER (WHERE status = 'paid') AS paid_revenue
FROM orders
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY user_id
ORDER BY paid_revenue DESC NULLS LAST
LIMIT 10;
```

### 验收标准

- [ ] EXPLAIN ANALYZE 输出中能看到 Index Scan 或 Bitmap Heap Scan（非 Seq Scan）
- [ ] 部分索引比复合索引体积更小
- [ ] 覆盖索引查询显示 Index Only Scan（无需回表）
- [ ] 窗口函数排名和累计计算正确
- [ ] 递归 CTE 能输出完整的分类层级路径
- [ ] 游标分页性能明显优于 OFFSET 深分页
