### P1-1 09/10/11/12 的 12 个练习没有参考答案、没有通过判据

- **位置**：`09-Go标准库实战-Python对照.md` L362-374；`10-...性能调优.md` L291-303；`11-...泛型.md` L271-283；`12-...FFI.md` L311-323
- **原文**（09 L366）：「将以下 Flask API 迁移为 Go net/http 服务，包含 GET/POST 和错误处理。在注释中标注每个 Flask 概念对应的 Go 概念。」
- **问题**：只有任务描述，没有 ① 参考实现、② 期望输出、③ 判定标准（编译通过？哪种请求返回哪种状态码？）。学习者无法判断"我写的是不是对的"，只能自我感觉；对"要能熟练运用"的目标来说，这类练习等于阅读材料。
- **修复建议**（每条练习补三行即可，成本很低）：
  - **09 练习1**：给出 3 条 `curl` 断言——`GET /api/users` 返回 `200` 且 body 含 `"users"`；`POST` 带 `{"a":1}` 返回 `201` 且 body 为 `{"created":{"a":1}}`；`PUT` 返回 `405`。附 12 行参考实现。
  - **09 练习2**：判据"3 个 URL 全部超时（5s）时 `g.Wait()` 返回 `context.DeadlineExceeded`，且总耗时 < 6s"。
  - **09 练习3**：判据"写→读回后 `reflect.DeepEqual` 为 true；文件首字节为 `[`"。
  - **10 练习1/2/3**：判据统一为"`go test -bench` 输出中 `allocs/op` 与 `B/op` 的具体阈值"（如预分配版 `allocs/op == 1`）。
  - **11 练习1/2/3**：判据"`Map([]int{1,2,3}, ...)` 编译通过且返回 `[]string`；`Set[MyString]` 因缺 `~` 编译失败（用于讲清类型集）"。
  - **12 练习1/2/3**：见 P1-3（先解决依赖前置）。
- **验证方式与结果**：逐篇核对练习小节；脚本统计 09/10/11/12 四篇「## 🎯 练习」段内 `输出|期望|want|判据` 出现次数 → **均为 0**；段长分别为 393/311/333/337 字符，确认只有任务描述。

### P1-2 05 练习3 的"应该超时"注释与实际行为不符（共享 1s context）

- **位置**：`05-并发编程-Goroutine与Channel.md` L712-736
- **原文**：「// 任务 1：0.5 秒，应该成功」/「// 任务 2：2 秒，应该超时」
- **问题**：`ctx` 在任务 1 之前创建（1s 超时），任务 1 消耗 0.5s 后，任务 2 只剩约 0.5s 预算——它不是"因为 2s > 1s 而超时"，而是"因为预算被前一个任务吃掉"才超时。结论虽仍是"失败"，但归因错了，学习者会以为"每个任务各有 1s"。
- **修复建议**：每次任务单独 `context.WithTimeout(context.Background(), 1*time.Second)`；或把注释改为"共享 1s 总预算：任务1 用掉 0.5s，任务2 只剩 0.5s → 超时"。
- **验证方式与结果**：读代码路径（`ctx` 在 `main` 创建一次、两次 `runWithTimeout` 复用）+ 逻辑推演（0.5s + 2s > 1s）；未实跑（示例含 `time.Sleep`，跑通也需 2s，结论可静态确定）。

### P1-3 12 篇的 3 个练习在本机（无 gcc / 无 Docker）全部做不了，且未写前置条件

- **位置**：`12-Go与Python FFI互调.md` L311-323
- **原文**：「编写一个 Go 函数做数组排序，编译为 `.so`，用 Python ctypes 调用。」/「编写一个简单的 gRPC 服务（Go 服务端 + Python 客户端）」
- **问题**：练习 1 需要 cgo（`-buildmode=c-shared` 强制 CGO_ENABLED=1 → 需 gcc），练习 3 需要 protoc + grpc 代码生成；本机实测 `go test -race` 就因 `cgo: C compiler "gcc" not found` 失败，说明这条路径在默认 Windows 环境下**根本走不通**。正文没有"前置条件：安装 MinGW-w64 / TDM-GCC，或改用 WSL"的提示。
- **修复建议**：在每个练习前加"前置检查"块（`go env CGO_ENABLED`、`gcc --version`、`protoc --version`），并给一条"没有 gcc 也能做的替代练习"（如用 `go run` + stdin/stdout 完成练习 2，再用 `benchstat` 对比 Python 侧耗时）。
- **验证方式与结果**：本机 `CGO_ENABLED=1 go test -race` → `# runtime/cgo / cgo: C compiler "gcc" not found`；`Get-Command gcc` 无结果；`Get-Command docker` 无结果。

## 4. 毕业项目进度感

**做得好的**：
- 每版只改一个维度（语法 → struct → 接口/错误 → 并发 → 测试/部署 → 容器），"改造要点"表把 vN-1 → vN 的差异列成 4 行，推进感清晰。
- v1 给了最硬的验收判据：「输出与 Python 版本一致」（唯一一版明确对照两侧输出的）。
- v4 给了可验证的判据：「v4 总耗时 ≈ 最长任务耗时」（`go run` 实测 6.0s ≈ 最长任务 5s + 调度，成立）。

**缺口**：
### P2-1 除 v1/v4 外，其余版本没有"做对了"的判据
- **位置**：`v2-...版.md` L166-172、`v3-...版.md` L238-244、`v5-...版.md` L349-355、`v6-...版.md` L236-242
- **问题**：自检项是"能用 struct 替代 dict""能解释多阶段构建"这类**能力描述**，不是**产物判据**。学员不知道"我的 v2 算不算完成"。
- **修复建议**：每版补一行"验收命令 + 期望输出"，例如：
  - v2：`go run . | tail -1` 应为 `=== 完成: 3/4 成功 ===` 之类（成功率随机，改为"输出含 4 行 `[hh:mm:ss] ✅/❌` + 1 行统计"）。
  - v3：至少出现 1 行 `[ERROR]`（把某个任务成功率设 0.0 保证必失败）——现文档用 0.5 是随机的，跑不出失败也无法验证错误分支。
  - v5：`go test ./... -cover` → `ok ... coverage: 87.2%`（实测值，可直接写死为"≥ 80%"）。
  - v6：`docker images scheduler` 的 SIZE ≤ 20MB。
- **验证方式与结果**：读四篇自检表（均为"能…"句式，无命令/无数字）；v5 的 87.2% 为本机实跑值，可直接作为基线。

### P2-2 v3 的错误分支不可稳定复现（成功率随机）
- **位置**：`v3-...版.md` L212-215
- **原文**：「scheduler.AddTask(NewTask("生成报告", 3, 0.5))  // 低成功率」
- **问题**：`rand.Float64() < 0.5` 每次运行结果不同，`errors.Is` 分支可能一次都不触发，学员无法确认自己写对了错误处理。
- **修复建议**：加一个 `successRate: 0.0` 的任务（必然失败）用于演示，或给 `Task` 注入可固定的 `rand.Source`（`rand.New(rand.NewSource(1))`）。
- **验证方式与结果**：读 `go\v3\main.go`（`rand.Float64()` 无种子注入，Go 1.20+ 全局源自动随机）→ 分支命中率 50%/次。

### P2-3 v5→v6 没有"从批处理到服务"的过渡
- **位置**：`v5` 末 L359-379（"迁移完成！"）→ `v6` L19-40（直接进 Docker）
- **问题**：v5 的产物是"跑完就退出的 CLI"，v6 却按"常驻服务"部署（`EXPOSE 8080`、探针、`replicas: 3`）。学员在这里会失去连续性："我上一版的程序怎么突然要监听端口了？"（技术侧同源问题见技术报告 P0-2）。
- **修复建议**：在 v6 开头加一步"服务化改造"（+30 行：`/health` + `/run` + `http.Server` + 优雅退出），把它作为 v6 的第一个"改造要点"，再进容器。
- **验证方式与结果**：读 `go\v5\main.go`（78 行，无 `net/http`，`main` 结束即退出）与 v6 清单（`containerPort: 8080` + `/health`）对照。
