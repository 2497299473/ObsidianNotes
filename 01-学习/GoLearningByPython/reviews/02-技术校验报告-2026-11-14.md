### P1-1 v6 Dockerfile `COPY go.mod go.sum ./`：本项目没有 `go.sum`，构建第一层就失败

- **位置**：`v6-Docker部署版.md` L52-53
- **原文**：「COPY go.mod go.sum ./ / RUN go mod download」
- **问题**：`go\v5\go.mod` 只有 `module` + `go 1.22` 两行，没有任何 `require`，因此**没有 `go.sum` 文件**（已实查目录）。`COPY` 遇到不存在的源文件会直接报 `failed to compute cache key: ... go.sum: not found`，`docker build` 在第一阶段就中断。这是 08-23 修 Dockerfile 时的残留。

- **验证方式与结果**：`Get-ChildItem -Recurse go\v5` 无 `go.sum`；`go mod tidy` 不生成 go.sum（无 require）；Docker 语义按官方文档 `COPY` 源不存在即失败（**未实跑 docker**：本机无 Docker，标注为推理+文件事实）。

### P1-2 07 场景 02 用 `filepath.SkipDir` 当"提前退出"，实际 `-n` 限制失效（静默多输出）—— ✅ **审查期间已改为 `errStop` 哨兵（12:20），留档**

- **位置**：`07-业务场景实战合集.md` L207-219（11:45 快照）
- **原文（旧版）**：
  ```go
  if count >= *limit {
      return filepath.SkipDir  // 提前退出
  }
  ```
- **问题**：回调是在**文件**（非目录）上返回 `filepath.SkipDir`，按 `path/filepath` 文档语义它只会"跳过当前目录剩余文件"，**不会终止整个 Walk**；Walk 继续进入下一个目录，`count` 继续增长。`-n 10` 会输出远超 10 个文件。
- **修复建议**：改用哨兵错误提前终止：`var errStop = errors.New("stop")`，回调 `return errStop`，Walk 外层 `if errors.Is(err, errStop) { err = nil }`；或改用 `filepath.WalkDir` + `fs.SkipAll`（Go 1.20+）。注释不要写"提前退出"。
- **验证方式与结果**：
  - 旧版实证：构造 `root/a/{f0,f1,f2}.go`、`root/b/{f0,f1,f2}.go`，`limit=2` 时按文档写法运行 → `visited f0 count=1 / f1 count=2 / f0 count=3`，`Walk 结束: err=<nil>, 总共访问 3 个（应为 2）`。
  - **12:20 复查**：现存版本已改为 `return errStop` + `errors.Is(err, errStop)` 判断（`errStop` 出现 3 次、原 `SkipDir` 仅在解释性注释中保留），重新 `go vet` → `rc=0`。修复方向与本报告一致。

### P1-3 07 场景 06 忽略 `os.Open` 错误：文件不存在时"静默 0 行 + 退出码 0"（最危险的一类）—— ✅ **审查期间已修复（12:20），留档**

- **位置**：`07-业务场景实战合集.md` L477-497（11:45 快照）
- **原文（旧版）**：
  ```go
  f, _ := os.Open("data.csv")
  defer f.Close()
  ```
- **问题**：`data.csv` 不存在时 `f == nil`，`csv.NewReader(nil).ReadAll()` 返回 `ErrInvalid`（被 `_` 丢掉），循环 0 次，程序**正常退出**，既没有 "no such file" 也没有非零退出码。这是"能跑但结果错"的教科书案例：CI 里静默通过、线上静默产出空结果。同一块 `writer.Write(...)`、`records, _` 也都丢了错误。

### P1-4 13 篇 §2 的 Go JSON 数字物理上不可能，由此得出的 "15.5x" 不成立

- **位置**：`13-Python vs Go Benchmark实测.md` L143-151
- **原文**：
  - L147：「| 1000 次序列化耗时 | 4.82s | **0.31s** | **15.5x** |」
  - L151：「Go 的 struct 字段标签在编译时解析，运行时零开销。」
- **问题**：
  1. 10000 条记录（输出约 512KB）单次 `json.Marshal` 若只需 0.31ms，等于 **1.6 GB/s** 的 JSON 编码吞吐；`encoding/json` 基于反射 + 缓存类型信息，业界实测约 100-200MB/s。本机实测 **3.66ms/次**（1000 次 3.66s），比文档慢 12 倍。
  2. 比值随之崩塌：本机 Python 11.61s / Go 3.66s ≈ **3.2x**，不是 15.5x（即便用文档自己的 Python 4.82s 去除以真实 3.66s，也只有 1.3x）。
  3. 归因也错：struct tag 是**运行时**由 `reflect` 读取并缓存在类型信息里的，不是"编译时解析"。
- **修复建议**：用本机重跑并写实测（建议同时给 `go test -bench` 的 `ns/op`/`B/op`），结论改为"约 3 倍，主要省在解释执行开销"；删掉"编译时解析/零开销"，改为"tag 在运行时解析一次并缓存（`reflect`），热路径无重复解析"。
- **验证方式与结果**：`bench_go\main.go`（与文档同代码）→ `Go json.Marshal x1000: 3.656s (单次 3.66ms)`；Python 同代码 → `json.dumps x1000: 11.61s (单次 10.33ms, 512780 bytes)`。机器为 Ryzen 7 5800H（文档为 i7-12700H，同代同档）。

### P1-5 13 篇 §1 把 FastAPI 的 `def` 端点说成"asyncio 事件循环（单线程）"

- **位置**：`13-...Benchmark实测.md` L91；代码 L53-55
- **原文**：「Go 的优势在并发处理——net/http 每个请求一个 goroutine（2KB），FastAPI 用 asyncio 事件循环（单线程）。」
- **问题**：文档给的 FastAPI 端点写的是 `def hello():`（**同步函数**）。FastAPI 对同步 `def` 端点的处理是**丢到外部线程池**执行（`anyio` 线程池，默认 40 worker），而不是在事件循环里跑；只有在 `async def` 且内部 `await` 时才走事件循环。因此这段对比解释的机制与实际代码不符，也解释不了它自己测出的 12,000 QPS（线程池上限反而可能成为瓶颈）。
- **修复建议**：把示例改成 `async def hello():` 再讲"单线程事件循环"，或保留 `def` 但把分析改成"FastAPI 把同步端点放进线程池（默认 40 并发），受 GIL 与线程池上限双重限制"。
- **验证方式与结果**：FastAPI 官方文档《Concurrency and async / await》：同步 `def` 路径函数 "is run in an external threadpool ... instead of being awaited"（`https://fastapi.tiangolo.com/async/`，2026-11-14 抓取）。

### P1-6 06 篇建议 `runtime.GOMAXPROCS(runtime.NumCPU())`：在 1.25+ 是**负优化**

- **位置**：`06-Python有Go无与Go有Python无.md` L451-456
- **原文**：
  ```go
  runtime.GOMAXPROCS(runtime.NumCPU())  // 利用所有 CPU 核心
  ```
- **问题**：自 Go 1.5 起 `GOMAXPROCS` 默认就等于可用 CPU 数，这行本来冗余；更糟的是 1.25+ 的默认值会**读取 cgroup CPU quota 并周期自动更新**，而一旦手动调用 `GOMAXPROCS`，官方文档明确"disables automatic updates"。在 0.5 核 / 1 核限额的容器里显式设成 `NumCPU()` 会直接开出一堆被节流的 P，吞吐反而下降（v6 的 compose 里恰好就有 `cpus: "0.5"`）。
- **修复建议**：删掉这行，改为一句话"Go 1.25+ 默认按 cgroup 配额自动设定并随配额变化更新；不要手工覆盖，除非你确切知道原因（需要固定并行度时用 `GOMAXPROCS` 环境变量）"。
- **验证方式与结果**：本机 `go doc runtime.GOMAXPROCS`（Go 1.27.4）原文：「the Go runtime selects an appropriate default value from … the process's average CPU throughput limit based on cgroup CPU quota」「Setting a custom value with the GOMAXPROCS environment variable or by calling GOMAXPROCS disables automatic updates」；另有 `SetDefaultGOMAXPROCS` 用于恢复。

### P1-8 12 篇 §1 的 Python 侧 `lib.Free(ptr)` 未设 `argtypes`，运行即抛 `ArgumentError`

- **位置**：`12-Go与Python FFI互调.md` L99-104
- **原文**：
  ```python
  lib.Greet.restype = ctypes.c_void_p
  ptr = lib.Greet(b"World")
  ...
  ```

### P1-10 "Go 的 nil 有类型"这一说法在 3 篇里重复，且举例的理由是错的

- **位置**：`02-变量与内置数据结构对比.md` L37、L135；`06-...双向对比.md` L752-753；`08-...面试20问.md` L378-383
- **原文**：
  - 02 L37：「Go 的 `nil` 有类型，不能混用（`nil` for `int` 和 `nil` for `string` 不同）」
  - 08 L378-383：「Go 的 nil **有类型**…」+ 代码 `var p *int = nil; var s []int = nil; // p == s  // ❌ 编译错误：类型不同`
- **问题**：`nil` 在 Go 规范里是**无类型（untyped）**的预声明标识符，它的"类型"来自被赋值的变量/上下文；说"nil 有类型"是把现象当定义。更严重的是 08 的举例归因错误：`p == s` 报错有**两个**原因——① `*int` 与 `[]int` 类型不同；② **slice 本身不可比较**（即使 `var a, b []int` 也不能 `a == b`）。用一个双重错误的最小例去支撑一个不准确的定义，面试会连环翻车。
- **修复建议**：统一改为「`nil` 是无类型值，只能赋给指针/map/slice/channel/func/interface；不同类型变量各有自己的零值，互不兼容。注意 slice/map/func 只能与 nil 比较」。08 的代码例子换成 `var p *int; var q *string; // p == q` 编译错误（单一原因），并单列一条"slice 不可比较"。
- **验证方式与结果**：本机 `go build` 实测：`var a, b []int; _ = a == b` → `.\main.go:5:6: invalid operation: a == b (slice can only be compared to nil)`，直接证明"slice 不可比较"独立于 nil 的类型问题。
