### P0（照抄必翻车 / 概念教错）

#### P0-1 `declare module` "扩展第三方模块"写成"重声明"，会把整个库的类型覆盖掉（静默语义错误）

- **位置**：`阶段三-工程化与实战集成/03-类型声明文件与npm包.md:138-150`（§2.5 扩展第三方模块，`declare module "express"` 在 142 行）
- **原文摘录**：
  ```typescript
  // types/express.d.ts
  declare module "express" {
    interface Request { user?: { id: number; name: string; }; }
  }
  ```
- **问题说明**：这段放在**无 `import`/`export` 的 `.d.ts`** 里时，它不是"模块增强"，而是一条**环境模块声明（ambient module declaration）**——TS 会用它来"声明" `express` 这个模块，从而**顶掉** `node_modules/@types/express` 或包自带的全部类型。结果是：`import { Response, app } from "express"` 报"没有导出成员"，`Request` 上原有的 `path`/`method` 也消失。这正是简报点名的"能跑但结果错"的最危险类别——编译不报错（声明文件自己 `rc=0`），错在**下游**。
- **实测（A/B 对照）**：自建 `node_modules/express`（含 `Request{path,method}`、`Response`、`app`）后：
  - 文档写法：`rc=2`，`consumer.ts(2,19) TS2305 Module '"express"' has no exported member 'Response'`、`(2,29) … 'app'`、`(3,22) TS2353 'path' does not exist in type 'Request'`。
  - 正确写法（首行加 `import "express";`）：`rc=0`，且 `user` 属性正确合并。
- **修复建议**：在 `types/express.d.ts` 首行加 `import "express";`（使其成为模块），并在正文加一句：
  > 「`declare module "x"` 有两种语义：文件**不是**模块时 = 声明新模块（会覆盖同名包）；文件**是**模块时 = 增强已有模块。扩展第三方库必须让文件先成为模块。」
  同时把 §4.3 的 `declare module "untyped-lib"`（216 行）单独放一个**无 import 的 `.d.ts`**，否则 `TS2664 Invalid module name in augmentation`（本轮已复现）。
- **验证方式与结果**：`.scratch\...\aug_test\aug_test.py` 两组对照，输出见上。**已实测**。

#### P0-2 ESLint 9 下 `--ext .ts` 直接报 "Invalid option"，三处 lint 脚本全部无法执行

- **位置**：`阶段三-工程化与实战集成/04-测试与CI.md:273-274`、`毕业项目-TS任务管理器/v6-测试与CI版.md:410-411`、`v7-可发布npm包版.md:104`
- **原文摘录**：`"lint": "eslint src/ --ext .ts",` / `"lint:fix": "eslint src/ --ext .ts --fix",`
- **问题说明**：这三处 doc 自己已经切到 **ESLint 9 flat config**（`eslint.config.mjs`），而 flat config 模式**不接受 `--ext`**，运行即报
  `Invalid option '--ext' - perhaps you meant '-c'? You're using eslint.config.js, some command line flags are no longer available.`
  更直接的内部矛盾：**本路径总索引第 16 行自己写着**「ESLint 9 flat config（`eslint.config.mjs`，**无需 `--ext` 参数**）」。也就是说索引讲对了，正文三处没跟上——`npm run lint` / `npm run check` / CI 的 lint 步骤会依次失败。
- **修复建议**：三处统一改为 `"lint": "eslint src"`、`"lint:fix": "eslint src --fix"`；文件类型由 `eslint.config.mjs` 的 `files: ["src/**/*.ts"]` 决定（三处配置里已经写了 `files`，改完即可用）。
- **验证方式与结果**：官方文档与 issue 三方印证——① ESLint CLI 参考页明确 `--ext` 仅 eslintrc 模式可用；② [eslint/eslint#17931](https://github.com/eslint/eslint/issues/17931) 原文引用了同一条报错并给出"删掉 `--ext`，用 `files` 表达"的官方答复；③ 本机未装 eslint，**未做实机复现**（标注：文档级核实，未实跑）。

#### P0-3 阶段一 03「重载的常见陷阱」：好例子本身不编译，坏例子的说明与事实相反

- **位置**：`阶段一-类型系统基础/03-函数与数组类型.md:115-128`
- **原文摘录**：
  ```typescript
  // ❌ 坏例子：实现签名暴露了 string，但重载签名没有
  function parse(x: number): number;
  function parse(x: string): number;
  function parse(x: number | string): number { return Number(x); }
  // TS 不会暴露 string 之外的重载——调用者看不到

  // ✅ 好例子：用联合类型或显式重载覆盖所有入参类型
  function parse(x: number | string): number;
  ```
- **问题说明**（两层都错）：
  1. **"坏例子"其实是完全正确的代码**：两个重载签名 + 兼容的实现签名，是标准写法。注释说"实现签名暴露了 string"不成立——**实现签名永远不对外暴露**（这是本节主题），而重载列表**本来就有** `string`。末句"TS 不会暴露 string 之外的重载"逻辑不通。
  2. **"好例子"不编译**：`function parse(x: number | string): number;` 只有签名没有实现，实测 `error TS2391: Function implementation is missing or not immediately following the declaration`。学习者照抄"✅ 好例子"会立刻撞错。
  3. 真正的陷阱（本节本该讲的那个）没讲：**实现签名接受 `string`，但重载列表没有 `string`** → `parse("1")` 报"没有匹配的重载"，这才是"实现签名不对外暴露"的坑。
- **修复建议**：整节重写为三行对照
  ```typescript
  // ✅ 正确：重载列表覆盖所有想公开的入参形态，实现签名兼容它们
  function parse(x: number): number;
  function parse(x: string): number;
  function parse(x: number | string): number { return Number(x); }

  // ❌ 陷阱：实现签名能吃 string，但重载列表没写 → 调用方看不到
  function parse2(x: number): number;
  function parse2(x: number | string): number { return Number(x); }
  // parse2("1"); // ❌ 报错：没有匹配的重载
  ```
- **验证方式与结果**：`blocks/阶段一…__b06.ts` → `rc=2`，`(10,10): error TS2391`。修复写法已按上述结构在脑中比对（未单独落文件，标注**已实测错误、未实测修复**）。

#### T1-2 "filter 不会自动收窄"与 TS 5.5 事实相反，且与总索引自相矛盾

- **位置**：`阶段一-类型系统基础/03-函数与数组类型.md:181-183`；冲突处 `00-TypeScript学习路径总索引.md:16`
- **原文摘录**：`// filter 不会自动收窄`（随后用 `(x): x is string =>` 手动加谓词）
- **问题说明**：TS **5.5 起**，`filter` 的内联箭头函数会**自动推断类型谓词**。索引第 16 行自己写着"5.5 起 `filter` 可自动推断类型谓词"，而正文这篇（阶段一，学习者最早接触 filter 的地方）教的是相反的结论。后果不致命（显式谓词仍然正确、更稳），但会让学习者对"哪些推断是自动的"形成错误直觉，也白写了样板代码。
- **实测**：
  ```typescript
  const mixed: (string | number)[] = [1, "a", 2, "b"];
  const strings = mixed.filter((x) => typeof x === "string");
  const probe: number[] = strings;
  ```
  → `error TS2322: Type 'string[]' is not assignable to type 'number[]'`，即 `strings` 已被推断为 `string[]`，**无需求助显式谓词**。
- **修复建议**：改为
  `// TS 5.5+：内联箭头会自动推断类型谓词，strings 已是 string[]；显式谓词（x): x is string 用于"想自己把关"或旧版本/跨函数复用`
  并保留显式谓词版本作为"更明确"的写法（两种都展示，讲清区别）。
- **验证方式与结果**：`probes/p1_filter.ts` 编译，错误信息即结论。**已实测**。

#### T1-6 类型查找优先级表把"项目内 `declare module`"排最后，实测它是**覆盖级**而非兜底级

- **位置**：`阶段三-工程化与实战集成/03-类型声明文件与npm包.md:199-206`
- **原文摘录**：
  ```
  1. 包自身的 types 字段（package.json）
  2. 包根目录下的 index.d.ts
  3. node_modules/@types/xxx/index.d.ts
  4. 项目内的 declare module
  ```
- **问题说明**：第 4 条给人的印象是"前面都找不到才用我"。实际相反：**无 `import` 的 `declare module "x"` 会直接声明模块 `x`，把包自带类型顶掉**（P0-1 的实测就是这个机制）。把它列在最后，会让读者以为"写了也不影响包本身"。
- **修复建议**：改为两条并列语义：
  > 1-3 是**模块解析顺序**（找到即用）；第 4 项不是兜底，而是**覆盖**——文件是模块时 = 增强（需目标存在，否则 `TS2664`），文件不是模块时 = 声明新模块（覆盖同名包）。
- **验证方式与结果**：`aug_test`（同 P0-1）+ `probes/p9_ambient_aug.ts`（`TS2664`）。**已实测**。
