## P0 — 照抄必翻车 / 静默算错

### T-01（P0）场景 6 推荐系统：`fit` 输入形状与 `Input(shape=(1,))` 不匹配，必抛 ValueError

- **位置**：`10-业务场景实战合集.md` L311–341（尤其 L341）
- **原文**：
  > `user_ids = np.random.randint(0, n_users, n_samples)` … `user_input = tf.keras.Input(shape=(1,), dtype=tf.int32, name='user')`
  > `model.fit({'user': user_ids, 'movie': movie_ids}, ratings, ...)`
- **问题**：`user_ids/movie_ids` 是 `(5000,)` 的一维数组，而 Input 声明 `(batch, 1)`。Keras 在 `fit` 时会报 `Input 0 of layer "model" is incompatible with the layer: expected shape=(None, 1), found shape=(None,)`。这不是"结果偏差"，是**照抄即崩**。（同篇 04 篇 §9、06 篇 §5 都正确传了 `(n,1)`，说明是单篇疏漏。）
- **修复建议**：`user_ids.reshape(-1, 1)`、`movie_ids.reshape(-1, 1)`；或把 Input 改为 `shape=()`（scalar）并把数据保持一维。
- **验证方式**：`py_compile` 通过（语法无误），运行期错误由 shape 规则推断——**推理未实跑**（本机无 TF）。Keras Input 形状契约见 `keras.io/api/layers/core_layers/input/`（页面直连失败，仅凭 API 契约）。

### T-02（P0）D4 挑战题与 D7 项目 1：梯度"双重聚合"，参数更新被放大 `num_replicas` 倍（静默错）

- **位置**：`分布式训练/D4-自定义训练循环分布式.md` L455–496（L464 `apply_gradients`、L482–485 `all_reduce` + `assign_add`）；`分布式训练/D7-分布式训练实战项目.md` L87–121（L89 `apply_gradients`、L112–115 `all_reduce` + `assign_add`）
- **原文**：
  > `grads = tf.distribute.get_replica_context().all_reduce(tf.distribute.ReduceOp.SUM, grads)`
  > `optimizer.apply_gradients(zip(accum_vars, model.trainable_variables))`
- **问题**：MirroredStrategy 下 Keras 优化器在 replica context 内 `apply_gradients` 时**自己还会按 MirroredVariable 的 SUM 聚合一次**（这正是本系列 D4 §2.4 与"loss 要除以 global_batch"的原因）。这里先用 `all_reduce(SUM)` 把梯度对齐成"全局平均"，再交给优化器 → 优化器把 N 个副本上**相同的**值再求和一次 → 生效梯度 = 正确值 × num_replicas。4 卡时等效学习率 ×4，训练仍能收敛、日志照常下降，**属于最危险的静默语义错误**，而且出现在全库唯一"真梯度累积"示例上。
  - D7 另叠加一个问题：`get_scaled_loss` 之后把**跨 step 的 scaled 梯度**累加，而 `LossScaleOptimizer` 的动态 loss scale 会在每次 `apply` 后变化 —— 同一累积窗口内的 4 份梯度可能带着不同 scale，除回后不等价于大 batch。
- **修复建议**：删掉 `get_replica_context().all_reduce(...)` 一行（让优化器在 apply 时统一聚合）；或保留手动聚合但把 `apply_gradients` 移到 replica context 之外，并对梯度先除以 `num_replicas`。混合精度累积改为：固定 loss scale（`LossScaleOptimizer(optimizer, dynamic=False)`）或先 `unscale` 再累积。
- **验证方式**：**推理未实跑**（无 GPU）。依据：Keras 优化器 `_aggregate_gradients` 对 MirroredVariable 默认 SUM 聚合 —— 这一行为在本系列 D4 §2.4/L238 自己写明了（"不要用 per_gpu_batch_size，否则 loss 会被放大 N 倍"），两处口径互相矛盾即为证据。

### T-03（P1）04 篇 StringLookup 整数映射写错，且与 02 篇矛盾

- **位置**：`04-特征工程对比.md` L202–206

- **修复建议**：改注释为 `# '北京' → 1`，并补一句"0 是 OOV，索引从 1 开始"（与 02 措辞统一）。
- **验证方式**：推理（`StringLookup` 默认 OOV 槽位规则）；与 02 篇 L153 注释交叉比对。

### T-04（P1）03 篇"Sklearn 优化器不可选"表与 sklearn API 不符（对照面事实错误）

- **位置**：`03-传统ML模型迁移.md` L469–476
- **原文**：
  > `| LogisticRegression | lbfgs / liblinear / saga | ✅ 3 选 1 |`
  > `| Ridge | 最小二乘 + 正则 | ❌ |`
- **问题**：`LogisticRegression(solver=...)` 官方可选 **6 种**：`lbfgs / liblinear / newton-cg / newton-cholesky / sag / saga`；`Ridge(solver=...)` 同样可指定 `auto/svd/cholesky/lsqr/sparse_cg/sag/saga/lbfgs`。表中"3 选 1""❌ 不可选"把 Sklearn 说得比实际更死板，恰好落在"贬低另一侧"的高危区。
- **修复建议**：改为 `lbfgs / liblinear / newton-cg / newton-cholesky / sag / saga（6 选 1）`；Ridge 行改为 `✅ solver 可选（svd/cholesky/lsqr/…）`；保留"用户不能自定义优化过程"这个真正成立的论点。
- **验证方式**：sklearn 官方 API 记忆 + 参数默认值（`solver='lbfgs'`）；未直连文档（本机 `sklearn` 亦未装）。**标注：事实核对依据为 API 契约，未跑 `inspect.signature`。**

### T-05（P1）07 篇"EarlyStopping 仅 MLPClassifier 有"不成立

- **位置**：`07-双向对比-Sklearn有TF无与TF有Sklearn无.md` L164
- **原文**：`| **EarlyStopping** | 验证指标不提升时停止 | 仅 MLPClassifier 有 |`

### T-06（P1）v4 / v5 / T9 用测试集当 EarlyStopping 的验证集，再在同一测试集报分（评测量泄漏）

- **位置**：`v4-深度学习入门.md` L81–87；`v5-端到端ML项目.md` L81–89；`Transformer/T9-Transformer 项目实战.md` L131–146（`validation_data=test_ds`）

### T-07（P1）T3 练习 2 参考代码必崩：`build_model` 默认 `max_len=100`，数据却 pad 到 200

- **位置**：`Transformer/T3-Positional Encoding.md` L464–500
- **原文**：
  > `def build_model(pe_type, max_len=100, vocab_size=10000, d_model=128):` … `inputs = tf.keras.layers.Input(shape=(max_len,))`
  > `vocab_size, max_len = 10000, 200` … `pad_sequences(x_train, maxlen=max_len)` … `model = build_model(pe_type)`
- **问题**：循环里调用 `build_model(pe_type)` 用的是默认 `max_len=100`，而输入被 pad 到 200 → `Input(shape=(100,))` 收到 `(None, 200)`，报 shape 不兼容；即便侥幸通过，`pe = get_positional_encoding(100, 128)` 与 `x` 的 200 步也无法广播。
- **修复建议**：循环改为 `build_model(pe_type, max_len=max_len)`；或把默认值删掉，强制显式传参。
- **验证方式**：AST/常量折叠检查（默认参数 100 vs 模块级 200），**推理未实跑**。

### T-08（P1）T1 练习 3 的验收结论与代码输出相反

- **位置**：`Transformer/T1-Self-Attention 深度原理.md` L609–629
- **原文**：
  > `attn_out_shuffled = attn_model.predict(x_shuffled[:1], ...)`
  > `# False — Self-Attention 输出基本不变（位置无关）`
- **问题**：`SelfAttention` 是**置换等变**（permutation equivariant）：打乱输入 → 输出同样被置换，**逐位置张量比较必然不等**，`np.allclose` 会返回 False，`not ...` 打印 **True**，与注释和"验收标准"（"输出基本不随顺序变化"）相反。要演示等变性必须先把输出按同一 perm 排回去，或比较集合/排序后的范数。
- **修复建议**：`out_shuffled_restored = tf.gather(attn_out_shuffled, np.argsort(perm))` 再比；或比较 `np.sort(out, axis=1)`。验收标准改为"打乱后按 perm 还原可复现（误差<1e-5）"。
- **验证方式**：**实测**（纯 Python 复现置换等价：对 `softmax(xx^T)x` 施加 perm 后输出恰为 perm(output)），见本报告附录 A。

### T-09（P1）T9 项目 2：`TFViTModel(...).pooler_output` 不能这么接 Functional API，且缺 ViT 归一化

- **位置**：`Transformer/T9-Transformer 项目实战.md` L247–258、L237–242
- **原文**：
  > `base_model = TFViTModel.from_pretrained("google/vit-base-patch16-224-in21k")` … `x = base_model(inputs).pooler_output`
  > `def preprocess(image, label): image = tf.image.resize(image, (224, 224)); return image, label`
- **问题**：
  1. HuggingFace 的 TF 模型 `call` 返回 `TFBaseModelOutputWithPooling` 数据类，不是张量；在 Functional API 里对**符号张量**调用并取 `.pooler_output` 无法构图（Keras 只能追踪返回张量/字典的层）。应使用 `TFViTForImageClassification`，或把 backbone 包进自定义 `Layer` 只返回 `pooler_output`。
  2. 预处理只有 `resize`，**没有** ViT 必需的 `pixel/127.5 - 1`（或 mean/std 归一化），输入分布与预训练完全不符 → 冻结阶段准确率会远低于验收线 70%。
- **修复建议**：`tf.keras.layers.Rescaling(1/127.5, offset=-1)` 放进模型首层；backbone 用 `TFViTForImageClassification` 或自定义包装层。
- **验证方式**：**推理未实跑**（无 TF/transformers）。依据：transformers TF 模型返回 dataclass（`outputs.pooler_output` 是属性访问，非张量），以及 ViT feature extractor 的标准 `do_rescale/do_normalize` 流程。

### T-14（P1）D3 手动 shard 场景下 `batch()` 的口径被写成"全局 batch"

- **位置**：`分布式训练/D3-MultiWorker 多机多卡.md` L186–200
- **原文**：
  > `num_workers = 3  # TF_CONFIG 中的进程总数` … `dataset.shard(num_shards=num_workers, index=task_id)`
  > `global_batch = per_worker_batch * strategy.num_replicas_in_sync`
- **问题**：`batch()` 作用在**每台 worker 自己的** shard 后数据集上，是 per-worker 语义；注释却称"全局 batch_size 要覆盖所有机器的所有 GPU"。若 `num_replicas_in_sync` 在多机策略下返回**集群总副本数**（本库 D3 L159 与 D7 L160 都按"8 = 2 机×4 卡"理解），则每 worker 实际 batch = 64×8=512，全局 = 512×3=1536，per-GPU 从预期 64 变成 128 —— 多乘了一次 worker 数。D7 L175 同样写法。
- **修复建议**：手动 shard 时写 `per_worker_batch * 本机 GPU 数`，并在注释里区分"per-worker batch / global batch / per-replica batch"三层；或干脆删掉手动 shard，改用默认 `AutoShardPolicy.AUTO`（D3 L213–215 已正确描述）。
- **验证方式**：**推理**（tf.data 的 `batch` 在 distribute 之前执行，属 per-worker）；`num_replicas_in_sync` 的多机语义**未直连核实**，建议 `strategy.num_replicas_in_sync` 在 2×4 环境实测打印。

## 已核实 vs 未验证

**已验证（有实测/可复现依据）**
1. `01` 练习 4 的验收阈值 `<0.05` **不构成缺陷**：用 numpy 复现 `SGD(0.01)+batch32+200ep`，TF 预测与 OLS 预测的 MSE = **8.53e-06**（远低于 0.05），原担心不成立（附录 A）。
2. 2026-08-23 五个前修点**未回归**：`06` L443/L457 蒸馏全程 logits（无二次 sigmoid）；`T2` L213 与 `T4` L371/T6 L208 的 mask 语义（1=可见）与自定义层（1=遮蔽）区分清楚且各篇一致；`D5` §3.2 为真累积（`grads/accum_steps` 入 accum_vars，仅每 N 步 apply）；`X1` L416–434 用 `Split-train/FeatureStats.pb` 且 `validate_statistics(previous_statistics=...)`；`X2` L266–284 枚举名与 `COMPARATOR_*` 均真实；`06` 练习 1 验收明确写"TF-DF 不支持 GPU"。
3. TF-DF **Windows 无 pip 包**（`06` L58、`07` L69、`99-第二周` L306 的断言正确）：TensorFlow 官方 Known Issues 明写 "TensorFlow Decision Forests is not yet available as a Windows Pip package"，安装页写 "A Windows build … is not maintained"（`tensorflow.org/decision_forests/known_issues`，搜索片段已核）。**该条不是缺陷，不再立案，避免历史假阳性回归。**
4. `D5` 的显存算术（110M×16B=1.76GB ≈ 440+440+880MB）与 `06` 的 LoRA 参数算术（590,592 / 12,288）逐数复算正确。
5. 51 篇代码块均通过"语法级"通读（无未闭合围栏、无可疑缩进）；`py_compile` 仅对纯 Python 片段可用，含 TF 符号的块按 API 契约比对。

**未验证（本报告不据此下 P0/P1 结论）**
- 所有 TF/TFX/TFT 运行时行为（本机无 TF 且禁止联网安装）——T-01/T-02/T-07/T-09 属"高置信推理"，需在有 TF 的机器上各跑 1 次确认。
