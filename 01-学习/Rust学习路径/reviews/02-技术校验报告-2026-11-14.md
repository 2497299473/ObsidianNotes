## P0 问题（照抄必翻车）

### T-1 `01-线程与消息传递.md:121-148`：mpsc 示例把 `tx` move 进线程后又 `drop(tx)`，E0382

- **原文（L131-133 / L141）**：
  ```rust
  thread::spawn(move || {
      tx.send(String::from("来自线程 1")).unwrap();
  });
  // …
  drop(tx);   // 关键：丢弃主线程手里的原始 tx
  ```
- **问题**：`tx` 在 L131 已被 move 进第一个 `spawn` 闭包，L141 再 `drop(tx)` 必然
  `error[E0382]: use of moved value: tx`。注释「丢弃主线程手里的原始 tx」描述的是一个
  已经不存在的值——这正是本课最重要的知识点（「忘记 drop 原始 tx → `for msg in rx` 永久阻塞」），
  却给了一段编译不过的示范。紧随其后的「实战：工作线程汇总结果」块（L159-188）写法正确
  （循环内 clone，再 drop 原始 tx），说明作者知道正确写法，只是首例写错。
- **修复建议**（保持「两个生产者 + 丢弃原始 tx」的教学意图）：
  ```rust
  let tx1 = tx.clone();
  let tx2 = tx.clone();
  thread::spawn(move || { tx1.send(String::from("来自线程 1")).unwrap(); });
  thread::spawn(move || { tx2.send(String::from("来自线程 2")).unwrap(); });
  drop(tx);   // 现在主线程确实还持有原始 tx，这句才成立
  ```
- **验证方式与结果**：`rustc 1.100.0 --edition 2021 --emit=metadata` 编译该块 →
  `error[E0382]: use of moved value: tx`（块内 L20 = md L141），
  note 明确指出 `value moved into closure here`（md L131）。**实测报错，非推测。**

### T-2 `04-结构体、枚举与模式匹配.md:186-203`：自定义 `enum Option<T>` 后 `Some(5)` 绑定到 std 变体，4×E0308

- **原文（L187-193 / L201）**：
  ```rust
  enum Option<T> { Some(T), None }
  …
  let some_num: Option<i32> = Some(5);
  …
  println!("sum = {}, absent = {:?}", sum, absent);
  ```
- **问题**：块内重定义 `Option` 只遮蔽了**类型名**，`Some`/`None` 这两个**变体名**仍来自
  prelude 的 `std::option::Option`，于是 `Some(5)` 的类型是 `std::option::Option<{integer}>`，
  与本地 `Option<i32>` 不同 → 4 个 `E0308 mismatched types`
  （`Some(5)`、`None`、`match` 两个分支各一）。即便修好类型，`{:?}` 还会因本地 `Option`
  没有 `#[derive(Debug)]` 再报 `E0277`。示例本意是「标准库就是这样定义的」，作为可运行代码是错的选择。
- **修复建议**：把定义降级为注释（最能表达「这就是标准库的定义」且不会被误粘贴）：
  ```rust
  // 标准库中的定义（示意，不要在本文件重复定义）：
  // enum Option<T> { Some(T), None }
  ```
  若要保留可运行版本，则需 `use Option::*;` 会与 prelude 变体冲突，不推荐；
  次优做法是改名为 `Maybe<T>` 并把 `Some/None` 一并改名。
- **验证方式与结果**：`rustc` 编译 → 4 × `error[E0308]`，note 原文
  「`std::option::Option<{integer}>` and `Option<i32>` have similar names, but are actually
  distinct types」。**实测报错。**

## P1 问题（重要缺陷）

### T-3 `毕业项目/v5-多线程并发版.md:63-84`：`parallel_stats` 空列表时 `chunks(0)` panic，且与 `code/v5` 不一致

- **原文（L65 / L69）**：
  ```rust
  let chunk_size = (tasks.len() + workers - 1) / workers; // 向上取整
  …
  for piece in tasks.chunks(chunk_size) {
  ```
- **问题**：`tasks.len() == 0` 时 `chunk_size = (0 + w - 1) / w = 0`，
  `slice::chunks(0)` **panic**（`chunk size must be non-zero`）。任务列表为空是毕业项目的正常初始状态，
  照抄这段就会在「刚启动、还没有任务」时崩。
  关键证据：`code/v5/main.rs:89` 与 `code/v6/main.rs:183` **都写了 `if chunk_size > 0 {`** 保护，
  唯独 md 里的「参考实现」没有——说明代码修过、文档没同步。
- **修复建议**：把 md 块与 `code/v5` 对齐（加 `if chunk_size > 0 { … }` 包住 scope），
  并加一行注释「空列表直接返回 (0,0)，避免 chunks(0) panic」。
- **验证方式与结果**：最小复现程序（`.scratch/.../probe2/chunks_zero.rs`）编译通过、运行
  `panicked at chunks_zero.rs:7 … chunk size must be non-zero`（exit 101）。
  同时 `cargo check` 确认 `code/v5`/`code/v6` 已有保护分支。

### T-4 `03-函数与所有权.md:76-80`：「所有权三条规则」第 1、2 条同义重复，实际只教了两条

- **原文（L78-80）**：
  ```
  1. **每个值都有且只有一个所有者**（owner）
  2. **同一时刻只能有一个所有者**
  3. **所有者离开作用域时，值被丢弃**（`drop`，自动释放内存）
  ```
- **问题**：第 1 条已含「唯一」，第 2 条再说一次「同一时刻只能有一个」，两条是同一命题的换词。
  通行三规则是：① 每个值都有一个所有者；② 同一时刻只能有一个所有者；③ 所有者离开作用域值被释放。
  本条把 ① 写成了 ①+② 的合体，学生背「三规则」时实际只记住两条半，且理解不到
  「所有权可以**转移**（move）但任一时刻只有一个」这一层——恰好是紧接着 §3 move 语义的引子。
- **修复建议**：
  ```
  1. 每个值都有一个所有者（owner）
  2. 同一时刻只能有一个所有者；所有权可以转移（move），但不是复制
  3. 所有者离开作用域时，值被 drop
  ```
  并把 §3 的 move 段落首句改为「第 2 条规则的直接推论」。
- **验证方式与结果**：文本对照 TRPL 第 4 章规则表述（**未联网复核原文，按通行教材口径**）；
  该块的代码本身编译通过，属**表述缺陷而非编译缺陷**。

### T-5 `code/v4/main.rs:17-18`：头注释示例会静默把 `list` 并进标题（单命令解析器的坑）

- **原文**：
  ```
  //!   cargo run -- --backend=memory add 临时任务 list
  ```
- **问题**：v4 沿用 v3 的**单命令**解析器（`parse_args` 只取第一个子命令，其余全部当参数），
  所以 `add 临时任务 list` 的标题会变成 `"临时任务 list"`，`list` 命令**不会执行**，也没有任何提示。
  这与 v1/v2 的「一次串联多个命令」行为不同，头注释却照抄了 v1 的多命令示例。
- **修复建议**：改为 `cargo run -- --backend=memory add 临时任务`，并在注释里补一句
  「v3 起改为单命令模式（数据已持久化，无需串联）」——正好呼应 v3 的设计变更。
- **验证方式与结果**：`cargo run --quiet -- --backend=memory add 临时 list` 实跑，
  输出仅 `[info] 使用 memory 后端` / `已添加任务 #1`，**无 list 输出**；
  随后的 `--backend=file add 持久` + 读 `tasks.json` 确认标题未被截断（`add` 拿到全部剩余参数）。
  这是本轮唯一的**静默语义错误**（能跑、不报错、结果与读者预期不同）。

### T-6 `04-测试、文档与工程实践.md:204`：「同一版本号不可重复发布，也不可撤回」

- **原文**：`cargo publish  # 正式发布（同一版本号不可重复发布，也不可撤回）`
- **问题**：crates.io 提供 `cargo yank`——可把某版本标记为「已撤回（yanked）」，
  效果是新依赖无法选中该版本、已有 `Cargo.lock` 仍可构建。说「不可撤回」会让读者
  在误发版本时以为只能发新版本补救，实际 yank 是标准做法（虽不能删除文件）。
- **修复建议**：改为「同一版本号不可重复发布，也不能删除；误发可用 `cargo yank --version x.y.z` 撤回
  （阻止新依赖选中，已有锁定不受影响），再发一个修订版」。
- **验证方式与结果**：依据 Cargo Book `cargo yank` 语义（**未联网抓取原文，按官方命令手册常识**）；
  本条属文档表述，无编译面。

### T-7 `00-Rust学习路径总索引.md:20`：stable 版本快照落后（1.98+ → 实测 1.100.0）

- **原文**：`**🔄 2026-09 版本口径**：stable 已至 1.98+（2026-08，以 blog.rust-lang.org 为准）`
- **问题**：本机实测 `rustc 1.100.0 (0ef1bc386 2026-11-09)` / `cargo 1.100.0 (3acc79c0c 2026-11-05)`，
  快照已落后两个 minor。学员对照「1.98+」会以为自己的 1.100 是「超前版本」。
  该句已注明「以 blog 为准」，所以不算硬错，但作为版本基线应更新。
- **修复建议**：改为「stable 1.100（2026-11 实测），版本号只增不减，具体以 blog.rust-lang.org 为准」，
  或直接去掉数字只保留「跟随 stable」。
- **验证方式与结果**：`rustc --version` / `cargo --version` 实测输出（见报告头）。
