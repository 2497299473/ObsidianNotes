## 1. panic!：不可恢复错误

`panic!` 用于程序陷入不变量被破坏、无法继续的状态（如越界的逻辑错误）。默认展开栈后退出；设置 `RUST_BACKTRACE=1` 可看到完整调用栈。

```rust
fn read_config(key: &str) -> String {
    if key.is_empty() {
        // 调用方传空 key 属于程序员的错误，不是用户输入问题
        panic!("read_config: key 不能为空");
    }
    String::from("value")
}

fn main() {
    // 终端执行：RUST_BACKTRACE=1 cargo run 查看完整调用栈
    read_config("");
}
```

- 展开（默认）：逐层清理栈上数据；abort 模式：直接终止、二进制更小。panic 策略是**编译期**设置——Cargo.toml 中 `[profile.release] panic = "abort"`，或 `rustc -C panic=abort`（没有 `RUST_PANIC` 这类运行时环境变量；相关的环境变量只有 `RUST_BACKTRACE`）。
- 数组越界、`unwrap` 失败、显式 `panic!` 都会触发 panic。

> 💡 panic 是「放弃」，不是「处理」。库代码应尽量把可恢复错误转成 `Result` 返回，把选择权交给调用方。

## 2. Result<T, E> 与 unwrap / expect 的边界

```rust
use std::fs;

fn main() {
    match fs::read_to_string("tasks.txt") {
        Ok(content) => println!("读到 {} 字节", content.len()),
        Err(e) => eprintln!("读取失败: {e}"),
    }

    // 原型 / 测试 / 确定不会失败的场景可以用：
    let n = "42".parse::<u32>().unwrap();
    assert_eq!(n, 42);

    // expect 比 unwrap 多一条上下文信息，panic 时更容易定位：
    let port = std::env::var("PORT")
        .expect("环境变量 PORT 必须设置") 
        .parse::<u32>()
        .expect("PORT 必须是数字");
    println!("port = {port}");
}
```

| 写法 | 失败时行为 | 适用场景 |
|------|------------|----------|
| `match` / `if let` | 完全自定义处理 | 真正需要恢复的分支 |
| `expect("说明")` | panic + 自定义信息 | 不变量保证成立、失败即 bug |
| `unwrap()` | panic，信息只有错误本身 | 测试、示例、极有把握的短命脚本 |

## 3. ? 运算符：错误传播与 From 转换

`expr?` 的语义：`Ok(v)` 取出 `v` 继续；`Err(e)` 则 `Err(e.into())` 提前返回。`.into()` 意味着只要目标错误类型实现了 `From<源错误>`，就能自动转换。

```rust
use std::fs;
use std::io;

fn first_line(path: &str) -> Result<String, io::Error> {
    let content = fs::read_to_string(path)?; // io::Error 原样向上传播
    let line = content
        .lines()
        .next()
        .map(|s| s.to_string())
        .ok_or(io::Error::new(io::ErrorKind::InvalidData, "文件为空"))?;
    Ok(line)
}

fn main() {
    match first_line("tasks.txt") {
        Ok(line) => println!("第一行: {line}"),
        Err(e) => eprintln!("出错: {e}"),
    }
}
```

`Option` 也可以用 `?`：`Some(v)` 取出，`None` 提前返回 `None`。

**让 main 返回 Result**：`main` 可以返回 `Result<(), E: Debug>`，出错时进程码非 0（仅打印 Debug，生产入口建议自己打印友好信息）：

```rust
fn main() -> Result<(), String> {
    let path = std::env::args().nth(1).ok_or("用法: app <文件路径>".to_string())?;
    let content = std::fs::read_to_string(&path).map_err(|e| e.to_string())?;
    println!("{} 共 {} 字节", path, content.len());
    Ok(())
}
```

## 4. 自定义错误枚举：为任务管理器设计 AppError

任务管理器中典型错误来源：文件读写（`io::Error`）、数字解析（`ParseIntError`）、任务不存在。用枚举统一建模，并为外部错误实现 `From`，`?` 就能无缝工作。

```rust
use std::fmt;
use std::fs;
use std::io;
use std::num::ParseIntError;

#[derive(Debug)]
enum AppError {
    Io(io::Error),
    Parse(ParseIntError),
    NotFound(String),
}

impl fmt::Display for AppError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            AppError::Io(e) => write!(f, "IO 错误: {e}"),
            AppError::Parse(e) => write!(f, "解析错误: {e}"),
            AppError::NotFound(name) => write!(f, "未找到: {name}"),
        }
    }
}

impl std::error::Error for AppError {}

impl From<io::Error> for AppError {
    fn from(e: io::Error) -> Self {
        AppError::Io(e)
    }
}

impl From<ParseIntError> for AppError {
    fn from(e: ParseIntError) -> Self {
        AppError::Parse(e)
    }
}

/// 读取优先级文件：第一行应为数字
fn load_priority(path: &str) -> Result<u32, AppError> {
    let content = fs::read_to_string(path)?; // io::Error -> AppError::Io
    let first = content
        .lines()
        .next()
        .ok_or_else(|| AppError::NotFound(path.to_string()))?;
    let prio = first.trim().parse::<u32>()?; // ParseIntError -> AppError::Parse
    Ok(prio)
}

fn main() -> Result<(), AppError> {
    match load_priority("priority.txt") {
        Ok(p) => println!("优先级 = {p}"),
        Err(e) => eprintln!("加载失败: {e}"),
    }
    Ok(())
}
```

> 💡 枚举错误 + `From` 是库代码的推荐姿势：调用方既能 `match` 分支处理，也能用 `?` 一键传播。

## 5. 组合子、生态选型与决策表

**常用组合子**：

```rust
fn parse_priority(raw: &str) -> u32 {
    raw.trim().parse().unwrap_or(0) // 失败给默认值
}

fn double_if_ok(raw: &str) -> Option<u32> {
    raw.trim()
        .parse::<u32>()
        .ok() // Result -> Option
        .and_then(|v| v.checked_mul(2)) // 串联下一步
}

fn main() {
    assert_eq!(parse_priority("3"), 3);
    assert_eq!(parse_priority("abc"), 0);
    assert_eq!(double_if_ok("21"), Some(42));
    assert_eq!(double_if_ok("not a number"), None);

    let label = Some(String::from("release"))
        .map(|s| format!("[{s}]"))
        .unwrap_or_else(|| String::from("[未命名]"));
    println!("{label}");
}
```

| 组合子 | 作用 |
|--------|------|
| `map(f)` | 变换 `Ok`/`Some` 里的值 |
| `and_then(f)` | 值再进一个返回 `Result`/`Option` 的函数 |
| `unwrap_or(v)` / `unwrap_or_else(f)` | 失败时给默认值（后者惰性求值） |
| `map_err(f)` | 转换错误类型，常用于 `?` 前补充上下文 |
| `ok()` / `ok_or(e)` | `Result↔Option` 互转 |

**生态速览**（需添加依赖后使用）：

```rust
// thiserror：库代码，用宏少写 Display/From 样板
use thiserror::Error;

#[derive(Debug, Error)]
pub enum AppError2 {
    #[error("IO 错误: {0}")]
    Io(#[from] std::io::Error),
    #[error("解析错误: {0}")]
    Parse(#[from] std::num::ParseIntError),
    #[error("未找到: {0}")]
    NotFound(String),
}
```

```rust
// anyhow：应用代码，一个 Result<T> 走天下，还能附加上下文链
use anyhow::{Context, Result};

fn load_config(path: &str) -> Result<String> {
    std::fs::read_to_string(path)
        .with_context(|| format!("读取配置文件失败: {path}"))
}
```

**何时 panic、何时 Result 决策表**：

| 场景 | 选择 | 理由 |
|------|------|------|
| 不变量被破坏（逻辑 bug、内部数组越界） | `panic!` / `expect` | 继续运行会产生更坏结果 |
| 用户输入、文件、网络等外部因素 | `Result` | 调用方有机会重试/提示/降级 |
| 库代码的对外 API | `Result` + 自定义错误类型 | 不替调用方做退出决定 |
| 应用入口、脚本 | `anyhow::Result` | 快速拿到带上下文的错误链 |
| 测试、示例代码 | `unwrap` 可接受 | 短命且目的明确 |

## 常见陷阱

| 陷阱 | 表现 | 对策 |
|------|------|------|
| 到处 `unwrap` | 一处输入异常整个程序 panic | 生产路径用 `match`/`?`；确信用 `expect` 并写明理由 |
| 错误信息不带上下文 | 只看到「No such file」，不知道是哪个文件 | `map_err` / `with_context` 附加路径、ID 等上下文 |
| `?` 类型不匹配 | 编译错误「the `?` operator can only be applied to ... that implements From」 | 给目标错误实现 `From<源错误>`，或用 `map_err` 显式转换 |
| `main` 返回 `Result` 直接交差 | 用户看到的是 Debug 格式而非友好提示 | 正式程序在 `main` 内 `match` 后打印 `Display` 信息再 `exit(1)` |
| 把可恢复错误当 bug `panic!` | 用户少输一个参数程序就崩 | 按决策表判断，外部输入永远走 `Result` |
