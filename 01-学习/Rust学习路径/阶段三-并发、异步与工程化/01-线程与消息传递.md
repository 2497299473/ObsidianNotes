## 1. 创建线程：spawn 与 join

`std::thread::spawn` 接收一个闭包，在一个新的 OS 线程中执行它，并返回 `JoinHandle`。对句柄调用 `join()` 会阻塞当前线程直到子线程结束，同时还能捕获子线程中发生的 panic。

```rust
use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..=3 {
            println!("子线程: {i}");
            thread::sleep(Duration::from_millis(100));
        }
        42 // 闭包的返回值可以通过 join 取回
    });

    for i in 1..=3 {
        println!("主线程: {i}");
        thread::sleep(Duration::from_millis(50));
    }

    // 等待子线程结束并拿到返回值
    let result = handle.join().expect("子线程 panic 了");
    println!("子线程返回值: {result}");
}
```

要点：
- `join()` 返回 `Result<T, Box<dyn Any + Send>>`：成功时 `Ok` 携带闭包返回值；子线程 panic 时为 `Err`
- 主线程退出会直接终止整个进程，**不 join 的子线程可能根本没跑完**
- 一个线程的 panic 不会拖垮其他线程——每个线程的 panic 是相互隔离的

> 💡 提示：子线程 panic 时，主线程可以通过 `handle.join().is_err()` 感知并决定重试或上报错误，而不是让整个程序随之崩溃。

## 2. move 闭包：把所有权带进线程

传给 `spawn` 的闭包可能在当前函数返回之后仍在执行，因此默认情况下它不能借用局部变量。加上 `move` 关键字后，闭包捕获的变量会被移动进闭包，所有权随之转移给新线程：

```rust
use std::thread;

fn main() {
    let name = String::from("Rust");

    let handle = thread::spawn(move || {
        // name 的所有权已移入闭包，可以放心使用
        println!("hello, {name}");
    });

    handle.join().unwrap();

    // 下一行无法编译：name 的所有权已经移走
    // println!("{name}");
}
```

这正是 Rust「无畏并发（fearless concurrency）」的体现：**数据竞争在编译期就被所有权系统阻止**。数据竞争需要同时满足三个条件——多线程同时访问、至少一方在写、没有同步机制——而借用检查器让这类代码根本无法通过编译：

```rust
use std::thread;

fn main() {
    let mut data = vec![1, 2, 3];

    // 编译错误：spawn 的闭包可能活得比 main 久，
    // 不允许借用局部变量 data
    let handle = thread::spawn(|| {
        data.push(4);
    });

    data.push(5);
    handle.join().unwrap();
}
```

编译器的逻辑是：闭包可能在 `main` 返回后才执行，届时对局部变量的引用就成了悬垂引用。如果确实需要共享数据，要用下一课的 `Arc<Mutex<T>>`；或者干脆用通道把所有权「寄」过去。

## 3. mpsc 通道：线程间传递数据

`std::sync::mpsc` 提供多生产者、单消费者（Multiple Producer, Single Consumer）通道。`channel()` 返回 `(tx, rx)` 一对端点：`tx.send(value)` 把值的所有权移入通道，`rx.recv()` 阻塞接收。

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let (tx, rx) = mpsc::channel();

    // clone 发送端即可得到多个生产者
    let tx2 = tx.clone();

    thread::spawn(move || {
        tx.send(String::from("来自线程 1")).unwrap();
    });

    thread::spawn(move || {
        tx2.send(String::from("来自线程 2")).unwrap();
    });

    // 关键：丢弃主线程手里的原始 tx，
    // 否则所有发送端并未全部关闭，rx 的迭代不会终止
    drop(tx);

    // 把接收端当迭代器用：直到所有发送端都被 drop 才结束
    for msg in rx {
        println!("收到: {msg}");
    }
}
```

要点：
- `send` 之后值的所有权发生转移，发送方不能再使用该值
- `recv()` 返回 `Result<T, RecvError>`；所有发送端都被 drop 后，`for msg in rx` 迭代形式自动结束
- 接收端先被 drop 时，`send()` 会返回 `Err`——这就是「通道断开」

### 实战：工作线程汇总结果

把数据分组，每个工作线程处理一组并通过通道回传结果，主线程汇总：

```rust
use std::sync::mpsc;
use std::thread;

fn main() {
    let chunks: Vec<Vec<i64>> = vec![
        vec![1, 2, 3],
        vec![10, 20, 30],
        vec![100, 200, 300],
    ];

    let (tx, rx) = mpsc::channel();

    for (idx, chunk) in chunks.into_iter().enumerate() {
        let tx = tx.clone(); // 每个工作线程持有自己的发送端
        thread::spawn(move || {
            let sum: i64 = chunk.iter().sum();
            tx.send((idx, sum)).expect("接收端先被 drop 了");
        });
    }
    drop(tx); // 丢弃原始发送端，否则 rx 的循环永不结束

    let mut total: i64 = 0;
    for (idx, sum) in rx {
        println!("第 {idx} 组的和 = {sum}");
        total += sum;
    }
    println!("总和 = {total}"); // 666
}
```

> 💡 提示：这个「拆分 → 并行计算 → 汇总」的模式是后续毕业项目中并发任务处理的雏形，也是理解 rayon 数据并行的基础。

## 4. thread::scope 作用域线程（1.63+）

Rust 1.63 之前，`spawn` 出来的线程无法借用局部变量，只能 move 或 clone。`std::thread::scope` 解决了这个问题：作用域内创建的所有线程会在作用域结束前**自动 join**，因此闭包可以安全地借用栈上的数据：

```rust
use std::thread;

fn main() {
    let data = vec![1, 2, 3, 4, 5, 6];

    thread::scope(|s| {
        for chunk in data.chunks(2) {
            // 借用 chunk（data 的切片），在作用域内是合法的
            s.spawn(move || {
                let partial: i32 = chunk.iter().sum();
                println!("部分和: {partial}");
            });
        }
        // 也可以直接不可变借用主线程的变量（多个不可变借用可共存）
        s.spawn(|| println!("data 长度 = {}", data.len()));
    }); // 作用域结束：自动等待所有子线程完成

    println!("所有子线程已结束");
}
```

适用场景：
- 需要借用栈上数据的短时并行任务，省去 Arc/clone 的开销
- 希望自动 join、杜绝「忘记等待」的场景

## 5. 与 Go goroutine 的对比

如果你有其他语言背景，下表可以帮助建立直觉：

| 对比项 | Rust std::thread | Go goroutine |
|--------|------------------|--------------|
| 调度模型 | OS 线程（1:1 映射） | 运行时 M:N 调度的用户态轻量线程 |
| 内存开销 | 每线程约 2MB 栈 | 初始栈约 2-8KB，可动态增长 |
| 数量级 | 数十至数百为宜 | 可轻松开数万、数十万 |
| 数据竞争防护 | 编译期由所有权（Send/Sync）阻止 | 默认可共享，需 `-race` 检测器兜底 |
| 通信方式 | mpsc 通道 / Arc<Mutex<T>> | channel（CSP 思想） |
| 轻量异步 | 需 async 运行时（下一课的 tokio） | 语言运行时内建 |

> 💡 提示：从 Go 转来的读者可以把 Rust 的 `spawn` 理解为「重量级 goroutine」；海量并发任务请交给 tokio::spawn 的异步任务，而不是 OS 线程。

## 常见陷阱

| 陷阱 | 表现 | 对策 |
|------|------|------|
| spawn 闭包借用局部变量 | 编译错误「closure may outlive the current function」 | 用 `move` 转移所有权，或改用 `thread::scope` |
| 忘记 join | 主线程先退出，子线程输出不完整甚至丢失 | 收尾统一 `handle.join()`，或用 scope 自动 join |
| 通道断开 | `send().unwrap()` panic（接收端已 drop） | 用 match 处理 send 错误，保证接收端生命周期足够长 |
| 忘记 drop 原始 tx | `for msg in rx` 永久阻塞（死锁） | clone 之后 drop 原始 tx，或把原始 tx 直接 move 进第一个线程 |
| move 之后继续使用变量 | 编译错误「value used here after move」 | 提前规划所有权；确需共享请学下一课的 Arc<Mutex<T>> |
