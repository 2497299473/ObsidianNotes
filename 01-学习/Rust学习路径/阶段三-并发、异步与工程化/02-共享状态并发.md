## 1. Mutex<T>：互斥锁与 RAII 自动解锁

`Mutex<T>`（mutual exclusion）保证同一时刻只有一个线程能访问其内部数据。访问前必须调用 `lock()` 获取锁，它返回一个 `MutexGuard`：

```rust
use std::sync::Mutex;

fn main() {
    let counter = Mutex::new(0);

    {
        // lock() 阻塞直到拿到锁，返回 MutexGuard<i32>
        let mut guard = counter.lock().unwrap();
        *guard += 1; // guard 实现了 DerefMut，通过 *guard 读写内部数据
        println!("锁内读值: {}", *guard);
    } // guard 在这里被 drop，锁自动释放（RAII）

    println!("最终值: {}", *counter.lock().unwrap());
}
```

设计精髓：
- **不拿锁就碰不到数据**：编译器强制「先 lock，后访问」，不存在忘加锁的裸数据
- **自动解锁**：`MutexGuard` 离开作用域被 drop 时释放锁，无需手写 unlock，也不会忘记解锁
- `lock()` 返回 `Result`：如果之前持锁的线程 panic 了，Mutex 会被标记为「中毒（poisoned）」，后续 `lock()` 返回 `Err`

> 💡 提示：即使用单线程，Mutex 的这个「守卫即权限」模式也值得体会——它是 Rust 用类型系统管理可变性的又一例证。

## 2. Arc<T> 与经典组合 Arc<Mutex<T>>

多线程共享一份可变数据的标准姿势是 `Arc<Mutex<T>>`：
- `Arc`（Atomic Reference Counting）：原子引用计数指针，让多个线程共同持有所有权，`Arc::clone` 只增加计数
- `Mutex`：保证同一时刻只有一个线程能修改内部数据

```rust
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    // 一个多线程共享的任务列表
    let tasks = Arc::new(Mutex::new(Vec::<String>::new()));
    let mut handles = Vec::new();

    for i in 1..=4 {
        let tasks = Arc::clone(&tasks); // 只克隆引用计数，不复制数据
        handles.push(thread::spawn(move || {
            let mut guard = tasks.lock().unwrap();
            guard.push(format!("任务-{i}"));
            // guard 在闭包末尾 drop，锁自动释放
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    println!("任务列表: {:?}", tasks.lock().unwrap());
    // 任务列表: ["任务-1", "任务-2", "任务-3", "任务-4"]（顺序可能不同）
}
```

为什么不用 `Rc`？`Rc` 的引用计数**不是原子操作**，两个线程同时 clone/drop 会把计数算错，导致提前释放或内存泄漏。`Arc` 用原子指令换来线程安全，代价是微小的性能开销。

| 需求 | 单线程工具 | 多线程替代 |
|------|-----------|-----------|
| 共享所有权 | `Rc<T>` | `Arc<T>` |
| 内部可变性 | `RefCell<T>` | `Mutex<T>` / `RwLock<T>` |

## 3. RwLock：读写锁

`Mutex` 不区分读写，读多写少的场景下所有读者也要排队。`RwLock<T>` 允许**任意多个读者**或**唯一一个写者**：

```rust
use std::sync::{Arc, RwLock};
use std::thread;

fn main() {
    let config = Arc::new(RwLock::new(String::from("debug")));
    let mut handles = Vec::new();

    // 多个读者可以同时持有读锁
    for i in 0..3 {
        let config = Arc::clone(&config);
        handles.push(thread::spawn(move || {
            let value = config.read().unwrap();
            println!("读者 {i} 看到: {value}");
        }));
    }

    for h in handles {
        h.join().unwrap();
    }

    // 写锁是独占的：拿到它时不能有其他读者或写者
    *config.write().unwrap() = String::from("release");
    println!("最终配置: {}", *config.read().unwrap());
}
```

选型建议：读远多于写（配置、缓存）用 `RwLock`；读写相当或临界区极短，直接用 `Mutex` 往往更快（读写锁内部开销更大，且要防写者饥饿）。

## 4. Send 与 Sync：为什么 Rc/RefCell 不能跨线程

两个标记 trait 划定了类型的跨线程能力：
- `Send`：类型 `T` 的**所有权**可以移动到另一个线程。绝大多数类型都是 Send
- `Sync`：类型 `T` 可以通过**引用**跨线程共享，等价于 `&T: Send`

编译器会根据结构体的字段自动推导 Send/Sync。一旦某个类型不满足，跨线程使用会直接编译失败：

```rust
use std::rc::Rc;
use std::thread;

fn main() {
    let v = Rc::new(vec![1, 2, 3]);
    // 编译错误：Rc<Vec<i32>> cannot be sent between threads safely
    thread::spawn(move || {
        println!("{:?}", v);
    });
}
```

原因：
- `Rc<T>` 不是 Send：它的引用计数是普通整数，并发 clone/drop 会产生数据竞争、算错计数
- `RefCell<T>` 不是 Sync：它的借用检查是运行时的、非原子的，两个线程同时 `borrow_mut` 无法被发现，会产生未定义行为

> 💡 提示：这正是「无畏并发」的另一面——不是运行时帮你查，而是编译期直接拒绝。对照上一课：mpsc 通道的 `send` 也要求 `T: Send`。

## 5. 死锁与并发模型选型

死锁的典型成因：**多个锁的获取顺序不一致**。下面的代码有真实的死锁风险：

```rust
use std::sync::{Arc, Mutex};
use std::thread;
use std::time::Duration;

fn main() {
    let a = Arc::new(Mutex::new(1));
    let b = Arc::new(Mutex::new(2));

    let (a1, b1) = (Arc::clone(&a), Arc::clone(&b));
    let t1 = thread::spawn(move || {
        let _ga = a1.lock().unwrap(); // 先锁 a
        thread::sleep(Duration::from_millis(10));
        let _gb = b1.lock().unwrap(); // 再等 b
    });

    let t2 = thread::spawn(move || {
        let _gb = b.lock().unwrap(); // 先锁 b
        let _ga = a.lock().unwrap(); // 再等 a —— 与 t1 互相等待
    });

    t1.join().unwrap();
    t2.join().unwrap();
}
```

避免策略：
1. **统一加锁顺序**：所有线程按相同顺序获取多把锁
2. **缩短临界区**：锁内只做必要计算，绝不在持锁时做 IO、睡眠
3. **try_lock / 超时**：拿不到锁就退避重试，避免无限等待
4. **优先消息传递**：用通道转移所有权，从源头消灭共享可变状态

### 消息传递 vs 共享状态

| 维度 | 消息传递（mpsc） | 共享状态（Arc<Mutex<T>>） |
|------|------------------|--------------------------|
| 数据所有权 | 随消息转移，归属清晰 | 多方共享，需靠锁维持纪律 |
| 死锁风险 | 低 | 多锁组合时明显升高 |
| 典型场景 | 任务分发、结果汇总、流水线 | 计数器、缓存、频繁读写的状态 |
| 开销来源 | 值的移动/分配、通道队列 | 锁竞争、等待 |
| 心智模型 | Actor / CSP 风格 | 传统加锁并发 |

## 常见陷阱

| 陷阱 | 表现 | 对策 |
|------|------|------|
| MutexGuard 没有及时 drop | 锁被长期持有，其他线程卡在 lock() | 用 `{}` 限制 guard 作用域，或显式 `drop(guard)` |
| 跨 await 持 std::sync::Mutex 锁 | 异步任务切换后锁无法释放（下一课详述） | 跨 await 用 `tokio::sync::Mutex`，或保证锁不跨 await |
| 盲目 unwrap 锁结果 | 遇到中毒锁直接 panic | `match lock()` 分支处理，或用 `into_inner()` 抢救数据 |
| 持锁期间做耗时 IO | 临界区过长，吞吐骤降 | 先在锁内 clone 数据，锁外做 IO，再回锁写结果 |
| Arc<Mutex<T>> 层层嵌套 | 代码难读、锁粒度混乱 | 重新设计数据结构，按职责拆分锁 |
