## 1. 单元测试：#[test]、断言宏与 #[cfg(test)]

Rust 内建测试框架：任何标注 `#[test]` 的函数都会被 `cargo test` 执行。惯例是把测试放在同文件的 `#[cfg(test)] mod tests` 中——`#[cfg(test)]` 让该模块**只在测试构建时编译**，不进入发布产物：

```rust
// src/lib.rs
pub fn add(a: i64, b: i64) -> i64 {
    a + b
}

pub fn divide(a: f64, b: f64) -> Result<f64, String> {
    if b == 0.0 {
        Err(String::from("除数为零"))
    } else {
        Ok(a / b)
    }
}

#[cfg(test)]
mod tests {
    use super::*; // 引入外层的所有项，包括私有项

    #[test]
    fn add_works() {
        assert_eq!(add(2, 3), 5, "2 + 3 应该等于 5");
    }

    #[test]
    fn divide_by_zero_is_err() {
        assert!(divide(1.0, 0.0).is_err());
    }

    #[test]
    #[should_panic(expected = "除数为零")]
    fn unchecked_divide_panics() {
        // 验证旧式 unwrap 代码在除零时确实 panic
        divide(1.0, 0.0).expect("除数为零");
    }
}
```

三个断言宏：
- `assert!(条件)`：条件为假则失败
- `assert_eq!(左, 右)` / `assert_ne!(左, 右)`：相等/不等断言，失败时打印两侧的值
- `#[should_panic(expected = "...")]`：断言测试**应当 panic**，且 panic 信息包含指定子串——用来验证错误路径

## 2. 运行测试与集成测试

常用命令：

```bash
cargo test                    # 运行全部测试
cargo test divide             # 只运行名字包含 divide 的测试
cargo test -- --nocapture     # 显示测试里的 println! 输出
cargo test -- --test-threads=1  # 串行运行（默认是并行）
cargo test -- --ignored       # 运行被 #[ignore] 标记的测试
```

**集成测试**放在 `tests/` 目录：每个文件会被编译成独立的 crate，只能访问库的**公开 API**——这模拟了真实用户的使用方式：

```rust
// tests/api.rs
use mylib::divide; // mylib 是 Cargo.toml 里的包名

#[test]
fn it_divides() {
    assert_eq!(divide(10.0, 4.0).unwrap(), 2.5);
}
```

| 类型 | 位置 | 能访问 | 用途 |
|------|------|--------|------|
| 单元测试 | src/ 内 `#[cfg(test)]` 模块 | 包括私有项 | 验证内部逻辑、边界条件 |
| 集成测试 | tests/ 目录 | 仅公开 API | 验证模块协作、端到端行为 |
| 文档测试 | `///` 中的代码块 | 仅公开 API | 保证文档示例可编译可运行 |

## 3. 文档注释与 cargo doc

`///` 开头的注释会成为其后条目的文档，支持 Markdown，并可用 `cargo doc --open` 生成 HTML 文档。**文档中的代码块会被当作测试运行**（文档测试）：

```rust
/// 计算已完成任务的百分比。
///
/// # 参数
/// * `done` - 已完成的任务数
/// * `total` - 任务总数
///
/// # 返回值
/// 返回 0.0 到 100.0 的百分比；`total` 为 0 时返回 0.0
///
/// # 示例
/// ```
/// assert_eq!(mylib::completion_rate(1, 4), 25.0);
/// ```
pub fn completion_rate(done: u32, total: u32) -> f64 {
    if total == 0 {
        return 0.0;
    }
    done as f64 / total as f64 * 100.0
}
```

常用文档小节：`# Examples`、`# Panics`、`# Errors`、`# Safety`——rustdoc 会识别这些标题。写库给别人用时，凡是可能 panic 或返回 Err 的公开函数，都应说明条件。

## 4. 模块组织、workspace 与工具链

模块系统回顾（文件组织）：

```text
myapp/
├── Cargo.toml
├── src/
│   ├── main.rs        # 二进制入口
│   ├── lib.rs         # 库根：pub mod 声明
│   ├── tasks.rs       # mod tasks
│   └── storage/
│       ├── mod.rs     # mod storage
│       └── json.rs    # storage::json
└── tests/
    └── api.rs         # 集成测试
```

```rust
// lib.rs
pub mod tasks;
pub mod storage;

// main.rs
use myapp::tasks::Task;
use myapp::storage::json;
```

**workspace**：多个相关 crate 共享一个仓库、一份 Cargo.lock 与目标目录，适合「核心库 + CLI + 服务端」这类结构（毕业项目后期的形态）：

```toml
# 根目录 Cargo.toml
[workspace]
members = ["crates/core", "crates/cli", "crates/server"]
resolver = "2"
```

代码质量工具：

```bash
cargo fmt            # rustfmt：统一代码格式（建议在编辑器保存时自动运行）
cargo clippy         # clippy：官方 lint，能发现性能与惯用法问题
cargo clippy --fix   # 自动修复部分警告
```

## 5. 发布流程与常用生态

发布到 crates.io 的关键点：

```toml
[package]
name = "mylib"
version = "0.1.0"     # 语义化版本：主版本.次版本.修订号
license = "MIT"
description = "一个简洁的任务管理核心库"
repository = "https://github.com/you/mylib"
```

```bash
cargo login <token>          # 一次性登录（token 从 crates.io 获取）
cargo publish --dry-run      # 打包预检：检查缺文件、版本号等
cargo publish                # 正式发布（同一版本号不可重复发布，也不可撤回）
```

语义化版本约定：`0.x.y` 阶段 API 可以随意破坏；`1.0` 之后，破坏性变更必须升主版本。依赖声明 `tokio = "1"` 表示接受 `>=1.0.0, <2.0.0` 的兼容更新。

常用生态清单（按毕业项目会用到的顺序）：

| Crate | 用途 | 什么时候会用到 |
|-------|------|----------------|
| serde / serde_json | 序列化与反序列化 | 任务数据存成 JSON、HTTP API |
| clap | 命令行参数解析 | 毕业项目 CLI 的 add/list/done 子命令 |
| tokio | 异步运行时 | 并发任务、网络请求 |
| axum | Web 框架 | 任务的 HTTP API 服务 |
| sqlx | 异步数据库访问 | 任务持久化（SQLite/Postgres） |
| anyhow / thiserror | 错误处理 | 应用层用 anyhow，库层用 thiserror |
| rayon | 数据并行 | CPU 密集的批量处理 |

> 💡 提示：`anyhow` 适合写应用（错误一把抓、方便带上下文），`thiserror` 适合写库（让调用方能精确 match 错误类型）。

## 常见陷阱

| 陷阱 | 表现 | 对策 |
|------|------|------|
| 测试依赖执行顺序或共享状态 | 单独跑通过、全量跑随机失败 | 默认测试是并行的：用独立临时目录，或 `--test-threads=1` |
| pub 过度暴露 | 内部实现变成公开 API，重构寸步难行 | 默认私有；模块间共享用 `pub(crate)` |
| 忽略 clippy 警告 | 警告越积越多，真问题被淹没 | 把 clippy 纳入 CI，新代码零警告 |
| 文档示例过时 | 用户照抄文档报错 | 让示例成为文档测试，`cargo test` 自动验证 |
| 集成测试引用私有函数 | 编译错误 | 集成测试只能走公开 API；私有逻辑的测试放回单元测试 |

## ✏️ 综合练习

### 练习 1：概念复述
1. 单元测试和集成测试分别放在哪里？它们在「能访问哪些项」上有什么区别？
2. `#[cfg(test)]` 的作用是什么？如果去掉它会发生什么？
3. 语义化版本中，什么变化必须升主版本号？

### 练习 2：代码实现
在 `code/` 目录新建 cargo 项目（如 `code/testing-demo/`），实现一个 `parse_task(s: &str) -> Result<Task, String>` 函数（把 `"1,写笔记,false"` 解析成结构体），并为它编写至少 4 个测试：正常输入、字段缺失、非法布尔值（用 `#[should_panic]` 或断言 Err），并给函数写上带 `# Examples` 的文档注释，确认 `cargo test` 与 `cargo doc --open` 均通过。

### 练习 3：扩展思考
「文档即测试」是 Rust 生态的惯例：文档里的代码示例会被编译执行。对比你见过的其他语言文档，这种做法的长期收益是什么？又有什么局限（比如示例依赖外部服务时）？
