## 场景 1：本地开发环境一键搭建

### 场景描述

新同事入职，配环境要一天。用 Docker Compose 把 Web + DB + Cache 一键拉起，5 分钟开始写代码。

### 架构选型

| 候选 | 为什么（不）选 |
|------|--------------|
| Compose + Volume + Watch | ✅ 声明式、可复现、热更新 |
| Vagrant | ❌ 虚拟机太重，启动慢 |
| 手动安装 | ❌ 不可复现，团队每个人环境不同 |

### 完整代码

```yaml
# compose.yaml
services:
  web:
    build:
      context: .
      target: dev
    ports:
      - "5000:5000"
    environment:
      - DB_HOST=db
      - DB_NAME=appdb
      - DB_USER=app
      - DB_PASSWORD=devpass
      - REDIS_URL=redis://cache:6379
      - DEBUG=1
    depends_on:
      db:
        condition: service_healthy
      cache:
        condition: service_healthy
    networks: [frontend, backend]
    develop:
      watch:
        - action: sync
          path: ./src
          target: /app/src
        - action: rebuild
          path: ./requirements.txt
    healthcheck:
      test: ["CMD", "curl", "-f", "http://localhost:5000/health"]
      interval: 10s
      timeout: 3s
      retries: 3

  db:
    image: postgres:16-alpine
    environment:
      POSTGRES_DB: appdb
      POSTGRES_USER: app
      POSTGRES_PASSWORD: devpass
    volumes:
      - db-data:/var/lib/postgresql/data
      - ./db/init.sql:/docker-entrypoint-initdb.d/init.sql:ro
    ports:
      - "5432:5432"
    networks: [backend]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app -d appdb"]
      interval: 5s
      timeout: 3s
      retries: 5

  cache:
    image: redis:7-alpine
    command: redis-server --save 60 1 --loglevel verbose
    volumes: [cache-data:/data]
    ports: ["6379:6379"]
    networks: [backend]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 3

volumes:
  db-data:
  cache-data:

networks:
  frontend: { driver: bridge }
  backend: { driver: bridge }
```

```dockerfile
# Dockerfile（多阶段，对应 compose 的 build.target: dev）

FROM python:3.12-slim AS base
WORKDIR /app
ENV PYTHONUNBUFFERED=1

# 构建阶段：只装依赖（requirements.txt 不变时可命中缓存）
FROM base AS build
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

# 开发阶段：compose 的 target: dev 指向这里
FROM build AS dev
ENV PATH=/root/.local/bin:$PATH
# 安装 curl 供 healthcheck 使用
RUN apt-get update && apt-get install -y --no-install-recommends curl && rm -rf /var/lib/apt/lists/*
COPY src ./src
CMD ["python", "src/app.py"]

# 生产阶段：不带调试工具，只保留运行所需
FROM base AS prod
COPY --from=build /root/.local /root/.local
ENV PATH=/root/.local/bin:$PATH
COPY src ./src
CMD ["python", "src/app.py"]
```

```bash
docker compose up -d       # 一键启动
docker compose watch       # 热更新
docker compose logs -f web # 查看日志
```

### 生产注意事项

> [!warning] 开发环境与生产环境隔离
> 1. 开发暴露端口到宿主机方便调试，生产只暴露反向代理端口
> 2. 开发用 `build`，生产用 `image`（从仓库拉取）
> 3. 开发开 DEBUG，生产关闭
> 4. 开发密码和生产密码分开管理

## 场景 2：CI/CD 流水线

### 场景描述

代码 push 后自动构建镜像、跑测试、扫描漏洞、推送到仓库、部署。Docker 是 CI/CD 的核心载体。

### 完整代码

```dockerfile
# Dockerfile（多阶段：test → runtime）
FROM python:3.12-slim AS builder
WORKDIR /app
COPY requirements.txt .
RUN pip install --user --no-cache-dir -r requirements.txt

FROM python:3.12-slim AS test
COPY --from=builder /root/.local /root/.local
WORKDIR /app
COPY . .
RUN /root/.local/bin/pytest tests/ --junitxml=test-results.xml

FROM python:3.12-slim AS runtime
RUN groupadd -r app && useradd -r -g app -u 1000 app
COPY --from=builder /root/.local /home/app/.local
WORKDIR /app
COPY --from=test /app .
ENV PATH=/home/app/.local/bin:$PATH
USER app
CMD ["python", "-m", "uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

```yaml
# .github/workflows/ci.yml
name: CI/CD Pipeline
on:
  push:
    branches: [main, develop]
  pull_request:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - name: Run tests
        uses: docker/build-push-action@v5
        with:
          context: .
          target: test
          load: true
          tags: app:test
          cache-from: type=gha
          cache-to: type=gha,mode=max

  security-scan:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Build image
        uses: docker/build-push-action@v5
        with: { context: ., load: true, tags: app:scan }
      - name: Trivy scan
        uses: aquasecurity/trivy-action@master
        with:
          image-ref: app:scan
          severity: CRITICAL,HIGH
          exit-code: 1

  build-push:
    needs: security-scan
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - name: Build and push
        uses: docker/build-push-action@v5
        with:
          context: .
          target: runtime
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max
```

### 生产注意事项

> [!warning] CI/CD 常见陷阱
> 1. CI 镜像 tag 用 `latest`，无法追溯 → 用 Git commit SHA
> 2. 密钥写在 YAML 里 → 永远用 CI 平台的 secrets
> 3. 推送前不跑安全扫描 → 集成 Trivy 作为门禁
> 4. 不用缓存，每次全量构建 → 用 BuildKit `cache-from`/`cache-to`

## 场景 3：多架构镜像构建

### 场景描述

用户有 x86 也有 ARM（Apple Silicon、树莓派）。需要构建一个镜像同时支持 `linux/amd64` 和 `linux/arm64`。

### 完整代码

```bash
# 创建 buildx builder
docker buildx create --name multiarch --driver docker-container --use
docker buildx inspect --bootstrap

# 构建多架构镜像并推送
docker buildx build \
  --platform linux/amd64,linux/arm64 \
  -t myrepo/app:v1.0 \
  --push .

# 验证多架构 manifest
docker buildx imagetools inspect myrepo/app:v1.0
```

```dockerfile
FROM --platform=$BUILDPLATFORM golang:1.22-alpine AS builder
ARG TARGETOS
ARG TARGETARCH
WORKDIR /app
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 GOOS=$TARGETOS GOARCH=$TARGETARCH \
    go build -ldflags="-s -w" -o /app/server .

FROM alpine:3.20
COPY --from=builder /app/server /usr/local/bin/server
ENTRYPOINT ["server"]
```

### 生产注意事项

> [!warning] 多架构构建陷阱
> 1. 构建多架构镜像比单架构慢 2-3 倍
> 2. 本地用 QEMU 模拟，生产建议用原生 ARM builder（如 AWS CodeBuild arm64 实例）
> 3. 基础镜像必须有对应架构 tag

## 场景 4：容器日志收集

### 场景描述

容器化后日志分散在各节点。需要集中收集、存储、查询。采用轻量方案：Fluent Bit + Loki + Grafana。

### 完整代码

```yaml
# compose.yaml
services:
  fluent-bit:
    # 自带 Loki 输出插件；官方 fluent/fluent-bit 镜像不含 loki OUTPUT 插件
    image: grafana/fluent-bit-plugin
    volumes:
      - /var/lib/docker/containers:/var/lib/docker/containers:ro
      - ./fluent-bit.conf:/fluent-bit/etc/fluent-bit.conf:ro
    networks: [logging]

  loki:
    image: grafana/loki:2.9.0
    command: -config.file=/etc/loki/local-config.yaml
    volumes: [loki-data:/loki]
    networks: [logging]

  grafana:
    image: grafana/grafana:10.2.0
    ports: ["3000:3000"]
    environment:
      - GF_SECURITY_ADMIN_PASSWORD=admin
    volumes: [grafana-data:/var/lib/grafana]
    networks: [logging]

volumes:
  loki-data:
  grafana-data:

networks:
  logging: { driver: bridge }
```

```ini
# fluent-bit.conf
[SERVICE]
  Flush 5
  Log_Level info

[INPUT]
  Name tail
  Path /var/lib/docker/containers/*/*-json.log
  Parser docker
  Tag docker.*

[FILTER]
  Name grep
  Match docker.*
  Exclude log /^\s*$/

[OUTPUT]
  Name loki
  Match docker.*
  Host loki
  Port 3100
  Labels job=containers
```

> [!warning] Docker Desktop 用户注意
> Windows/Mac 的 Docker Desktop 中，Docker 守护进程运行在虚拟机里，宿主机的 `/var/lib/docker/containers` 无法直接挂载到真实的容器日志。本节日志采集方案主要适用于 Linux 宿主机。

### 生产注意事项

> [!warning] 日志收集陷阱
> 1. 不设日志轮转，磁盘被撑爆 → `--log-opt max-size=10m --log-opt max-file=3`
> 2. 敏感日志不脱敏 → 在 Fluent Bit 中配置 filter 脱敏
> 3. 日志量太大，Loki 查询慢 → 配置日志分级和告警

## 场景 5：隔离测试沙箱

### 场景描述

运行用户提交的不可信代码，需要严格隔离。

### 完整代码

```bash
# 创建隔离网络
docker network create sandbox

# 启动测试容器，严格限制
docker run -d \
  --name test-sandbox \
  --network sandbox \
  --memory="256m" \
  --cpus="0.5" \
  --read-only \
  --tmpfs /tmp:size=64m,mode=1777 \
  --cap-drop ALL \
  --pids-limit=50 \
  -u 1000:1000 \
  --security-opt no-new-privileges \
  --rm \
  myapp:test
```

### 生产注意事项

> [!warning] 沙箱安全注意
> 1. 用 `--network none` 或隔离网络阻断网络访问
> 2. 设置超时（`--stop-timeout 30`）和内存上限
> 3. 更严格场景考虑用 gVisor 或 Kata Containers（更强的隔离级别）

## 场景 6：数据库容器化

### 场景描述

数据库容器化需要解决数据持久化、备份、健康检查问题。

### 完整代码

```yaml
services:
  mysql:
    image: mysql:8.0
    environment:
      MYSQL_ROOT_PASSWORD: devrootpass
      MYSQL_DATABASE: appdb
    volumes:
      - mysql-data:/var/lib/mysql
      - ./backups:/backups
    ports: ["3306:3306"]
    healthcheck:
      test: ["CMD-SHELL", "mysqladmin ping -h localhost"]
      interval: 10s
    deploy:
      resources:
        limits: { memory: 1G }

  # 定时备份
  backup:
    image: mysql:8.0
    command: >
      sh -c "while true; do
        mysqldump -h mysql -u root -pdevrootpass appdb > /backups/db-$$(date +%Y%m%d).sql;
        sleep 86400;
      done"
    volumes: ["./backups:/backups"]
    depends_on:
      mysql:
        condition: service_healthy

volumes:
  mysql-data:
```

### 生产注意事项

> [!warning] 数据库容器化注意
> 1. **Volume 不是备份** → 定期 `docker run --rm -v db-data:/data alpine tar cvf /backup/db.tar` 做离线备份
> 2. 生产数据库建议用云服务（RDS/Cloud SQL），容器仅用于开发测试
> 3. 密码用 Docker secrets 或 `--env-file` 管理

## 场景 7：Redis 缓存容器化

### 完整代码

```yaml
services:
  redis:
    image: redis:7-alpine
    command: >
      redis-server
      --save 60 1000
      --appendonly yes
      --maxmemory 256mb
      --maxmemory-policy allkeys-lru
    volumes: [redis-data:/data]
    ports: ["6379:6379"]
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      timeout: 3s
      retries: 3

volumes:
  redis-data:
```

### 生产注意事项

> [!warning] Redis 容器化注意
> 1. 生产环境设置密码或启用 ACL
> 2. 启用持久化（AOF + RDB）
> 3. 限制内存 `maxmemory` + 淘汰策略

## 场景 8：静态站点托管

### 完整代码

```dockerfile
# 多阶段构建：Node 构建 → Nginx 托管
FROM node:20-alpine AS builder

COPY --from=builder /app/dist /usr/share/nginx/html
```

```nginx
# nginx.conf
server {
    listen 80;
    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ /index.html;  # SPA 路由支持
    }

    gzip on;
    gzip_types text/css application/javascript application/json;
}
```

## 场景 9：批处理任务容器化

### 场景描述

定时运行的数据处理任务（如每日报表生成）。

### 完整代码

```yaml
services:
  etl-job:
    image: etl-tool:v1
    command: ["python", "etl.py", "--date", "${DATE:-2026-01-01}"]
    environment:
      - DB_URL=postgres://user:pass@db:5432/mydb
    volumes: ["./data:/data"]
    restart: "no"  # 跑完不重启
```

`${DATE:-2026-01-01}` 是 Compose 变量插值：解析 yaml 时从 `.env` 文件或 shell 环境变量读取 `DATE`，未设置就用默认值 `2026-01-01`。不要写成 `$(DATE)`——exec 数组不经过 shell，`$(...)` 也不是 Compose 插值语法，只会原样传入容器。

```bash
# 手动执行（不设置 DATE 时用默认日期）
docker compose up etl-job

# 指定日期执行（DATE 由 Compose 变量插值代入）
DATE=2026-07-01 docker compose run --rm etl-job

# 定时任务（Cron）
0 2 * * * cd /path/to/project && docker compose run --rm etl-job
```

## 场景 10：私有镜像仓库搭建

### 场景描述

不想用 Docker Hub，自己搭私有仓库。

### 方案 A：简单 registry（开发用）

```yaml
services:
  registry:
    image: registry:2
    ports: ["5000:5000"]
    volumes: [registry-data:/var/lib/registry]

volumes:
  registry-data:
```

### 方案 B：Harbor（生产级）

```bash
# Harbor 安装（带 UI、漏洞扫描、项目管理、RBAC）
helm repo add harbor https://helm.goharbor.io
helm install harbor harbor/harbor \
  --namespace harbor --create-namespace \
  --set expose.ingress.hosts.core=harbor.example.com \
  --set persistence.persistentVolumeClaim.registry.size=100Gi

# 配置 Docker 信任 Harbor
# /etc/docker/daemon.json
{
  "insecure-registries": ["harbor.example.com"]
}
```

### 生产注意事项

> [!warning] 私有仓库注意
> 1. 生产必须启用 TLS
> 2. 配置身份验证（htpasswd / OAuth / LDAP）
> 3. 考虑 Harbor 替代原生 registry（自带 UI、漏洞扫描、项目管理）

## 🎯 实践练习

### 练习 1：搭建完整开发环境

用场景 1 的 Dockerfile 和 compose.yaml，启动一个 Web + DB + Cache 的完整开发环境：

```bash
# 1. 创建项目目录
mkdir dev-env && cd dev-env

# 2. 准备最小应用代码（Flask 监听 5000，提供 /health 供健康检查）
mkdir src db
cat > src/app.py << 'EOF'
from flask import Flask
app = Flask(__name__)

@app.route("/health")
def health():
    return {"status": "ok"}

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
EOF
echo flask > requirements.txt
echo "-- init sql" > db/init.sql

# 3. 把场景 1 的多阶段 Dockerfile 保存为项目根目录的 Dockerfile
#    （必须包含 dev 阶段，与 compose 的 build.target: dev 对应）

# 4. 创建 compose.yaml（复制场景 1 的完整配置）

# 5. 启动（首次会自动构建 dev 阶段镜像）
docker compose up -d

# 6. 验证所有服务健康
docker compose ps
# 全部显示 Up (healthy)

# 7. 进入 web 容器
docker compose exec web sh

# 8. 清理
docker compose down -v
```

> 💡 **注释**：一条命令启动三个服务 + 网络 + Volume + 健康检查 + 依赖管理。对比手动敲 `docker run` 的痛苦，这就是编排的威力。

**验证标准**：三个服务全部 `Up (healthy)`。

### 练习 2：从 10 个场景中选 3 个实现

建议优先级：
1. **场景 8**（静态站点）——最简单，10 分钟搞定
2. **场景 1**（开发环境）——综合应用 Compose + 网络 + Volume
3. **场景 6**（数据库容器化）——理解 Volume 持久化和备份

> 💡 **注释**：每个场景都是独立的，选你当前最需要的场景优先实现。场景 10 难度最高，建议最后尝试。

## 💡 要点注释

1. **开发环境 ≠ 生产环境**
   - 开发：Bind Mount + Watch + 调试工具
   - 生产：只读镜像 + 资源限制 + 多副本 + 安全加固

2. **镜像版本管理**
   - 永远用具体 tag：`v1.2.3` 而不是 `latest`
   - CI 用 Git SHA：`myapp:${{ github.sha }}`

3. **数据持久化**
   - 数据库、缓存、日志都要用 Volume
   - 定期备份，定期测试恢复

4. **安全是持续过程**
   - 每个场景都要问自己：密钥放哪？权限最小化了吗？资源限制了吗？

## ⚠️ 常见易错点

> [!warning] **坑 1：生产用 docker-compose 而不是 Swarm Stack**
> 单机 Compose 没有自愈和扩缩能力。生产环境用 Swarm Stack 或 K8S。

> [!warning] **坑 2：CI/CD 中密钥泄露**
> 永远用 CI 平台的 secrets，不要写在 YAML 里。

> [!warning] **坑 3：日志默认无限制**
> 不设 `--log-opt max-size=10m --log-opt max-file=3`，磁盘会被撑爆。

> [!warning] **坑 4：数据库容器在生产用 Volume 但不备份**
> Volume 不是备份。定期 `docker run --rm -v vol:/data alpine tar cvf` 备份。

> [!warning] **坑 5：多架构构建不在 CI 中做**
> 本地构建慢且不可复现。应在 CI 中用 buildx 多架构构建。
