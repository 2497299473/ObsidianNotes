## 2. 问题清单

### P0-1｜03 章"最简单的 Dockerfile"五行行内注释 → 第一步 `FROM` 就解析失败

- **位置**：`03-构建你的第一个镜像.md:30-37`
- **原文**：
  ```dockerfile
  FROM python:3.12-alpine            # 1. 以 Python 镜像为基础
  COPY app.py /app/                  # 2. 把你的代码复制进去
  ```
- **问题**：Docker 官方明确规定"**行首**的 `#` 才是注释，行内其它位置的 `#` 一律当作参数"（Dockerfile reference · Format 一节）。`FROM` 只接受 1 个或 3 个参数（`image [AS name]`），这一行被切成 6 个 token，解析器直接报 `FROM requires either one or three arguments`，**构建在第一条指令就停**。COPY 行同理（4 个参数、末参不以 `/` 结尾）；只有 `RUN pip install flask # ...` 侥幸通过（shell 把 `#` 当注释）。这段是本章"你的第一个 Dockerfile"的最前置示例，学习者 100% 会整段复制。
- **同类问题（同一根因，严重度低一档，因为都在 ✅/❌ 对照块里）**：`03:261`、`04:116-123`（5 行）、`08:198`、`11:199` 与 `11:202`。
- **修复建议**：把注释移到独立行（推荐，保留编号信息）：
  ```dockerfile
  # 1. 以 Python 镜像为基础
  FROM python:3.12-alpine
  # 2. 把你的代码复制进去
  COPY app.py /app/
  ```
  并在 `04:113`、`08:188`、`11:198` 的对照块做同样处理；顺手在 03 的易错点里加一条"坑 6：把 `#` 写在指令行尾"。
- **验证方式与结果**：官方文档 <https://docs.docker.com/reference/dockerfile/> —— "BuildKit treats lines that begin with `#` as a comment… A `#` marker anywhere else in a line is treated as an argument."；`FROM` 语法为 `FROM <image> [AS <name>]`。**未实跑**（本机无 docker），结论由解析规则推导，确定性高。

### P1-1｜构建输出描述 `Step 1/5 … CACHED` 与 27.x 默认 BuildKit 不符

- **位置**：`03:178`、`04:190-198`、`labs/lab-03-first-image/README.md:41`、`04:241`（`transferring context: 2.5MB`）
- **原文**：
  > `# Step 2/5: FROM python:3.12-alpine  → CACHED`
  > `# Step 4/5: COPY app.py .            → 重建！（app.py 变了）`
- **问题**：三处叠加错误：
  1. `Step x/y :` 是**已弃用的 legacy builder** 的输出；BuildKit 打印的是 `[+] Building …` 与 `#N [x/y] 指令`，缓存命中显示 `#N CACHED`。
  2. 同一行命令里用了 `--progress=plain`——这是 **buildx/BuildKit 专属选项**（官方 `docker buildx build` 的 `--progress`），也就是说作者写的命令本身就只可能走 BuildKit，输出绝不可能是 `Step x/y`。
  3. 编号也自相矛盾：03 说 `Step 1/5` 是 FROM，04 却写 `Step 2/5: FROM`。
  学习者按 27.x 跑，看不到任何 `Step`，会以为"构建没按预期执行"。
- **修复建议**：统一改成 BuildKit 口径，例如：
  ```
  #8 [4/5] COPY app.py .
  #8 CACHED
  ```
  或更稳妥——**只描述现象不写死编号**："第二次构建时，未变化的步骤会显示 `CACHED` 并瞬间完成"。03:178 的"看到 Step 1/5 说明正在执行"建议改成"看到 `[2/5]`/`CACHED` 之类的进度行说明正在按序执行（27.x 默认 BuildKit）"。
- **验证方式与结果**：官方 `--progress` 选项只存在于 `docker buildx build`（<https://docs.docker.com/reference/cli/docker/buildx/build/>）；legacy builder 输出格式见 Docker 社区实测帖 <https://forums.docker.com/t/using-buildkit-by-default/137851>（`DOCKER_BUILDKIT=0` 才回到旧输出）。**未实跑**。

### P1-4｜`main.go` 两处 SQL 注入（路由参数直接当 GORM 条件）

- **位置**：`Go+Docker综合项目/main.go:279`（`getTodo`）、`:289`、`:306`（`deleteTodo`）
- **原文**：
  ```go
  if err := db.First(&todo, c.Param("id")).Error; err != nil {
  if err := db.Delete(&Todo{}, c.Param("id")).Error; err != nil {
  ```
- **问题**：GORM 的 `First(dest, conds...)` 在收到**字符串**且无法解析为主键时，会把该字符串当成**原始 SQL 条件**拼进 `WHERE`。`c.Param("id")` 未做任何校验/参数化，`DELETE /api/todos/1%20OR%201=1` 会生成 `DELETE FROM todos WHERE 1 OR 1=1`——**一次请求清空整表**。`GET`/`PUT` 分支可被用来越权读取任意行。这是一份"给学习者照抄的生产级模板"，风险被放大。
- **修复建议**：
  ```go
  id, err := strconv.ParseUint(c.Param("id"), 10, 64)
  if err != nil { c.JSON(400, gin.H{"error": "invalid id"}); return }
  if err := db.First(&todo, id).Error; err != nil { … }
  // Delete 同理：db.Delete(&Todo{}, id)
  ```
  另建议 `updateTodo` 只绑定白名单字段（见 P2-9 的 mass assignment）。
- **验证方式与结果**：**推理未验证**（无 go 工具链、无法实跑）。依据：GORM 文档"Query by primary key / Conditions"——字符串条件会作为 clause 直接进入 SQL；`First(&u, "10")` 被当主键、`First(&u, "1 OR 1=1")` 被当条件。建议修完后补一条 `httptest` 用例（`/api/todos/1%20OR%201=1` 应返回 400）。

### P2-2｜"每条 Dockerfile 指令生成一个新层"

- **位置**：`04:32`、`04:63`、`11:73`（并在 `04` 的 mermaid 里把 WORKDIR 标 0B、CMD 标"元数据"）
- **原文**：`每条 Dockerfile 指令生成一个新层：`
- **问题**：只有 `RUN`/`COPY`/`ADD` 产生**文件系统层**；`CMD`/`ENV`/`WORKDIR`/`LABEL`/`EXPOSE`/`USER` 只写镜像配置，在 `docker image history` 里是 0B 条目而非可复用层。04 自己的图（`04:38-41`）已经显示 0B，与文字结论冲突。这个差别直接决定"合并 RUN 能减层、合并 ENV 不能"。
- **修复建议**：改为"`RUN`/`COPY`/`ADD` 各生成一个只读层，其余指令只改镜像配置（history 里显示 0B）"。
- **验证方式**：官方 Dockerfile reference —— "The `RUN` instruction will execute any commands to create a new layer"（只有 RUN 被这样描述）；`docker image history` 的 0B 条目为已知行为。**未实跑**。

### P2-4｜"Docker 网络有五种模式"不完整

- **位置**：`06:56-62`、`11:162`
- **原文**：`> **结论**：五种模式——bridge（默认）、host、none、container、overlay。`
- **问题**：官方 Network drivers 共 **6 种驱动**：bridge / host / none / overlay / **ipvlan** / **macvlan**；`container:` 是 `docker run --network container:<id>` 的复用写法，不是独立驱动。面试场景下"只有五种"会被追问 macvlan/ipvlan（容器要"像物理设备一样出现在交换机上"时的唯一选择）。
- **修复建议**：改为"6 种驱动 + `container:` 复用模式"；11 章答案里补一句"需要容器直接拿局域网 IP 时用 macvlan/ipvlan"。
- **验证方式**：官方 Networking overview 驱动表（bridge/host/none/overlay/ipvlan/macvlan），<https://docs.docker.com/engine/network>。**未实跑**。

### P2-5｜`compose.prod.yaml` 同时有 `build` 与 `image`，与"从仓库拉取"的注释矛盾

- **位置**：`Go+Docker综合项目/compose.prod.yaml:3-8`（注释 + `image:`），叠加 `compose.yaml:6-8`（`build:`）
- **原文**：`# 生产从镜像仓库拉取（CI 构建并推送）` / `image: ghcr.io/summer/go-todo-api:${APP_VERSION:-latest}`
- **问题**：Compose 合并后该服务同时具备 `build` 和 `image`，`docker compose up` 的默认行为是**本地构建并打上该 tag**，而不是拉取；注释描述的行为需要 `pull_policy: always`（或删掉 build）才会发生。学习者按"方式四"操作会以为在验证 CI 产物，实际在本地重编译。
- **修复建议**：prod 覆盖里加 `pull_policy: always`，并把 `APP_VERSION=latest` 的示例改成具体版本（如 `APP_VERSION=1.0.0`）；或在 README 写明"本地验证生产镜像请先 `docker compose -f compose.yaml -f compose.prod.yaml build`"。
- **验证方式**：Compose 规范 `build`+`image` 语义（构建后以 image 命名）；`pull_policy` 为覆盖默认拉取行为的官方字段。**未实跑**。

### P2-6｜lab-07 的 db healthcheck 硬编码 `app/appdb`，与参数化 env 不一致

- **位置**：`labs/lab-07-compose/compose.yaml:36-45`
- **原文**：`POSTGRES_USER: ${DB_USER:-app}` / `test: ["CMD-SHELL", "pg_isready -U app -d appdb"]`
- **问题**：只要通过 `.env` 改了 `DB_USER`/`DB_NAME`（07 章正好教这个），healthcheck 就会一直 `pg_isready: ... no response`，`web` 因 `service_healthy` 永远不启动。这是"教学示例互相拆台"的典型。
- **修复建议**：`test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"]`（Compose 里 `$$` 转义成容器内 `$`）。
- **验证方式**：静态推演（healthcheck 在容器内执行，能读到同一 `environment`）；**未实跑**。

### P2-8｜CI 的 security job 扫 `:latest`，tag 触发时该 tag 可能不存在；且仓库没有任何 `*_test.go`

- **位置**：`.github/workflows/ci.yml:171`、`:83-87`；`:13-14`（schedule）
- **原文**：`image-ref: ${{ env.REGISTRY }}/${{ env.IMAGE_NAME }}:latest`
- **问题**：`metadata-action` 的 `type=raw,value=latest,enable={{is_default_branch}}` 在 **tag push** 事件下 `is_default_branch` 为假，只会推 semver tag；此时 security job 去扫 `:latest` 会 404。另外 `go test -race ./...` 在没有任何测试文件时只打印 `no test files` 并返回 0——CI 的 "Test" 关卡是空跑的，与 README「lint → test → build → push → Trivy」的描述不符。
- **修复建议**：security job 用 `${{ github.sha }}` 对应的 tag 或 `needs.build.outputs.image-digest` 按 digest 扫描；补 2-3 个 `main_test.go`（至少 `/health` 与 `POST /api/todos` 的 httptest），否则把 "Test" job 改名 "Build" 并注明"暂无测试"。
- **验证方式**：workflow YAML 静态解析（PyYAML 通过）+ `Glob **/*_test.go` 命中 0；`metadata-action` 的 `is_default_branch` 语义按其文档。**未实跑 CI**。

### P2-9｜`main.go` 忽略 `redis.ParseURL` 的错误 + PUT 的 mass assignment

- **位置**：`main.go:150`、`:287-302`
- **原文**：`opts, _ := redis.ParseURL(redisURL)` / `c.ShouldBindJSON(&todo)` → `db.Save(&todo)`
- **问题**：① `ParseURL` 失败时 `opts` 为 nil，`redis.NewClient(nil)` 会在后续 panic；且这违反项目自己的 `CONTRIBUTING.md`「错误处理：不忽略 error」。② `updateTodo` 把请求体直接绑定进从库里查出的 model，客户端传 `{"id": 999}` 就会把 **id=999 那行**覆盖掉（越权写），而不是更新 URL 里的 id。
- **修复建议**：`opts, err := redis.ParseURL(...)` 后 `log.Fatalf`；PUT 用独立 DTO（只含 `title`/`done`）再写回，`todo.ID` 始终取路径参数。
- **验证方式**：静态阅读 + CONTRIBUTING 自述规则比对；**未编译未实跑**。

### P2-10｜"同一 compose 文件可以 `docker stack deploy` 到 Swarm"

- **位置**：`07-Docker Compose 多容器编排.md:560`
- **原文**：`> 5. **尝试 Swarm Stack**：\`docker stack deploy -c compose.yaml myapp\`——同一文件可以用于 Swarm 部署`
- **问题**：`docker stack deploy` 只接受 v3 语法，且**不支持 `build`、`develop.watch`、`depends_on.condition`**；本章的 compose.yaml 恰好三样都用了。照做会得到 `unsupported Compose file version` 或被静默忽略。
- **修复建议**：改成"Swarm 需要单独维护一份 v3 文件（去掉 build/develop/condition）"，或把这条移到"可选迭代"并标注限制。
- **验证方式**：Swarm stack 的 compose v3 限制为官方已知约束；**未实跑**（本机无 Swarm）。

### P2-11｜`nginx.conf` 用 `add_header Content-Type` 会产出重复 Content-Type

- **位置**：`Go+Docker综合项目/nginx/nginx.conf:52`、`:90`
- **原文**：`add_header Content-Type text/plain;` / `add_header Content-Type application/json;`
- **问题**：`return 200 "ok\n"` 时 nginx 已按 `default_type`（默认 `application/octet-stream`）生成一个 `Content-Type`，`add_header` 再追加一个 → 响应里出现**两个** Content-Type。`location = /` 返回 JSON 时同理，某些客户端会取到 `application/octet-stream`。
- **修复建议**：改用 `default_type text/plain;` / `default_type application/json;`（或 `types { }`），删掉这两条 `add_header`。
- **验证方式**：nginx 指令语义（`add_header` 是追加，`default_type` 才是设定）；**未实跑 nginx**。

### P2-12｜`latest` 口径在项目内反复出现（与全套笔记"禁用 latest"的教导冲突）

## 3. 存疑待核实（不混入 P0/P1）

1. **`grafana/fluent-bit-plugin` 这个镜像是否存在**：官方只文档化 `grafana/fluent-bit-plugin-loki`。Docker Hub API 被本机网络策略拦截（SSRF 拦截），无法确认。若存在，P1-2 只剩"插件名应为 `grafana-loki`"这一半。
2. **`useradd -r -g app -u 1000 app`（`09:61`）**：`-r`（系统用户）配 `-u 1000` 在部分发行版会告警甚至拒绝（`SYS_UID_MAX`）。未在 debian 镜像内实测，故不立案；建议改为 `useradd -m -u 1000 app`。
3. **`docker ps -l`**（速查页 `:108`）：仍可用但已被 `--latest` 取代，27.x 是否打 deprecation 警告未实测。
4. **Compose `deploy.replicas` 在非 Swarm 下的扩缩容行为**（`07:257-266`、`compose.prod.yaml`）：`docker compose up` 会创建 N 个副本容器，但端口映射会冲突（本项目 prod 未给 api 映射端口，故不触发）。未实测。
5. **`08:491` 坑 1「COPY --from 的源路径是构建阶段的工作目录」**：`--from` 的相对路径解析基准（stage 根 vs stage WORKDIR）未在官方文档找到一句话定论，未立案。
